and in every test).

## 3. The single accounting clock — independent verification

- **Scope of the claim, now accurate:** the application's accounting clock (the same `SystemClock` instance that derives every journal's posting date) supplies
  `issuedAt` and `createdAt` of the credit note, `createdAt` of every line, `createdAt` / `updatedAt` of every refund line, and `resolvedAt` / `updatedAt` of every
  outcome. **No** timestamp written by this feature comes from the database clock. (Other tables' defaults, e.g. audit rows, are unchanged and outside the feature.)
- **Proof:** a test fixes the application clock, issues and attests, and asserts every one of those columns **to the millisecond** while the database's own clock
  is months later; it then advances the clock two days, attests, and asserts `resolvedAt` / `updatedAt` equal that instant and the journal's posting date is that
  instant's civil date in the company timezone. Three mutants (attestation time, note `createdAt`, line `createdAt`) are caught.
- **Residual:** the clock is trusted (§6, TA-6): a wrong host clock mis-dates documents **and** postings consistently — which is the point of one source — but it
  can select the wrong accounting period.

## 4. Can a refund be marked EXECUTED without the necessary financial evidence?

**Evidence required**, by method:

| Method                           | Evidence the system requires before `EXECUTED` exists                                                                                                                                                                                            |
| -------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| **CASH / BANK_TRANSFER**         | an **authenticated attester** (DB) · a **sealed execution journal with exactly the two expected lines** and the refund's amount (DB, deferred) · status + journal + audit row in **one transaction** (app) · a unique source key (one execution) |
| **CARD_TERMINAL / OTHER_MANUAL** | an **authenticated attester** (DB) · **no** journal may exist (DB) — the attestation is the only evidence                                                                                                                                        |
| **FAILED**                       | an authenticated attester and a reason code (DB) · **no** execution journal (DB)                                                                                                                                                                 |

**Every path that could set the status, and what stops it** (each row is executed by a test on real PostgreSQL):

| Path                                                                                  | Control                                                                                | Result                              | Test                                                                   |
| ------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------- | ----------------------------------- | ---------------------------------------------------------------------- |
| the HTTP route, authorised user                                                       | permission + step-up + idempotency + `PENDING`-only + journal + audit, one transaction | executes once                       | main integration; concurrency (8 racers → 1 success)                   |
| the HTTP route, cashier / issue-only / no step-up / view-only / foreign tenant        | route key, service-level authority, step-up, RLS                                       | refused, nothing written            | main integration (authority, isolation)                                |
| the same route twice / a replay                                                       | status guard `409`, terminal trigger, idempotency                                      | no second effect                    | main integration                                                       |
| the HTTP route in a closed period                                                     | one transaction                                                                        | rolled back, refund stays `PENDING` | ATOMICITY                                                              |
