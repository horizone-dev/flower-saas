# ADR-0010 — Prisma as the default ORM with a PostgreSQL RLS backstop; verdict from the Phase 0 spike

- **Status:** **Proposed — verdict pending Phase 0 Task 0.6 (the hard RLS/security gate)**
- **Related:** Z-5; architecture §46; [`../architecture/SECURITY.md`](../architecture/SECURITY.md); [ADR-0004](ADR-0004.md)

## Context

The isolation model (ADR-0004) uses PostgreSQL RLS as a backstop:
`tenant_id = current_setting('app.tenant_id')::uuid` on every tenant table, with the
GUC set by `SET LOCAL app.tenant_id` inside each request transaction. Two known
tensions:

1. **`SET LOCAL` is transaction-scoped.** It is safe with **session** and
   **transaction** pool modes but **unsafe with statement-level pooling** and unsafe
   if a scoped query runs outside a transaction.
2. **Prisma** historically had rough edges with per-request session variables and
   with PgBouncer in transaction mode (prepared-statement handling, interactive
   transactions).

## Decision (default, pending verification)

- **Prisma is the default ORM.** A Prisma **client extension** wraps every scoped
  operation in an **interactive transaction** that first issues
  `SET LOCAL app.tenant_id = $1` (and, where useful, `app.branch_id`), then runs the
  query. Non-scoped/platform operations use a separate client on an audited
  connection.
- **The app DB role is non-superuser, non-`BYPASSRLS`.** Migrations run as a
  separate, more-privileged role.
- **Pooling:** PgBouncer (or the managed equivalent) in **transaction** mode for the
  app; Prisma configured for pgbouncer (`pgbouncer=true`, no prepared-statement
  cache where required).

## The Phase 0 spike (Task 0.6 — the hard gate)

`tooling/spikes/rls/` builds: 2 tenant-scoped tables + an RLS policy; the Prisma
client extension issuing `SET LOCAL app.tenant_id` in interactive transactions;
tested against **real Docker PgBouncer** in **both `transaction` and `session` pool
modes**, plus a direct connection. It measures:

- **Isolation correctness** — tenant B cannot read/modify tenant A rows under either
  pool mode; a query that forgets the GUC returns **zero rows** (RLS denies), never
  another tenant's rows.
- **Connection behaviour** — no GUC bleed between pooled connections; `SET LOCAL`
  does not leak past the transaction; concurrent interleaved tenants stay isolated.
- **Correctness of interactive transactions** through the pooler; prepared-statement
  behaviour.
- **Latency** overhead of the wrapper transaction vs a bare query.

**Exit / verdict (written into this ADR at Task 0.6):**

- **`go`** — Prisma + the client extension + transaction-pool PgBouncer is
  sufficient for all paths; or
- **`go + Kysely fallback`** — Prisma for the bulk of the app, **Kysely** (raw,
  explicit SQL with a mandatory scope predicate) for scope-critical read paths where
  the spike shows Prisma cannot guarantee the GUC discipline under pooling. If this
  verdict is chosen, a follow-up Phase 0 task is appended and **completed before
  `phase-0-complete`**.

## Consequences

- The verdict is a **hard gate** on Phase 0 completion. RLS is not weakened to pass
  the spike; if it fails, the fallback is adopted.
- Whatever the verdict, the application layer (ADR-0004) remains the primary control
  and the CI probe suite remains build-blocking.
