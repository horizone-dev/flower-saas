# ADR-0010 — Prisma as the default ORM with a PostgreSQL RLS backstop; verdict from the Phase 0 spike

- **Status:** **Accepted — verdict `GO` (Task 0.6, 2026-09-03). No Kysely fallback.**
- **Related:** Z-5; architecture §46; [`../architecture/SECURITY.md`](../architecture/SECURITY.md); [ADR-0004](ADR-0004.md)

## Context

The isolation model (ADR-0004) uses PostgreSQL RLS as a backstop:
`tenant_id = current_setting('app.tenant_id')::uuid` on every tenant table, with the
GUC set by `SET LOCAL app.tenant_id` inside each request transaction. Two known
tensions:

1. **`SET LOCAL` is transaction-scoped.** It is safe with **session** and
   **transaction** pool modes but **unsafe with statement-level pooling** and unsafe
   if a scoped query runs outside a transaction.
2. **Prisma** historically had rough edges with per-request session variables and
   with PgBouncer in transaction mode (prepared-statement handling, interactive
   transactions).

## Decision (default, pending verification)

- **Prisma is the default ORM.** A Prisma **client extension** wraps every scoped
  operation in an **interactive transaction** that first issues
  `SET LOCAL app.tenant_id = $1` (and, where useful, `app.branch_id`), then runs the
  query. Non-scoped/platform operations use a separate client on an audited
  connection.
- **The app DB role is non-superuser, non-`BYPASSRLS`.** Migrations run as a
  separate, more-privileged role.
- **Pooling:** PgBouncer (or the managed equivalent) in **transaction** mode for the
  app; Prisma configured for pgbouncer (`pgbouncer=true`, no prepared-statement
  cache where required).

## The Phase 0 spike (Task 0.6 — the hard gate)

`tooling/spikes/rls/` builds: 2 tenant-scoped tables + an RLS policy; the Prisma
client extension issuing `SET LOCAL app.tenant_id` in interactive transactions;
tested against **real Docker PgBouncer** in **both `transaction` and `session` pool
modes**, plus a direct connection. It measures:

- **Isolation correctness** — tenant B cannot read/modify tenant A rows under either
  pool mode; a query that forgets the GUC returns **zero rows** (RLS denies), never
  another tenant's rows.
- **Connection behaviour** — no GUC bleed between pooled connections; `SET LOCAL`
  does not leak past the transaction; concurrent interleaved tenants stay isolated.
- **Correctness of interactive transactions** through the pooler; prepared-statement
  behaviour.
- **Latency** overhead of the wrapper transaction vs a bare query.

**Exit / verdict (written into this ADR at Task 0.6):**

- **`go`** — Prisma + the client extension + transaction-pool PgBouncer is
  sufficient for all paths; or
- **`go + Kysely fallback`** — Prisma for the bulk of the app, **Kysely** (raw,
  explicit SQL with a mandatory scope predicate) for scope-critical read paths where
  the spike shows Prisma cannot guarantee the GUC discipline under pooling. If this
  verdict is chosen, a follow-up Phase 0 task is appended and **completed before
  `phase-0-complete`**.

## Consequences

- The verdict is a **hard gate** on Phase 0 completion. RLS is not weakened to pass
  the spike; if it fails, the fallback is adopted.
- Whatever the verdict, the application layer (ADR-0004) remains the primary control
  and the CI probe suite remains build-blocking.

---

### Verdict — **GO** (recorded 2026-09-03, Task 0.6)

**Decision: `go`.** Prisma 7 + `@prisma/adapter-pg` + an interactive transaction that
first calls `set_config('app.tenant_id', $1, true)` (i.e. `SET LOCAL`, parameter-bound)
provides correct, fail-closed tenant isolation under a direct connection **and**
PgBouncer in **both** transaction-pool and session-pool modes. **No Kysely fallback
is required.**

#### The spike

`tooling/spikes/rls/` — real stack via `docker-compose.yml` (isolated project
`flower-rls-spike`): `postgres:17` + two `edoburu/pgbouncer` front-ends
(`pool_mode=transaction` on :55533, `pool_mode=session` on :55534) + a direct
connection (:55532). Two tenant-scoped tables (`spike_tenant`, `spike_row`); a
`spike_app` role that is **`NOSUPERUSER NOBYPASSRLS`**; RLS **enabled + FORCED** on
both tables; policies key off `nullif(current_setting('app.tenant_id', true), '')::uuid`
so an **unset or empty** GUC yields **zero rows**, never a cross-tenant match.
21 assertions, run against **each** of the three endpoints:

| Check                                                                                                                | direct | pgb-transaction | pgb-session |
| -------------------------------------------------------------------------------------------------------------------- | ------ | --------------- | ----------- |
| Scoped read sees only the acting tenant (A: 5 rows, B: 3 rows)                                                       | ✅     | ✅              | ✅          |
| Scoped read cannot fetch the other tenant's row by primary key                                                       | ✅     | ✅              | ✅          |
| **Unscoped** query (no GUC) → **0 rows** (fails closed, no error, no leak)                                           | ✅     | ✅              | ✅          |
| **No GUC bleed** — after a scoped txn, a new statement on the pooled connection sees `app.tenant_id = ''` and 0 rows | ✅     | ✅              | ✅          |
| `WITH CHECK` blocks inserting a row for another tenant                                                               | ✅     | ✅              | ✅          |
| 20× interleaved concurrent `A‖B` transactions stay isolated                                                          | ✅     | ✅              | ✅          |

Interactive transactions work correctly through PgBouncer transaction mode with the
`pg` driver adapter (default `?pgbouncer=true`); no prepared-statement breakage
observed at this scale.

#### Latency (wrapper overhead)

| endpoint              | scoped read p50 / p95 | bare `SELECT 1` p50 |
| --------------------- | --------------------- | ------------------- |
| direct                | 4.28 ms / 10.9 ms     | 1.08 ms             |
| pgbouncer-transaction | 4.49 ms / 7.64 ms     | 0.94 ms             |
| pgbouncer-session     | 4.17 ms / 6.4 ms      | 0.88 ms             |

The scoped wrapper adds **~3 ms** (one extra `BEGIN` / `set_config` / `COMMIT` round
trip) over a bare query, consistent across all modes. Acceptable for OLTP;
batch/read paths that need to shave it can share one transaction across several
reads.

#### Production guidance

- **Use PgBouncer `pool_mode = transaction`.** It multiplexes at transaction
  granularity, so N concurrent short scoped transactions share a small server pool
  efficiently.
- **Session mode is viable but requires `pool_size ≥ (app connection-pool size +
concurrency headroom)`** — with a small session pool, concurrent interactive
  transactions queue and can hit Prisma's `maxWait`. Not recommended.
- The app DB role is `NOSUPERUSER NOBYPASSRLS`; migrations run as a separate,
  more-privileged role.
- Every scoped table gets `ENABLE` **and** `FORCE ROW LEVEL SECURITY`.
- Policies use `nullif(current_setting('app.tenant_id', true), '')::uuid` so a
  missed GUC is a closed door, not an exception and not a leak.
- Phase 1 wraps this in `ScopedRepository` / a Prisma client extension; the
  `no-raw-prisma-in-scoped-modules` and `no-scope-from-request` lint rules (Task
  0.2) plus the build-blocking probe suite enforce that every scoped query goes
  through it.

#### Notes / limits of the spike

- A formal `/security-review` could not be auto-run (the GitHub remote is still
  empty, so it has no `origin/HEAD` to diff). A manual review of the spike covered:
  policy fail-closed semantics, `NOSUPERUSER/NOBYPASSRLS`, `FORCE RLS`,
  parameter-bound `set_config` + UUID pre-validation (no SQL injection),
  `SET LOCAL` transaction scoping, and rollback safety. The full automated
  security-review + cross-tenant probe suite runs in Phase 1 CI against real
  endpoints.
- Scale tested is functional, not load. A k6-style pool/prepared-statement stress
  test at Phase 10 hardening volume is a follow-up, not a Phase 0 blocker.
- Spike code is committed once for the record (`tooling/spikes/rls/`) and may be
  removed in a later commit.
