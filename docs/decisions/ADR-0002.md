# ADR-0002 — Four user-facing apps, no Staff App

- **Status:** Accepted (2026-09-03, V3 requirements revision)
- **Related:** architecture §1, §11; [ADR-0003](ADR-0003.md)

## Context

The original Master Prompt specified five apps including a dedicated Staff Mobile
App. The V3 requirements revision removed it. Where V3 and the original conflict,
V3 governs.

## Decision

**Exactly four user-facing applications:**

1. **Super Admin Web** (`apps/super-admin-web`) — platform control plane, separate
   deployment, separate auth realm.
2. **Owner Web** (`apps/owner-web`) — full tenant-wide business management.
3. **POS PWA** (`apps/pos-pwa`) — _Sell_ / _Manage_ / _My workspace_ route groups.
   **The full workforce module lives here**, gated by permission.
4. **Customer Web / PWA** (`apps/customer-web`) — multi-tenant storefront + AI chat.

**No Staff App. No fifth or sixth app.** The self-service staff surface is built as
`/v1/me/*` API endpoints whose **only consumer is the POS PWA** (_My workspace_).
`apps/staff-mobile` is deleted from the plan and will not be scaffolded.

## Consequences

- **Positive:** one less frontend to build, secure, test and ship; workforce
  features get the POS PWA's offline/realtime/device infrastructure for free.
- **Negative:** staff without POS access cannot self-serve on a phone in v1
  (accepted — the workforce backend is complete, a thin staff PWA can be added later
  against the existing `/v1/me/*` API with no backend change).
- Owner Web and the POS _Manage_ surface **share `packages/ui` feature components**;
  they differ only in default data scope (tenant-wide vs acting branch).

## Alternatives considered

- Keep the Staff App — rejected per V3.
- Fold _My workspace_ into a generic tenant portal — rejected: staff context is
  branch- and device-bound, which the POS PWA already models.
