## Context

`ARCHITECTURE.md §13–14` + ADR-0009 specify: PostgreSQL (domain write + outbox row,
one txn) → outbox dispatcher (`SKIP LOCKED`) → Redis Stream (per tenant, 24h) →
realtime gateway → clients; every event carries a per-tenant monotonic `seq`; the
client tracks `last_seq` per topic and full-REST-resyncs when it falls too far
behind.

The post-Phase-0 ultra-review (findings **F8**, **F9**) showed the Phase-0 seed's
gap logic is wrong under any real cross-topic interleaving:

- **F8** — if `seq` is per-tenant-global, a single topic only sees a sparse subset
  of the tenant's `seq` values, so a per-topic arithmetic gap test
  (`e.seq > prevSeq + maxSeqGap`) fires `gap-needs-resync` routinely even though
  nothing was lost.
- **F9** — the reducer's `stale` branch records the `eventId` but does not advance
  the per-topic `seq` mark, so a later in-order event can trip a false gap against
  a stale-lagging mark.

The owner's Phase 2-core decisions **OD-P2-3**, **OD-P2-4** and constraint
**FC-1** set the direction; this ADR records the resolved protocol so code, docs
and the gateway agree.

## Decision

### 1. `seq` — per-tenant-global, monotonic, assigned once, immutable

- `seq` is a **per-tenant-global** monotonically increasing integer. It is
  allocated by the **outbox dispatcher** (a single leader per tenant, via a
  PostgreSQL advisory lock), so within a tenant it is strictly increasing across
  all topics.
- **`seq` is assigned exactly once and is immutable** (FC-1). Dispatcher order of
  operations: (1) claim a batch of undispatched `outbox` rows
  (`FOR UPDATE SKIP LOCKED`, ordered by `created_at` then `id`); (2) for each row
  **where `outbox.seq IS NULL`**, allocate the next per-tenant value and write it
  with `UPDATE outbox SET seq = $seq WHERE id = $id AND seq IS NULL`, **committed
  before the Redis publish**; (3) `XADD` using the persisted `seq`; (4) mark
  `dispatched_at`. A row re-selected after a crash **already carries its `seq`**
  and is **never re-allocated** — a retried `XADD` republishes the identical
  `seq`.
- **OI-P2-1 is resolved in task 2.4** such that persisted `seq` assignment and
  concurrent dispatch **cannot** violate the ordering semantics above.
  Requirements (correctness first, minimum complexity):
  - a **single active dispatcher leader per tenant** (a PostgreSQL advisory lock
    keyed on a tenant bucket) — only the leader allocates `seq` for that tenant,
    so allocation is serialized and strictly increasing;
  - `seq` comes from a durable monotonic source (a per-tenant `pg` SEQUENCE, or a
    `tenant_outbox_seq` counter row updated `FOR UPDATE` in the claim transaction)
    — the choice is task 2.4's, but it must be **crash-safe and gap-tolerant**
    (`seq` gaps are harmless; `seq` reuse or reorder is not);
  - the claim → `seq`-stamp step **commits before any `XADD`**, so a crash cannot
    publish a `seq` that was never persisted;
  - rows are stamped in `(created_at, id)` order within a tenant, so `seq` order
    matches append order;
  - retry identity is stable: `event_id` (§2) and `seq` are both read back from the
    row on any re-dispatch, never recomputed from volatile state.
    A second (non-leader) dispatcher that happens to `SKIP LOCKED`-claim a row for a
    tenant it is not leader for must **not** stamp `seq` — it defers the row (leaves
    `dispatched_at`/`seq` null) for the leader. Task 2.4 records the exact mechanism
    in this ADR and in `PHASE-2-CORE-PLAN.md`.

  **OI-P2-1 resolution (task 2.4, 2026-09-04):** a `outbox_tenant_seq` counter
  table — one row per tenant, `(tenant_id PK, next_seq bigint, updated_at)` —
  incremented via `INSERT … ON CONFLICT DO UPDATE SET next_seq = next_seq + 1
RETURNING next_seq - 1` (never `MAX(seq)+1`, which would race). Chosen over a
  dynamic per-tenant `SEQUENCE` object: a plain table row is simpler to create,
  migrate, seed in tests, and reason about transactionally (a `SEQUENCE`'s
  `nextval()` is **not** transactional — it does not roll back with the
  transaction, which would break the "gaps are acceptable, reuse is not"
  invariant across a crash exactly the way a plain counter row does not).
  Concretely, per allocation attempt:

  1. one `runPlatform` transaction (`flower_platform`, BYPASSRLS — the
     dispatcher is inherently cross-tenant infra) calls
     `pg_try_advisory_xact_lock(hashtext('outbox_seq:' || tenant_id))`;
  2. only on success (leader): `SELECT … FOR UPDATE` every unstamped, eligible
     row for that tenant, `ORDER BY created_at, id`, then for each row in that
     order: increment `outbox_tenant_seq` and `UPDATE outbox SET seq = …
WHERE id = … AND seq IS NULL` (keyed on `id` alone — a `uuidv7()`, already
     globally unique; `created_at` is part of the row's composite primary key
     only because Postgres range-partitioning requires the partition key in
     every unique constraint, not for row identity);
  3. the whole transaction **commits** — this is the "before any `XADD`" point;
     the lock (transaction-scoped `pg_advisory_xact_lock`) releases here, which
     is the entirety of what a "leadership handover" is: the next caller to try
     the same lock simply succeeds once this transaction is gone (commit,
     rollback, or the connection dying in a crash — Postgres releases every
     lock held by a backend whose connection drops).

  Publishing (the `XADD` step) is a **separate**, later, lock-free step —
  `SELECT … FOR UPDATE SKIP LOCKED LIMIT 1` on any row with a non-null `seq`
  and `dispatched_at IS NULL`, globally oldest-first across tenants, one row
  per transaction. It needs no tenant-level coordination: by the time a row is
  eligible to publish its `seq` is already immutable and final, and per §3 a
  duplicate or reordered _live_ delivery is explicitly tolerated by the
  approved client protocol — only the **allocation** step's ordering is a hard
  invariant, and that is what the advisory lock protects. See
  `apps/worker/src/outbox/{seq-allocator,publisher,dispatcher}.ts` and their
  Testcontainers Postgres+Redis suite for the full acceptance evidence (single
  event; ordered multi-event; concurrent different tenants; two processes
  racing for one tenant; leader handover; seq immutability; the three FC-1
  crash scenarios; a dedup consumer; Redis-down retry/backoff/recovery; one
  failing tenant never blocking another; no secret-bearing field in the
  envelope).

### 2. `event_id` — deterministic, immutable

- `event_id` is **derived deterministically from the `outbox` row id** (e.g. the
  row UUID, or `uuidv5(namespace, outbox_id)`). A crash-induced re-publish carries
  the **same `event_id`**. It is the dedup key everywhere downstream (client
  reducer, gateway short-window dedup).

### 3. The durable cursor is the **Redis Stream entry ID**, not `seq`

- Each tenant has **one durable Redis Stream**, `rt:stream:{tenantId}`, holding
  **every** event for that tenant (all branches, all resource types). The
  dispatcher `XADD`s the full envelope.
- **The Redis Stream entry ID / retained-stream position is the single
  correctness basis for resume and retention-gap detection.** Nothing else is.
- The client stores a **scanned Stream cursor** — the entry ID up to which the
  gateway has consumed the stream _on that client's behalf_ (§6a). Resume =
  `XRANGE rt:stream:{tenantId} (<scannedCursor> +`, with the gateway filtering
  **payload delivery** to the client's authorized/subscribed topics but still
  advancing the scanned cursor across every scanned entry.
- **`seq` is a logical ordering / diagnostic value only.** Uses: per-topic UI
  ordering, human debugging, and an **informational** figure in the heartbeat. It
  is **never** an input to any resync decision — see §7.
- `DEFAULT_MAX_SEQ_GAP` and **any `tenantHighWaterSeq − clientLastSeq` threshold
  check are removed**. There is no arithmetic `seq`-distance resync trigger of any
  kind (per-topic _or_ tenant-global). Because `seq` is tenant-global, unrelated
  branch/topic activity advances the tenant high-water arbitrarily; using that
  distance would re-create the F8 false-resync.

### 4. Fanout — durable Stream → relay → Redis Pub/Sub → every gateway (OD-P2-4)

A Redis **consumer group is not the socket-broadcast mechanism** — a consumer
group _distributes_ entries among its members, so with N gateway instances each
event would reach only one instance and the sockets on the other N−1 would miss
it.

```
PostgreSQL outbox   (domain write + outbox row, one txn)
  → dispatcher        assigns seq (once), XADD → durable stream
  → rt:stream:{tenantId}          Redis Stream — event history / resume source
  → realtime relay                one logical consumer of the stream per tenant
  → PUBLISH rt:live:{tenantId}    Redis Pub/Sub — live multi-gateway fanout
  → every realtime gateway instance   (each SUBSCRIBEs for tenants it holds sockets for)
  → authorized branch/resource subscriptions → WebSocket clients
```

- The **relay** consumes `rt:stream:{tenantId}` (a consumer group is fine _here_ —
  this is the relay's own horizontal scaling / restart-resume, not socket
  broadcast) and `PUBLISH`es each event to the tenant's Pub/Sub channel. A relay
  restart may replay a few already-published events → **duplicate live delivery is
  acceptable** and is suppressed downstream by `event_id`.
- **Live delivery is at-least-once.** The gateway (and ultimately the client
  reducer) deduplicates by `event_id`.
- Pub/Sub channel granularity (one `rt:live:{tenantId}` vs per-topic channels) is
  settled in task 2.5 against fan-out cost (OI-P2-4). Whatever the granularity, the
  gateway only forwards an event to a socket whose **server-assigned** topics
  match.
- **Resume/replay never uses Pub/Sub** — it always reads the durable Stream.

### 5. Retention — time-based, ~24h target, not a `MAXLEN` guarantee (Z-7)

- A scheduler job periodically trims each stream by **time**:
  `XTRIM rt:stream:{tenantId} MINID ~ <streamId floor for (now − 24h)>` (and/or
  `XADD … MINID ~` on publish). The `~` (approximate) form is used for efficiency.
- The 24h figure is a **retention target driven by elapsed time**, not a bounded
  entry count. Documentation and metrics describe it as "≈ 24h time-based
  retention", **never** as "`MAXLEN` = 24h".
- A client whose **scanned Stream cursor** (§6a) is older than the stream's first
  retained entry (`XINFO STREAM` first-entry id > scanned cursor) must do a **full
  REST resync** (§7). Because the gateway advances the scanned cursor across _all_
  stream entries (§6a), a client only lands here after being genuinely
  offline/idle longer than the retention window — not because other branches were
  busy.

### 6a. The scanned Stream cursor — advances across the whole stream, not just delivered events

A client subscribes to a **subset** of the tenant's topics (some branches / some
resource types). The tenant's single stream carries **all** of them. Two cursors
are distinguished:

| Cursor                                                                                                            | Meaning                                                                                             | Advances                                                                                                                                                       |
| ----------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **scanned Stream cursor** (the one the client persists, sends on reconnect, and uses for retention-gap detection) | the Stream entry ID up to which the gateway/relay has _consumed_ the stream on this client's behalf | across **every** stream entry the gateway passes — including entries for topics the client is **not** subscribed to and entries whose payload was filtered out |
| **applied cursor** (client-side, per resource / per topic — for UI ordering)                                      | the last event actually applied to local state                                                      | only on a delivered, newer event                                                                                                                               |

- The gateway, whether live-forwarding or replaying, **always advances the scanned
  cursor to the id of the last stream entry it read**, and reports that id to the
  client (in each delivered frame and in the heartbeat — §6c). The client persists
  it.
- Consequence: **unrelated tenant activity can never leave a client permanently
  behind.** A branch-A-only client whose branch saw no events during a burst of
  thousands of branch-B events still has a scanned cursor near the stream tail,
  because the gateway advanced it while scanning past the branch-B entries.
- The server **filters payload delivery** to authorized/subscribed topics; it does
  **not** filter cursor advancement.

### 6b. Out-of-order & stale — applied cursor gates payload, scanned cursor is untouched (F9)

The client reducer separates the concerns the Phase-0 seed conflated:

| Concern                                  | Advances on                                                                              | Never advances on             |
| ---------------------------------------- | ---------------------------------------------------------------------------------------- | ----------------------------- |
| **scanned Stream cursor** (§6a)          | every stream entry read — regardless of `applied` / `duplicate` / `stale` / filtered-out | —                             |
| **resource state** (`versionByResource`) | a genuinely newer `resource_version`                                                     | a `stale` / `duplicate` event |

"Seeing an event" ≠ "applying its payload". A `stale` / `duplicate` / not-for-me
result still moves the scanned cursor forward, so it can never feed a false gap
(fixes **F9**).

### 6c. Heartbeat contents

The gateway heartbeat carries:

- **current Redis Stream tail entry ID** (authoritative — the client compares its
  scanned cursor against the retained range using this and the resume response);
- **current scanned cursor for this connection** (so a client that has been idle
  still learns how far the gateway has consumed on its behalf and persists it);
- **tenant high-water `seq`** — **informational / diagnostic only**. It is **not**
  compared arithmetically to anything to decide a resync.

### 7. Resync trigger — retained-Stream-range only, never arithmetic `seq` distance (F8)

A full REST resync of the affected lists is triggered **only** when the client's
**scanned Stream cursor falls outside the stream's retained range**:

1. **Retention gap** — on reconnect (or on a heartbeat), the client's persisted
   scanned cursor is **below the stream's first retained entry id**
   (`XINFO STREAM` first-entry-id > scannedCursor). The client was offline / idle
   longer than the ≈ 24h time-based retention window **and** the gateway did not
   advance its cursor in time; **or**
2. **Explicit `resync-required`** from the gateway `resume` handler, which
   detected case 1 server-side (`XRANGE` from the client's cursor returns
   `ERR invalid stream ID` / the cursor precedes the retained floor).

There is **no** resync triggered by `tenantHighWaterSeq − clientLastSeq`, by a
per-topic `seq` delta, by `DEFAULT_MAX_SEQ_GAP`, or by any other arithmetic
`seq`-distance measure. `seq` is tenant-global, so unrelated branch/topic activity
advances the tenant high-water without the client missing anything of its own —
an arithmetic check would re-create F8. Normal cross-topic interleaving (one
topic's consecutive events at `seq = 100` then `seq = 900`) produces **zero**
resyncs.

After a resync: the client discards its per-resource/-topic applied marks,
refetches the affected lists over REST, and sets its **scanned cursor to the
current stream tail id** returned by the resync response / heartbeat.

### 8. The event is a change signal, never authoritative state

- The envelope payload is a **small summary** (`{event_id, seq, tenant_id,
branch_id, type, resource_type, resource_id, resource_version, occurred_at,
actor_summary}`). The client **refetches the resource over REST** for full
  detail.
- Every screen is buildable from REST alone; a confirm action always re-validates
  server-side (CLAUDE.md rule 30). Realtime only accelerates.
- State truth = **REST/API + PostgreSQL**. Durable history/resume = **Redis
  Stream**. Live fanout = **Redis Pub/Sub**. These three are never conflated.

### 9. Subscription authorization (unchanged intent, restated)

- The client connects with its access token. The gateway resolves the session →
  tenant + branch scope and **assigns** topics `t:{tenantId}:b:{branchId}:{resourceType}`.
  A client-supplied topic string is ignored.
- The guard pipeline re-runs on **every** `subscribe` and on **every** token
  refresh. Session revocation → Redis Pub/Sub (`rt:revoke:{sessionId}`) → **every**
  gateway instance drops that socket (< 5s).

## Delivery-semantics summary (aligns ADR-0009)

| Layer                              | Guarantee                                                                                                                                                |
| ---------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------- |
| domain write + `outbox` row        | **atomic** (one PostgreSQL transaction)                                                                                                                  |
| dispatcher → durable Stream        | **at-least-once**; `seq` + `event_id` assigned once, immutable, reused verbatim on retry                                                                 |
| relay → Pub/Sub → gateway → socket | **at-least-once**; duplicates suppressed by `event_id`                                                                                                   |
| scanned Stream cursor              | advances across **every** stream entry the gateway reads (incl. filtered-out / other-branch) — so unrelated tenant activity never leaves a client behind |
| business effect of an event        | **effectively-once** — downstream consumers and the client reducer are idempotent on `event_id`                                                          |

There is **no claim of transport-level exactly-once** between PostgreSQL and Redis.
A crash after the Redis publish but before the PostgreSQL `dispatched_at` ack
**will** cause a duplicate transport delivery; both copies carry the identical
`event_id` and `seq`, and downstream processing stays correct.

## Acceptance tests (frozen for tasks 2.5 / 2.6 — the CI `realtime` job)

1. **F8 — cross-topic interleave, no false resync.** A long run where events for
   several `resourceType`s on one branch interleave (per-topic `seq` deltas of
   hundreds are normal) → the reducer returns **zero** `gap-needs-resync`; every
   event is `applied` or a legitimate `duplicate` / `stale`.
2. **F9 — reorder does not trip a false gap.** A higher-`seq` message carrying a
   lower `resource_version` is delivered (result `stale`), then an in-order event
   arrives → **no** `gap-needs-resync`; the position advanced past the stale
   event.
3. **Retention gap → resync.** A client reconnects with a stored scanned cursor
   below the stream's retained floor (it was genuinely offline > retention) →
   `resync-required`; after the REST resync its scanned cursor is the current tail
   and subsequent events apply in order.
4. **Within-retention reconnect → exact replay.** A client disconnects, N events
   land, it reconnects with its stored scanned cursor → it receives exactly those
   N events (filtered to its authorized topics), in order, none applied twice; its
   scanned cursor ends at the stream tail.
5. **Unrelated-tenant-activity does NOT cause a false resync (owner clarification,
   2026-09-04).** A client subscribed **only** to branch A. Thousands of events
   occur for **branch B**. Branch A receives **no** event during that period. The
   heartbeat's tenant high-water `seq` advances greatly. Asserts:
   - the client performs **no** full resync;
   - the client's **scanned Stream cursor advances** to ≈ the stream tail (driven
     by the gateway scanning past the branch-B entries / heartbeat), even though
     zero payloads were delivered;
   - a reconnect **within retention** replays correctly from the scanned cursor
     (branch A gets its next real event; no re-scan storm, no resync);
   - **no code path compares `tenantHighWaterSeq − clientLastSeq`.**
6. **FC-1 crash-republish identity.** Kill the dispatcher between `XADD` and the
   `dispatched_at` update; on restart the row republishes → the two stream entries
   have the **identical `event_id` and `seq`**; the client reducer applies it once.
7. **Multi-gateway fanout (≥ 2 instances).** A client on gateway A and a client on
   gateway B, both authorized for branch X, both receive the same event (live path
   = Pub/Sub, not a consumer group).
8. **Isolation.** A branch-X client never receives a branch-Y event; a tenant-B
   client never receives a tenant-A event; a client cannot subscribe to an
   arbitrary topic string; a token refresh that narrows scope stops the
   now-unauthorized topic.
9. **Revocation.** Session revoke closes the socket on **every** gateway instance
   in < 5s.
10. **Fault injection.** Kill the gateway / dispatcher / relay / Redis connection
    mid-stream → the client reconnects and converges to the REST-authoritative
    state (resync where the retention window was exceeded, replay otherwise).

## Consequences

- **Positive.** F8/F9 are structurally resolved: there is **no arithmetic
  `seq`-distance resync trigger at any granularity** (per-topic _or_ tenant-global
  high-water). Resume + retention-gap detection rest **only** on the scanned Redis
  Stream cursor vs the stream's retained range. The scanned cursor advancing
  across _all_ stream entries means unrelated branch/topic activity can never
  strand a client. Multi-gateway fanout is correct by construction (Pub/Sub, not a
  consumer group). `seq` + `event_id` immutability makes at-least-once transport
  safe. Retention is honest ("≈ 24h time-based").
- **Negative / cost.** One more moving part (the relay) between the stream and the
  gateway. Live delivery is at-least-once, so the client reducer and every
  downstream consumer **must** be idempotent on `event_id` (already required). The
  gateway must scan (and advance the cursor past) stream entries it will not
  deliver to a given client — cheap, but it means a busy tenant's stream is read
  in full by the relay regardless of any single client's subscription. Per-tenant
  single-leader `seq` allocation is a mild serialization point in the dispatcher
  (acceptable at MVP tenant volume; revisit with load).
- **Follow-ups.** The Phase-0 seed's `EventReducer` gap logic + `RealtimeEvent`
  doc comment are updated to match (comment in Task 2.0; logic in Task 2.6). SSE
  fallback transport stays a backlog item (B9) — it does not change this protocol.
