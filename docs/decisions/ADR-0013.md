# ADR-0013 — Toolchain and dependency version pins

- **Status:** Accepted (2026-09-03, during Phase 0 Task 0.1)
- **Related:** [`../phase-0/PHASE-0-PLAN.md`](../phase-0/PHASE-0-PLAN.md); `package.json`, `.npmrc`, `.nvmrc`

## Context

The Phase 0 plan text referred to "pnpm 9.x" and to library versions that are now
behind current stable releases. The owner requires that any deliberate deviation
from the frozen plan is recorded in an ADR, not changed silently. Verified against
the live registry on 2026-09-03.

## Decision

### `pnpm` config notes

- `package.json` → `pnpm.supportedArchitectures` includes `win32`, `linux`, `darwin`
  × `x64`, `arm64` so platform-specific optional binaries (Turborepo's Rust binary,
  SWC, Prisma engines) resolve on dev machines **and** Linux CI.
- `pnpm.onlyBuiltDependencies` allow-lists packages permitted to run install
  scripts (`lefthook` so far).
- `.npmrc`: `save-exact=true`, `auto-install-peers=true`, `dedupe-peer-dependents=true`,
  minimal `public-hoist-pattern` allow-list (prettier, eslint, `@types/node`).

| ---------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **`packages/db` — schema location**                  | Prisma schema lives in `packages/db` (not `infra/db`)                                                                                                                                                                                                                                                                    | Already anticipated by §P0's own "Refinement" footnote — `api` / `worker` / `scheduler` share one generated client + one migration history.                                                                                                                                                                               |
| **`prisma-client-js` generator + Prisma 7 config**   | Prisma 7 removed `datasource.url` from the schema; connection URLs live in `prisma7.config.ts` and the runtime `PrismaClient` takes a `pg` driver adapter (`@prisma/adapter-pg`). | **NEW package `@flower/service-runtime`** (Task 0.7) | A shared plumbing package for the three non-API runtime roles (`worker` / `scheduler` / `realtime`): env parsing, pino logger, Redis connect/health helper, a tiny health HTTP server, graceful-shutdown wiring.                                                                                                         | ~130 lines of identical bootstrap plumbing would otherwise be copy-pasted into three apps. ### Environment prerequisite recorded

The dev machine required the **Microsoft Visual C++ 2015–2022 x64 Redistributable**
(it was missing — `api-ms-win-crt-*` / `vcruntime140.dll` absent), without which no
MSVC-linked native binary (Turborepo, Next SWC, Prisma engine) loads. Installed
2026-09-03. Recorded here and in `PHASE-0-RESULTS.md` as an environment
prerequisite for Windows dev boxes.

## Consequences

- Deviations are visible and reversible. Each "DEVIATION" row is revisited when the
  upstream stable release catches up (TS 7 GA adoption; Prisma 8 GA).
- `pnpm install --frozen-lockfile` is the reproducibility contract in CI.

## Amendment (2026-09-04, Phase 2-core Task 2.0 — constraint FC-3 / OD-P2-8)

The §"Structural deviations" table said _"Phase 2 folds these processes onto the
`apps/api` domain modules and [`@flower/service-runtime`] shrinks or merges."_ The
owner's Phase 2-core constraints make this precise:

- **`api`, `worker`, `scheduler`, `realtime` remain separate OS processes /
  Docker Compose services** — not merged into the API process — each with its own
  failure / restart / scaling boundary (OD-P2-8).
- **"Fold onto the domain modules" means _reuse_, not _co-locate_.** The minimum
  reusable backend module layer currently under `apps/api/src/common/*` (+ the
  domain service/repository layer of `apps/api/src/modules/*` that a non-API
  process actually consumes) is **extracted into a new package,
  `@flower/backend`** (`packages/backend`), containing **no HTTP controllers, no
  Fastify request wiring, no `main.ts`/CORS/Swagger**.
- `apps/api` keeps its controllers + HTTP guard/interceptor wiring + `main.ts` and
  depends on `@flower/backend`. `apps/worker` and `apps/scheduler` depend on
  `@flower/backend` and boot a Nest **application context**
  (`NestFactory.createApplicationContext`). Business rules stay implemented
  **once** (CLAUDE.md rule 1).
- `eslint-plugin-boundaries` gains `@flower/backend` as an element type;
  `apps/worker` / `apps/scheduler` may depend on `@flower/backend` + `@flower/*`
  libs **only** — a dependency on `apps/api` or any `*controller*` / Fastify
  module **fails lint**.
- The extraction is **minimum-scope, no speculative redesign**; `@flower/service-runtime`
  stays for the shared bootstrap plumbing (env / logger / Redis health / graceful
  shutdown) and does **not** merge into `@flower/backend`.
- The realtime co-deployment window (ADR-0009: co-deploy through Phase ~6) is
  unchanged — co-deployed ≠ same process.
