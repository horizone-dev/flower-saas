# ADR-0012 — e-invoicing behind country adapter ports; KSA onboarding gated on ZATCA

- **Status:** Accepted (2026-09-03, Z-8)
- **Related:** architecture §45, §R.3; [ADR-0007](ADR-0007.md), [ADR-0011](ADR-0011.md)

## Context

KSA ZATCA (Fatoora) Phase 2 e-invoicing is live and, by mid-2026, the integration
threshold reaches ~SAR 375k turnover — effectively every real florist. UAE
e-invoicing is also progressing. Other GCC countries have divergent fiscal rules
(and Qatar/Kuwait have no VAT).

## Decision

- **All fiscal / e-invoicing integration sits behind a country-specific adapter
  port** (`EInvoicingProvider`) plus config-driven `country_tax_config` /
  `tax_category` / `tax_rate` with effective dates. **No country's rules are
  hardcoded** into core order/invoice logic. "No VAT" (Qatar, Kuwait) is modelled as
  _no tax_, not a 0% rate.
- The **port and the config engine are built now** (Phase 3 tax module); concrete
  ZATCA / UAE **adapter implementations are Phase 10** (class C).
- **KSA onboarding is GATED:** a KSA tenant is not onboarded to production until the
  required ZATCA integration / compliance **for that tenant's operating model** is
  implemented and verified against the ZATCA sandbox. This gate is **not** deferred
  to a generic hardening phase — if KSA is being onboarded, the adapter is pulled
  forward.
- Gapless sequential invoice numbering per company + document series, and full tax
  invoice fields (legal name en/ar, trade licence + expiry, CR number, TRN/VAT
  number, registered address, simplified vs full thresholds) are built with the tax
  module regardless of country.
- Immutable backup for fiscal documents (GCC retention 5+ years) — §50.

## Consequences

- **Positive:** the core invoice path is country-neutral; adding a country is an
  adapter + config exercise; KSA compliance risk is an explicit go-live gate.
- **Negative:** a KSA launch requires pulling the ZATCA adapter forward out of Phase
  10 — accepted and planned for, not a hidden cost.
