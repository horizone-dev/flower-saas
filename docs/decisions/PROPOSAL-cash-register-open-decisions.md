## 1. What is built (no migration, no permission, no account, no posting policy)

| Operation | Route                                          | Key (existing vocabulary) | Behaviour                                                                                                                                                                            |
| --------- | ---------------------------------------------- | ------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| Open      | `POST /v1/cash-register/sessions`              | `cash_register:open`      | one transaction: session + the single `OPENING_FLOAT` ledger row + audit; **GL-neutral**; denominations must make up the float exactly; overlap refused per register and per cashier |
| Read      | `GET …/sessions/current`, `GET …/sessions/:id` | `cash_register:view`      | session, expected cash (Σ ledger rows excluding `CLOSING`), newest ledger rows                                                                                                       |
| Count     | `POST …/sessions/:id/count`                    | `cash_register:close`     | expected vs counted, signed variance (shortage/overage); recorded as **audit evidence only** — no state, no movement, no GL                                                          |
| Close     | `POST …/sessions/:id/close`                    | `cash_register:close`     | only on a count **equal** to the ledger; OPEN → COUNTING → CLOSED in one transaction (never stranded in COUNTING); **any difference is refused (409) and the session stays open**    |

Every route is in the B5.5 REQUIRED tier (a verified, bound, ACTIVE device); the terminal and cashier are the verified session's, never a request field; no route requires an operation proof.
The routes are **inert in production**: the `cash_register:*` keys cannot be granted (S0b), so no real role can reach them until N6 / P-2 is approved.

## 3. Defects found and fixed by the real tests

1. **Idempotent replay lost a field.** The idempotency snapshot redacts any response key containing the word _session_ (`sessionId`, `registerSessionId`). A first version of the count / close response used `sessionId`, so a **replayed** answer returned `"[redacted]"` instead of the id. The field is now `id`, and a test asserts every response survives the snapshot scrub unchanged. Any future cash-register response must avoid keys containing _session_, _token_, _secret_ and the other redacted words.
2. **A concurrency 500.** Two opens by the **same cashier on different registers** both passed the overlap pre-check (the advisory lock was per register only), and the loser hit the per-cashier unique index as a 500. Opening now takes a per-register lock, then a per-cashier lock, always in that order (no cycle); the loser gets a deterministic `409 CASHIER_HAS_OPEN_SESSION`.
3. **A build-blocking probe gap.** The cross-tenant probe suite (CLAUDE.md rule 10) rejected the five new routes as unprobed. They are now proven by an explicit probe against real tenant-A resources (denied answer identical to an unknown id, nothing written, the database hides the rows, tenant A succeeds with the same ids) and listed in the suite, as `/v1/devices` is.
