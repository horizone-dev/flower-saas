# ADR-0016 — Audit + outbox foundation; hash chain & dispatcher deferred (Phase 1 task 1.14)

- **Status:** Accepted (2026-09-04, Phase 1 task 1.14)
- **Related:** [`../architecture/ARCHITECTURE.md`](../architecture/ARCHITECTURE.md)
  §F (ledger) / §54 (audit), [`../phase-1/PHASE-1-PLAN.md`](../phase-1/PHASE-1-PLAN.md)
  §0 (amendment 2), §3.14, §4 (G12), CLAUDE.md §7 (rules 28–30)

## Decisions

### Auditable-action registry

`apps/api/src/common/audit/actions.ts` holds `AUDITABLE_ACTIONS` — a typed map
of every security- or business-significant mutation that must leave an
`audit_log` record (tenant lifecycle + limit/entitlement override, RBAC role /
grant / scope changes, user create, org create, `provider_credential`
create/rotate/revoke, session revoke, impersonation start/stop, and one
`IMPERSONATION:read` per request served inside an impersonated session).
`AuditWriter.record` accepts only these actions (compile-time via
`AuditableAction`, and a runtime guard as defence in depth), so a new mutation
cannot ship without deciding its audit story (G12).

### Atomic, in-transaction writes (amendment 2)

`AuditWriter.record(tx, …)` and `OutboxWriter.enqueue(tx, …)` write inside the
caller's transaction — a rolled-back mutation leaves **zero** committed rows,
and a multi-effect request (provisioning) produces the expected **set** of
rows. `.emit(…)` opens its own platform transaction for the few writes that are
not part of a domain transaction (session revoke, impersonation-read).

### `IMPERSONATION:read`

A global `ImpersonationReadInterceptor` records one row per request served
inside an impersonated session (OD7 — "every read is audited with the
impersonator"). The actor snapshot is captured synchronously; the write is
best-effort after a successful response (reads carry no rollback risk).

### `security_event` view

A read-only SQL `VIEW` (`security_event`) unions the security-relevant slice of
`audit_log` (action prefixes `tenant.` / `role.` / `user.` /
`provider_credential.` / `session.` / `IMPERSONATION:`) with every
`login_security_event`. Reached only through the platform (BYPASSRLS) path
(`GET /v1/platform/audit/security-events`). Alerting / correlation is Phase 2.

### Deferred to Phase 2 — explicitly

- **Hash chain.** `audit_log` is append-only and partition-ranged, but rows are
  not yet linked by a per-stream `prev_hash`. Tamper-evidence lands with the
  Z-Report hash chain in Phase 5 / the audit hardening pass, whichever is first.
  **(See the 2026-09-04 amendment — retimed to Phase 4.)**
- **Outbox dispatcher.** No `SKIP LOCKED` fan-out worker in Phase 1; `outbox`
  rows accumulate with `dispatched_at` null. The dispatcher (in-process bus +
  BullMQ + Redis Streams + reporting) is Phase 2 (CLAUDE.md §28).
- **General-ledger postings.** Phase 1 writes no `journal_entry` rows; the
  append-only GL projection begins in Phase 5.

## Amendment (2026-09-04, Phase 2-core Task 2.0 — OD-P2-1)

**Audit hash chain — retimed to Phase 4, built as one shared primitive with the
Z-Report hash chain.**

- The "Phase 5 / whichever is first" wording is superseded: the per-tenant
  `audit_log` hash chain + the scheduled tamper-evidence verification job land in
  **Phase 4**, sharing the hash-chain implementation with the immutable
  **Z-Report** chain (`z_report` / `z_report_line`, gapless `z_number`,
  hash-chained) so the primitive is written once.
- **Phase 2-core adds nullable schema support only:** `audit_log.prev_hash bytea`
  and `audit_log.entry_hash bytea`, both **nullable and never written** in
  Phase 2-core, so the Phase 4 chain is not a migration rewrite.
- Every existing guarantee is unchanged: `audit_log` stays append-only,
  RLS-scoped, partition-ranged; `AuditWriter.record` still accepts only registered
  `AUDITABLE_ACTIONS`; audit records still commit atomically with their mutation.
- Rationale: tamper-evidence is a compliance / hardening property, not a
  functional blocker for the customer MVP; the Z-Report immutability chain
  (Phase 4) is the financially load-bearing one and its hash-chain code is the
  natural home for the shared primitive.

Recorded in [`../phase-2/PHASE-2-CORE-PLAN.md`](../phase-2/PHASE-2-CORE-PLAN.md)
§0 (OD-P2-1) and [`../phase-2/PHASE-2-BACKLOG.md`](../phase-2/PHASE-2-BACKLOG.md)
item B7.

## Consequences

- Compliance is testable now: for every registry action the mutation produces
  its record(s), a forced rollback leaves none, and provisioning produces the
  documented set.
- `outbox` growth is unbounded until the Phase 2 dispatcher ships; acceptable at
  Phase 1 tenant volume, tracked as a Phase 2 entry criterion.
