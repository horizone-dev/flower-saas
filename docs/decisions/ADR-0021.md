# ADR-0021 — Cash-movement ledger storage for V1: an indexed plain table, with a defined path to partitioning

- **Status:** Accepted **for the Phase 4 S1 database foundation only** (owner approval of
  S1-D6, 2026-11-10). The implementation lives on the isolated branch
  `phase-4/cash-register-foundation` and is **not integrated**; Phase 3B remains open and
  Phase 4 integration / release stays blocked on its closure gates. Nothing in this ADR
  authorises a route, a service, register provisioning, a GL posting or any change to
  frozen Phase 3 behaviour.
- **Related:** [`../architecture/ARCHITECTURE.md`](../architecture/ARCHITECTURE.md) §F.5
  (register & drawer), §F.6 (register session), §F.7 (cash-movement ledger), §F.9 (Z-Report
  immutability); CLAUDE.md rules 8 (branch is the data boundary; a terminal is attribution
  only), 16/18/19 (GL discipline, Z immutability), 22 (append-only ledgers), 15 (money =
  integer minor units); [ADR-0010](ADR-0010.md) (RLS + pooling posture);
  [ADR-0016](ADR-0016.md) (hash-chain primitive — used later by Z-Reports, not by this table).
- **Supersedes:** nothing. **Clarifies** one formula in §F.5 (see "Expected cash" below).

## Context

§F.7 defines `cash_movement` as the append-only ledger of everything that moves cash in or
out of a drawer: eleven types (`OPENING_FLOAT`, `CASH_SALE`, `CUSTOMER_PAYMENT`,
`CASH_REFUND`, `CASH_IN`, `CASH_OUT`, `EXPENSE`, `SAFE_DROP`, `REGISTER_TRANSFER`,
`ADJUSTMENT`, `CLOSING`). It is the highest-volume table Phase 4 adds: every cash sale,
refund, drop and count writes a row, and rows are never updated or deleted.

The question this ADR settles is **how the table is stored in V1**: a plain table, or a
partitioned one from day one.

## Decision

1. **V1 stores `cash_movement` as a plain, non-partitioned, indexed table.** Append-only is
   enforced by trigger _and_ by privilege (`flower_app` / `flower_platform` hold
   `SELECT, INSERT` only; no `UPDATE`, no `DELETE`).
2. **The table is designed so that a later conversion to partitions is a mechanical,
   verifiable migration, not a redesign.** The design rules below are enforced by tests
   (`packages/db/test/phase4-s1-cash-register-foundation.integration.test.ts`), so a later
   change cannot silently break them.
3. **Conversion is triggered by measured thresholds, not by a calendar** (see
   "Conversion triggers"). Until a trigger fires, partitioning is complexity with no benefit
   (CLAUDE.md rule 3).

### Design-for-partitioning rules (each is pinned by a test)

| #   | Rule                                                                                                                                                                                      | Why it matters for a later conversion                                                                                               |
| --- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------- |
| R1  | **No table may reference `cash_movement` by a foreign key.** Later tables reference a movement through `(tenantId, sourceKind, sourceId)` or a soft `(tenantId, id)` column, never an FK. | Inbound FKs onto a partitioned table need the partition key in the referenced key; avoiding them removes the rewrite entirely.      |
| R2  | **Every index leads with `tenantId`.** The ledger carries an exact allow-list of three non-PK indexes.                                                                                    | Every query is tenant-scoped (RLS), so a tenant-keyed partition scheme prunes on every access path.                                 |
| R3  | **`occurredAt` is `NOT NULL`.**                                                                                                                                                           | Keeps time-based sub-partitioning or archival possible later.                                                                       |
| R4  | **No free-text column** and **no `UPDATE`-able column** on the ledger.                                                                                                                    | Rows are immutable, so a copy-then-swap conversion cannot race a writer that edits history.                                         |
| R5  | **The idempotency key `(tenantId, sourceKind, sourceId, type)` is a single global unique index.**                                                                                         | It is what makes re-posting a source a no-op (rule 16). It must survive conversion unweakened — see the partition-key choice below. |
| R6  | Outbound foreign keys are composite and prove the full scope + currency against the session.                                                                                              | A partitioned table may hold outbound FKs; these stay valid across conversion.                                                      |

### Why a plain table now

- Rows are narrow (≈225 bytes of heap per row, four indexes ≈ 200 bytes more — an order-of-
  magnitude estimate to be **measured**, not trusted) and strictly append-only, so the usual
  costs of a large table (bloat, vacuum churn from updates) do not apply; only index depth
  and the working set grow.
- Partitioning adds operational surface (partition creation / retention, planner pruning
  behaviour, constraint restrictions) that V1 has no need to carry.
- The hot read paths — "this session's ledger in order" and "this branch's movements in a
  window" — are both served by tenant-leading composite indexes.

### Scaling estimates and their assumptions

Assumptions (all adjustable; none is measured production data): **2.5 registers per tenant**,
**250 movements per register per day**, **360 trading days per year**, ≈425 bytes per row
including its indexes.

| Tenants | Rows / year | Rows after 3 years | Approx. size / year (heap + indexes) |
| ------- | ----------- | ------------------ | ------------------------------------ |
| 100     | 22.5 M      | 67.5 M             | ≈ 10 GB                              |
| 1,000   | 225 M       | 675 M              | ≈ 95 GB                              |
| 5,000   | 1.125 B     | 3.4 B              | ≈ 480 GB                             |

At 100 tenants a plain table is comfortable for years. At 1,000 tenants it passes the
conversion threshold inside the first year. **The thresholds below, not this table, decide.**

### Conversion triggers (any one → schedule the conversion)

- the table exceeds **50 million rows** or **30 GB** (heap + indexes);
- the **index working set exceeds ≈25 % of RAM** of the primary;
- a p95 latency regression on the two hot reads that index maintenance or a missing
  covering index cannot fix;
- a retention / archival requirement that a plain table cannot meet.

Row count and `pg_total_relation_size` for the table must be reported by the operations
dashboard before the first tenant goes live, so the triggers can actually fire. (No such
dashboard is built by S1.)

### The partitioning plan

**Partition key: `HASH ("tenantId")`, 32 partitions** (power of two, adjustable at conversion
time; modulus changes are a re-copy, so choose generously).

_Why `tenantId` and not time._ PostgreSQL requires every unique index on a partitioned table
to contain the partition key. With range partitioning on `occurredAt`, the primary key would
have to become `(id, occurredAt)` and the idempotency key would have to become
`(tenantId, sourceKind, sourceId, type, occurredAt)` — i.e. **"once per source per period"
instead of "once per source"**. For a financial ledger that is an unacceptable weakening of
idempotency (R5). Both existing unique keys already contain `tenantId`, so hashing on
`tenantId` preserves every existing guarantee: the primary key becomes `(tenantId, id)` and
the idempotency key is unchanged. Every access path is tenant-scoped, so partition pruning
works for all of them.

_Time-based retention / archival_ is **not** delivered by this key. If it is required, it is
solved at conversion time by sub-partitioning each hash partition by `occurredAt` **plus** a
small non-partitioned idempotency table, or by an archival job that moves closed periods to
cold storage after the Z-Report that froze them. This is deliberately deferred: it needs a
retention requirement that does not yet exist.

**Procedure (expand / contract, per CLAUDE.md "no history rewrite"):**

1. _Expand_ — create the partitioned table beside the old one with the same columns, the
   same `CHECK`s, the same indexes (primary key `(tenantId, id)`), the same triggers, the same
   RLS policies and the same grants.
2. _Copy_ — batch `INSERT … SELECT` in `id` order with a high-water mark, per tenant. Rows
   are immutable, so the copy cannot race a writer that edits history; new rows are caught by
   the delta pass.
3. _Verify_ — per tenant: row count, `SUM("amountMinor")` per `(sessionId, type)`, and a hash
   of the ordered `id` list must match between old and new. Any mismatch aborts.
4. _Swap_ — a short exclusive lock: copy the delta, verify again, rename old → `cash_movement_legacy`
   and new → `cash_movement`.
5. _Contract_ — keep the legacy table read-only for a defined window, then drop it in a
   separate, reviewed migration.

Each step is its own reviewed migration (or runbook step); none is authorised by this ADR.

## Expected cash — clarification of §F.5

§F.5 states `expected cash = opening_float + Σ signed cash movements (excluding CLOSING)`.
Read literally with S1's design, that **double-counts the float**, because the float is now
a ledger row. The authoritative reading is:

> **expected cash = Σ signed `cash_movement` rows of the session, excluding `CLOSING`.**
> The `OPENING_FLOAT` row is one of those rows. `register_session.openingFloatMinor` is an
> **immutable copy** of that row's amount, kept for display and for cross-checking; it is
> **never added to the sum**.

The database proves the copy and the row agree: a deferred constraint trigger makes a
session uncommittable unless it has **exactly one** `OPENING_FLOAT` row whose amount equals
`openingFloatMinor`, and a trigger makes `openingFloatMinor` immutable.

## Opening count versus funding (S1-D7)

An opening count **measures cash already in the drawer**. It moves no money between accounts
and therefore **posts nothing to the general ledger** — it is GL-neutral. The `OPENING_FLOAT`
row's source is forced by a `CHECK` to be its own session (`sourceKind = 'REGISTER_SESSION'`,
`sourceId = registerSessionId`), so a float can never be attributed to a funding transfer.
Actual funding (a bank withdrawal, an owner injection, a safe-to-register transfer, another
register) is a **real financial event** and is a **later step** with its own source kinds,
approval and GL entry; it is out of scope for S1.

## Frozen-gate amendment — HG17 (Task 3b.8 hard gate)

**Status: test-only; implemented on the isolated Phase 4 branch; APPROVED by the owner (decision G-1, 2026-11-10) — the
narrowly scoped `CashMovement` exemption and its defensive tests are retained.** (The rejected alternative was to rename the
table.)

**What the frozen gate said.** `apps/api/src/modules/orders/task-3b8-hard-gate-structural.test.ts`, HG17 ("the deferred
Task 3b.8 scope is still NOT implemented"), asserted that `schema.prisma` has no model whose name matches
`inventory|stock|movement|bom|recipe`. Its intent is that no inventory / stock-reversal scope sneaks into the financial
domain. `CashMovement` matches only on the word "movement".

**Why not rename.** §F.7 names the table `cash_movement`; the owner's S1 instruction calls it "the movement table"; the
eleven movement types are `CASH_*`. Renaming would make the code disagree with the frozen architecture to satisfy a regex.

**The amendment.** The schema half of HG17 is now the pure rule `inventoryScopeViolations`. Every previous check is kept
(any other model whose name matches is still refused) and the exemption is **exactly one model name, `CashMovement`**, valid
only while ALL of these hold:

1. it is a reviewed S0 authorisation (`AUTHORIZED_ADDITIONS`), whose model-block hash pins its whole content;
2. its columns are **exactly** the sixteen cash-drawer columns — an _allowlist_, so any added column, inventory-shaped or
   not, fails HG17 independently of S0 — and none matches an inventory-shaped pattern (item, variant, product, sku, lot,
   batch, warehouse, stock, quantity, uom, unit, bom, recipe, ingredient, material, inventory);
3. it is mapped to table `cash_movement`, is scalar-only (no `@relation`), and appears exactly once;
4. every other model **or table** name that looks like inventory / stock / movement / bom / recipe is still refused — this
   now also covers a differently named model mapped to such a table, which the original check did not.

**Proof.** 29 durable cases in the same file (any other inventory-like model, authorised or not; a differently named model
mapped to `stock_movement`; 17 inventory-shaped columns; an innocuous extra column; a missing core column; a relation to a
stock model; a duplicate block; the ledger not authorised). Run against the real files, a reviewer who _updates the S0 hash_
while adding `quantity`, an innocuous `note` column, or a stock column to `CashMovement`, or who adds and authorises a
`StockMovement` model, is still stopped by HG17 alone.

## Session integrity — database guards (decision T-1, migration `20261202120000_phase_4_register_session_integrity`)

**Status: owner-approved (2026-11-10), database-only, on the isolated Phase 4 branch.** It supersedes the S1 sentence "no
state-transition rule is encoded" in the table above; S1's own migration is unchanged (and hash-pinned).

**What the database now enforces — and nothing more:**

1. a session is **created `OPEN`** (never `COUNTING` / `CLOSED`);
2. **`CLOSED` is terminal**: no column of a closed session changes again (not even `updatedAt`); it is never deleted;
3. status **changes** only along `OPEN→COUNTING`, `COUNTING→OPEN`, `COUNTING→CLOSED` (a same-state write changes nothing and is
   tolerated — the database cannot tell it from an `updatedAt` bump; the service layer rejects it as an invalid transition);
4. **no `cash_movement` may be inserted for a `CLOSED` session, and an insert and a close are serialised.**

**Why the lock is part of the design.** The composite foreign key from `cash_movement` to `register_session` takes only
`FOR KEY SHARE` on the session row. The statement that closes a session changes only the non-key column `status`
(`FOR NO KEY UPDATE`), and those two lock modes **do not conflict** — so a guard that merely _reads_ the status is racy: a
movement can read `COUNTING`, a close can commit, and the movement then commits into a closed session. The guard reads the row
**`FOR SHARE`**, which does conflict. Measured with `pg_xact_commit_timestamp` over 60 sessions × 6 concurrent inserters
against one close: without the lock **256 of 264** committed movements landed after the close committed; with it, **0 of 222**.
The live suite repeats this on every run, with a no-lock control that must show violations so the proof can see the race.

**Deliberately not decided here (each is an open owner decision, stopped on purpose):** what may be recorded while a session is
`COUNTING` (S-2 — so `COUNTING` keeps the behaviour S1 already had, pinned by test), the meaning of `CLOSING` (S-3), how a count is
recorded or approved (S-4/S-5), who may approve a close (S-1), over/short and variance posting (S-9), forced closure (S-7), and
any evidence a close requires. In particular the database alone does **not** guarantee that a count exists before
`COUNTING→CLOSED`: that is a service rule (decision S-5 would add a database layer).

**Operational note for the future service layer.** A transition transaction must lock the session row **`FOR UPDATE` first**.
A transaction that inserts a movement (taking `FOR SHARE`) and _later_ updates the same session upgrades its lock and can
deadlock with another movement transaction doing the same; locking `FOR UPDATE` first makes "record a row, then change the
status" in one transaction safe (proved by the live suite).

**Scope and integrity.** No table, column, index, constraint, policy or privilege changes; no data is rewritten (triggers fire on
future statements only); the functions are plain plpgsql, run as the caller under the caller's own tenant + branch RLS context,
and `flower_app` already holds the `UPDATE` privilege that `SELECT … FOR SHARE` requires. Existing rows are not touched: a
session that S1 allowed to reach `CLOSED` directly, or to receive a movement after closing, keeps those rows — and is protected
from now on (proved on a populated 50→51 upgrade).

## Consequences

- S1 ships three tables, no route and no service. Nothing can create a register or open a
  session through the API until the terminal-binding design (S1-D2) is approved.
- The ledger can later be partitioned without changing any contract that S1 defines.
- The redundant "one opening row per session" partial index was **not** created: the `CHECK`
  that pins an opening row's source to its own session already makes the idempotency index
  enforce it, and an extra index is pure write cost on this table.
- The estimates above must be replaced by measured numbers once a real tenant runs; this ADR
  should then be amended (not rewritten) with the observed figures.
