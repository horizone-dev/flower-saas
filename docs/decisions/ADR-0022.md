## Context

Every cash-register route needs to know **which terminal is acting**, and that answer must never come from the client.
Today (all verified in the code):

- `session.posTerminalId` and `session.deviceId` exist as nullable columns, and the auth guard already copies both into the
  immutable `RequestContext`; but `SessionService.issue` hard-codes `deviceId: null` and no login path sets a terminal.
  Guard-pipeline step 4 ("registered device") is a documented no-op, and `registered_device_required` is deliberately not
  writable (Phase 1, amendment 1).
- The access token is HS256 and carries only `sid`, `aud` and `tid`; the server-side session is the authority and the
  revocation point. `apps/realtime` verifies the identical token through the same primitive.
- `devices:activate` / `devices:manage` exist in the TypeScript vocabulary only — no registry row, so they cannot be granted
  to any role today. `max_registered_devices` is a defined limit key but is **not enforced anywhere**.
- Phase 3 already records `ctx.posTerminalId` on orders and journal lines, behind composite foreign keys that require the
  terminal to belong to the same tenant, company **and branch** as the document.

The frozen §12 describes the intent (a server-issued, revocable credential bound to a non-extractable key; one-time
activation code; a signed server challenge at login/refresh; the session bound to `device_id` and the terminal). It does
not specify the proof, replay prevention, failure and recovery behaviour, or how the binding interacts with the existing
session, scope and limit machinery. This ADR does.

## Decision

### D1 — Browser Web POS uses a non-extractable WebCrypto key _(approved)_

The Web POS holds an ECDSA **P-256** key pair generated with `extractable: false` and persisted in IndexedDB. Its signature
format is IEEE-P1363. Assurance is recorded as `UNVERIFIED_SOFTWARE`. The residual risk is stated, not hidden: script
running inside the genuine origin can _use_ (not export) the key while the page is open.

### D2 — Native-shell POS is a packaging of the same PWA _(approved)_

"Native POS" means the existing `apps/pos-pwa` in a native shell, using the platform key store (Android Keystore /
StrongBox, iOS Secure Enclave, Windows TPM) through a bridge that exposes only `generate`, `sign(bytes)`, `delete`,
`describe`, and converts DER signatures to P1363. All protocol logic stays in PWA JavaScript. **No fifth application is
created** (CLAUDE.md rule 2); a separate native app would require an ADR amendment first.

### D3 — Terminal identity is a server-side attribute of a verified device

The terminal a session acts as is derived **only** from a registered `pos_device` whose possession of a private key was
verified by the server. It is never a request field, header, cookie, query, path segment or socket string — not even an
authenticated one. The only client-sent identifier is the `kid` inside a proof; it selects a stored public key and is never
trusted. A terminal binding adds **attribution**, never an isolation boundary (rule 8).

### D4 — One algorithm, one proof format

`ES256` (ECDSA P-256 / SHA-256) is the only algorithm. A proof is a compact JWS whose header is exactly
`{alg:"ES256", typ:"flower-device-proof+jwt", kid:<deviceId>}` and whose strict payload carries `v`, `aud`, `purpose`
(`session | refresh | op`), a server nonce and a purpose-specific context that binds the proof to what it authorises
(`session`: nothing further; `refresh`: a hash of the exact refresh token; `op`: HTTP method, path, body hash and a hash of
the session id). Proofs travel in one header, `X-Device-Proof`; no request DTO changes. Ed25519 and a bearer "credential
bundle" are **not** used.

### D5 — Enrolment by one-time activation code with proof of possession

A code is bound at creation to `(tenant, company, branch, terminal)`, is 60-bit, single-use, valid 15 minutes, stored only as
a peppered HMAC, and there is at most one pending code per terminal. `POST /v1/devices/activate` carries no tenant, branch,
terminal or user field — all are taken from the code row. The submitter signs a proof of possession with the **new** key over
`sha256(code)`; invalid keys (non-P-256, off-curve) and already-enrolled thumbprints are refused with one generic response.
Activation returns only a device id.

### D6 — The session is bound at issue, never afterwards (fail-closed)

The proof is accepted only by the call that **issues** the session (`login` for a user without MFA, `mfa/verify` for a user
with MFA) and by `refresh` of an already-bound session. An absent proof yields an unbound session; a **present but invalid
proof is refused with `401` and no session is issued** (it never silently downgrades). There is no endpoint that upgrades an
unbound session. The binding is recorded server-side with an integrity MAC; the access token is unchanged. Refreshing a bound
session **requires** a fresh proof and is verified _before_ the refresh token rotates (sender-constrained refresh).

### D7 — Cash-register routes require a verified binding, unconditionally

Every route of the cash-register family requires a session whose binding is verified **and** whose device row is currently
`ACTIVE`, in the same tenant, on the same terminal, with the terminal `ACTIVE`. The requirement is enforced twice — by an
explicit decorator and, independently, by the route's permission key belonging to the cash-register family — so omitting a
decorator still fails closed. It does not depend on `registered_device_required`, which stays non-writable. Impersonation
sessions and platform-realm tokens never satisfy it. The device status is read from PostgreSQL on every such request (no
cache in V1).

### D8 — A bound session is narrowed to the device's branch

The access snapshot of a bound session carries `branchScope = [device.branchId]` and `companyScope = [device.companyId]`
(both must lie within the user's own scope or binding is refused), re-applied on every refresh. The device narrows what a
session may do; it never widens it (rule 8, rule 13). This is also what keeps frozen Phase 3 safe: its terminal-attribution
foreign keys can never be violated by a session that can only act in the terminal's own branch.

### D9 — Replay prevention is a durable, atomic claim — a stateless nonce alone is not enough

A server-issued nonce is stateless (HMAC-bound to device and purpose, 60 s) and therefore only proves "issued by us, for this
device and purpose, at time T". **Single use is enforced exclusively by a claim recorded in PostgreSQL:** after the signature
verifies, `INSERT … ON CONFLICT (nonce) DO NOTHING` — one row means claimed, zero rows means replay. The claim is atomic under
concurrency (unique index), durable (survives Redis loss, restart and failover), committed **before** the proof is acted on,
and retained for at least ten minutes (retention ≥ validity + clock skew + request latency); the database refuses to delete or
update a live claim. Redis plays no part in replay prevention. If PostgreSQL is unavailable the proof is refused (`503`);
there is no degraded mode. A retry after a failed effect needs a fresh proof.

### D10 — Lifecycle with a recoverable state machine

Device status is `ACTIVE ⇄ BLOCKED` and `ACTIVE | BLOCKED → REVOKED` (terminal). A block carries a coded reason —
`REPLACING`, `MAINTENANCE` or `SUSPECTED_COMPROMISE`; only the first two may be unblocked, a quarantined device can only be
revoked. **Replace is block-first**: the old device is blocked at once and revoked, atomically, in the transaction that
consumes the replacement code. If replacement activation fails or never happens, the terminal is never stranded: from every
reachable state the Owner (or, exceptionally, the platform) has at least one permitted action — re-issue the code, unblock
(if the reason allows), or revoke and start over — and that is enforced by an exhaustive state-machine test. A lost or stolen
device is **revoked**, not replaced. Revocation kills the device's sessions and drops sockets; the register session survives
hardware replacement because registers and sessions are keyed to the terminal and register, not the device.

### D11 — Authority: Owner only, with step-up; exceptional platform recovery

Tenant side: `devices:activate` (create code, start replace) and `devices:manage` (list, block, unblock, revoke), both
**step-up gated**, and additionally **gated on `accountType = OWNER`** inside the service — so a custom role that is granted
the key still cannot use it. Platform side (exceptional): two new platform keys — a view key and a recover key — the latter
step-up gated, requiring a coded reason and a ticket reference, rate-limited, and always writing a tenant-visible audit row and
a security event. Neither the tenant keys nor the platform keys are granted by this ADR; enabling them is a separate,
S0b-authorised step. Every action is audited in the same transaction as the state change.

### D12 — Attestation is informational metadata only

An optional client-supplied attestation blob (≤ 8 KiB) may be stored as **unverified, informational metadata**. It is never
parsed, never logged, never returned by any API, never copied into audit, and **no authorisation, assurance, limit or risk
decision may read it**. The schema forces `attestationVerified = false` and forbids the `ATTESTED_NATIVE` assurance level in
V1. It is **not evidence of device integrity**; a later ADR must define server-challenged verification before it may be
relied on.

### D13 — The registered-device limit is enforced fail-closed, in the service and in the database

Activation is the only way to create a device. It serialises on a per-tenant advisory lock, counts live devices (`ACTIVE` and
`BLOCKED`), and reads `max_registered_devices` strictly: **a missing limit row refuses activation** (the generic limit
service would treat it as unlimited). A database trigger repeats the check as a backstop, and only the platform role may
insert into `pos_device`. A tenant over its limit keeps its existing devices but cannot activate any new one, including a
replacement, until it is back under the limit; there are no exemptions.

### D14 — Compatibility is additive; the frozen surface is untouched

No claim is added to the access token; `SessionAuthenticator`, realtime verification, the `session` columns, refresh rotation,
the `security_event` view, `audit_log` columns, RLS of existing tables, the `registered_device_required` setting and every
Phase 3 migration, route and posting are unchanged. Unbound sessions behave exactly as today. The additive changes are
listed in the consequences.

### D15 — Provider-neutral and online-only

Device activation and every proof are online-only operations (Class C, rule 31). Nothing in this ADR depends on a vendor.

### D16 — Deferred explicitly

DPoP on every request (B6); verification of Android/Apple attestation; MDM; per-branch device policies; automatic expiry of
dormant devices; making `registered_device_required` writable; a four-eyes approval for platform recovery.

## Consequences

**Additive changes B5-min will introduce** (each is a later, separately approved task): `pos_device`, `device_activation_code`
and `device_proof_claim` tables with guards, RLS and a limit trigger; a trigger on `session` that makes the terminal columns
write-once and consistent with the device row; an optional `deviceBinding` member on the shared `SessionData`; a branded
`VerifiedDeviceBinding` replacing the free `posTerminalId` input of `SessionService.issue`; two optional parameters on
`insertSessionRow`; a read-only `peekSession` on the refresh store; a registered-terminal guard placed right after the auth
guard; one more allowed CORS header (`x-device-proof`); a dedicated device-limit service. **Changes needing approval:**
enabling `devices:*` and the platform keys (S0b), and the amendment of the frozen text below.

**Costs and risks accepted:** a Web POS key can be used by same-origin script while the page is open (assurance recorded;
operation proofs narrow the exposure); reads on a bound session remain exposed to a stolen access token for its ≤ 10-minute
life (B6 is deferred); a frozen register stays frozen until the takeover rule (S-7) exists; browser-storage eviction produces a
recoverable "stale device" event; every proof costs one PostgreSQL write.

**Behavioural note for Phase 3:** a bound session records its terminal on orders and journal lines (today always null) and can
act only in the terminal's branch. Unbound sessions are unchanged.

## Alternatives considered

| Alternative                                                       | Why not                                                                                                                                       |
| ----------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------- |
| Trust a client-supplied terminal id, authenticated by the session | forgeable by anyone holding a session; forbidden by rule 5                                                                                    |
| Put the device in the access token (`cnf` claim)                  | a second source of truth beside the session; changes the token shared with realtime                                                           |
| A separate "bind" endpoint after login                            | creates a window with an authenticated, unbound session that is later mutated; needs a `null → value` update the database cannot safely allow |
| Redis `SET NX` as the single-use authority                        | Redis can evict, restart or fail over and forget a claim; replay prevention for money authentication must be durable                          |
| Stateful nonces stored at issue                                   | an unauthenticated endpoint would write storage for any device id and let an attacker exhaust a device's slots                                |
| Client `iat` / `jti` windows                                      | POS clocks drift; a server nonce gives freshness with no client-clock trust                                                                   |
| Ed25519 as a second algorithm                                     | the Secure Enclave supports only P-256; one algorithm halves the verification surface                                                         |
| Cache device status in Redis                                      | a stale "ACTIVE" after a block is the dangerous direction; cash-register routes are low-volume, a primary-key read is cheap                   |
| Auto-unblock or auto-revoke a stalled replacement                 | unblocking automatically is unsafe; revoking automatically is destructive — a human decides                                                   |
| Unlimited when the limit row is missing (current generic rule)    | a plan created without the key would mean unlimited devices                                                                                   |

## Verification this ADR will require (summary — the detailed acceptance criteria are in the B5 task reports)

Real-PostgreSQL concurrency tests for the claim (one winner among many parallel claims), for activation at the device limit,

and the proof verifier.

## B5.3 implementation notes (2026-11-11) — what was built, and where it deliberately differs from the proposal text

Built (task B5.3, Owner-limited approval): migration 53 (registry rows + an Owner-only backfill of `devices:activate` /
`devices:manage`, nothing else), the `devices` module (`POST /v1/devices/terminals/:terminalId/activation-codes`,
`GET /v1/devices`, `GET /v1/devices/:deviceId`, `POST /v1/devices/:deviceId/revoke`, public `POST /v1/devices/activate`), the
kernel's activation proof of possession (`verifyActivationProof`), the abuse limiter and the audit actions
`device.activation_code_created`, `device.activated`, `device.revoked`. Nothing is wired into login, MFA, refresh, a guard or
the access token: **a registered device is not yet required or checked anywhere** (B5.4 / B5.5).

Wording checks against the approved decisions (each is a clarification or a stricter choice — none relaxes the text):

- **D5 — expiry.** The text says "valid 15 minutes"; B5.3 issues codes for **10 minutes** (the database still caps any code at
  15). Stricter. A refused activation never consumes a code; three wrong proofs on a found code cancel it.
- **D4/D5 — the activation proof.** The activation proof of possession is a compact JWS with the **same header shape and
  algorithm** as every other proof, but `kid` is the RFC 7638 **thumbprint of the new key** (no device id exists yet) and the
  payload is `{aud, cdh, purpose:"activate", v}` where `cdh = base64url(SHA-256(normalised code))` — there is no server nonce:
  the single-use code is the freshness anchor (consumed atomically, ≤ 15 min, DB clock). `activate` is a purpose separate from
  `session | refresh | op`; the kernel's session/refresh/op verifier does not accept it and the activation verifier accepts no
  other purpose.
- **D9 — replay.** For activation, replay prevention is the atomic single-use **code consumption** (row locked `FOR UPDATE`,
  `status = 'PENDING'` guard, DB-clock expiry, the `CONSUMED` transition checked by trigger). The durable `device_proof_claim`
  ledger is used by session/refresh/op proofs and arrives with B5.4 / B5.5. Redis plays no part in either.
- **D10 — revocation only.** `ACTIVE | BLOCKED → REVOKED`, with reasons `LOST | STOLEN | HARDWARE_FAILURE | DECOMMISSIONED |
SUSPECTED_COMPROMISE` (`REPLACED` is the B5.6 replacement flow and is refused). Re-revoking is an idempotent 200 that writes
  nothing. **Known gap, by design:** D10 says revocation "kills the device's sessions and drops sockets". No session can be
  bound to a device until B5.4, so there is nothing to kill yet; B5.4/B5.5 must add that effect **in the same change that
  first binds a session** — until then a revoked device simply cannot be used for anything because nothing uses a device.
- **D11 — Owner-only.** Both keys are step-up gated (`STEP_UP_PERMISSIONS`) and held only by the Owner system role (migration
  53 + `system-roles.ts`; S0b hard-disables every other system role). The service additionally requires
  `accountType = OWNER` **and** unrestricted company/branch scope, so a custom role holding the keys is denied
  (`OWNER_REQUIRED`) and the denial is a `DEVICE_OWNER_DENIED` security event. The two plain reads (`GET`) opt out of step-up
  (`@NoStepUp()`); issuing and revoking require it. No platform key exists.
- **D12 — attestation.** An optional blob (≤ 8 KiB) is stored as `unverifiedAttestation` with `attestationVerified = false`; it is
  never parsed, logged, audited or returned. Lists expose only the boolean `attestationSubmitted` (format column non-null) so an
  Owner can see that metadata was supplied — no decision reads it.
- **D13 — device limit.** Checked early at issue and at activation by the read-only helper (`checkDeviceLimit`, strict: a missing
  row is `UNCONFIGURED`, never unlimited) and **authoritatively** by the database trigger under the per-tenant advisory lock; a
  race that passes the early read is stopped by the trigger and mapped to `422 DEVICE_LIMIT_REACHED`. The frozen `LimitService`
  is unchanged.
- **D14 — additive.** No access-token claim, `session` column, refresh path, realtime verifier, `security_event` view or
  `audit_log` column changed. Because the view is unchanged, the three `device.*` audit actions are `security: false` (they do
  not appear in the view); the security-significant outcomes — `DEVICE_ACTIVATED`, `DEVICE_REVOKED`, `DEVICE_ACTIVATION_FAIL`,
  `DEVICE_ACTIVATION_ABUSE`, `DEVICE_OWNER_DENIED` — are written to `login_security_event`, which the view does include.

### Deployment prerequisites (B5.3) — these are operational requirements, not code

1. **`DEVICE_ACTIVATION_PEPPER`** (≥ 32 random characters, secret, never in a repository or a log) **must be set in production**.
   Without it the enrolment routes fail closed (`503 DEVICE_ENROLMENT_NOT_CONFIGURED`); there is no production default.
   **Rotation:** set the new value as `DEVICE_ACTIVATION_PEPPER` and the old one as `DEVICE_ACTIVATION_PEPPER_PREVIOUS`, deploy,
   wait at least 15 minutes (the longest a code can live), then remove the previous one.
2. **`DEVICE_TRUSTED_PROXY_HOPS`** must equal the number of reverse proxies in front of the API that append to
   `X-Forwarded-For` (default `0`: the TCP peer is the only source address and the header is **ignored**). If a load balancer
   terminates connections and the value stays `0`, every client shares one rate-limit bucket (safe but unusable); if it is set
   higher than reality, a client can choose its own bucket. **The API must never be exposed to the internet directly with a
   non-zero value**, and the proxy must **overwrite or append** (never pass through) a client-supplied `X-Forwarded-For`.
3. **Redis and PostgreSQL must be reachable** for the public route: either failing makes it return 503 (fail closed).
4. **Every tenant must have a `max_registered_devices` limit row** before it can activate a device. A report of ACTIVE tenants
   without one is provided as `TENANTS_WITHOUT_DEVICE_LIMIT_SQL`; there is no automatic backfill.
5. **Pre-existing, unchanged Phase 3 behaviour (not part of B5.3, reported only):** `main.ts` runs Fastify with
   `trustProxy: true`, and `request.ip`, the request-context `ip` and the auth controller take the **first**
   `X-Forwarded-For` entry. That value is caller-controlled. B5.3's limits deliberately do not use it, but the **audit `ip`
   column and the login limiter still do**; hardening them is a separate, separately approved change.

## B5.4 / B5.5 implementation notes (2026-11-12) — what was built, and where it deliberately differs from the proposal text

**Status of D6, D7, D8, D15, D16:** implemented in the working tree (uncommitted) but still **PROPOSED** — implementation is not acceptance.
Everything below is additive; no migration, no permission, no frozen Phase 3 file and no JWT / `SessionData` / realtime change was needed.

**B5.4 — bind at issue (D6, D8).** `X-Device-Proof` on `login` / `mfa/verify` / `refresh`; verify → the user's scope → durable claim → issue;
a present-but-invalid proof is a 401 and never downgrades; the binding record is a SEPARATE Redis key `devbind:{sessionId}` (HMAC, key =
HMAC(`AUTH_JWT_SECRET`, `flower:devbind:v1`)) written before the session blob, so the shared `SessionData` type is untouched. The proposal's
session-table trigger (M54) is **not built**: it is a migration and needs its own S0 authorisation; the code-level invariants (one write path,
both-or-neither, compensation on failure) are covered by tests and pins instead.

**B5.5 — the guard (D7).** `RegisteredTerminalGuard` is a global guard registered by its own module (`DeviceSessionModule`): it runs after `AuthGuard` and after `PermissionGuard` (order: authentication → permission → registered device). **Deviation from the proposal text ("right after the auth guard"):** `pipeline.module.ts` is byte-pinned by the frozen Phase 3 structural pins (`task-3b9-checkpoint-e`), so it was not edited; AppModule loads `PipelineModule` before the module that registers the device guard, which fixes the order (pinned by a structural test and proven over HTTP). The effect is stricter for nobody and weaker for nobody: a protected route requires BOTH the permission and the device, and a caller lacking the permission never triggers a device read. For a protected route
it reads the device and its terminal from PostgreSQL **on every request** (tenant-scoped transaction ⇒ RLS; no cache) and decides the
session against three sources that must agree — the session context, the authentic binding record, the current database row — on tenant,
device, terminal, company and branch; the device and terminal must be `ACTIVE`; the (device-narrowed) scope must still contain the
device's company and branch. Nothing is read from the request. Every refusal is one `403 DEVICE_REQUIRED`; an unreadable store is one
`503 DEVICE_VERIFICATION_UNAVAILABLE`; tamper / mismatch leave a `login_security_event` (`DEVICE_BINDING_TAMPERED`, `DEVICE_SESSION_MISMATCH`).

**Route classification (a deliberate narrowing of D7's wording, owner may change it):**

| Tier            | Rule                                                                                                                                                                    | Effect                                                                                                                                                                                              |
| --------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| REQUIRED        | permission key prefix `cash_register:`, `x_report:`, `z_report:` **or** `@RequireRegisteredTerminal()`                                                                  | unbound / impersonated / unverifiable ⇒ refused                                                                                                                                                     |
| VERIFY_IF_BOUND | the money keys `orders:manage`, `orders:cancel`, `payments:collect`, `receivables:collect`, `receivables:advance:apply`, `refunds:execute` (12 existing Phase 3 routes) | an UNBOUND session proceeds exactly as before (Owner Web, Admin Web and legacy POS share these routes — their behaviour is a frozen Phase 3 contract); a BOUND session is verified on every request |
| NONE            | everything else (public, platform, reads, administration, reporting)                                                                                                    | no device read                                                                                                                                                                                      |

No cash-register route exists yet, so no production route is REQUIRED today; the family rule and the boot assertion are ready for the first one.
**Owner decision requested:** whether the six money keys should become REQUIRED for POS (that would stop Owner Web and unbound POS from using them).

**Offline-first (D15, rule 31).** The guard needs no connectivity beyond the API call itself: nothing is checked client-side and no extra
round trip is added. A request queued while offline is authenticated by the server when it arrives: a device revoked in the meantime cannot
replay it (its sessions were ended), cannot refresh (a refresh needs a fresh proof from an ACTIVE device) and cannot log back in. Offline
operation is bounded by the access-token lifetime (≤ 10 min) and the refresh requirement; **a longer offline window for bound sessions,
flush-time re-authentication of a queued batch, and Class B offline cash sales need a separate design decision** (not decided here).

**Known limitations (reported, not hidden):** (1) reads and administration by a bound session are not device-verified — a blocked device
keeps read access until its access token expires (D16: DPoP on every request is B6). (2) realtime subscriptions are not covered by the
guard (rule 30 requires the same check on subscribe — a later task). (3) BLOCKED is reachable only by SQL today; the block / unblock /
replace API is B5.6, and `revoke` is the only user-facing lifecycle action. (4) the audit `ip` and the login limiter still trust the first
`X-Forwarded-For` (pre-existing Phase 3 behaviour). (5) The B5.4 correction found by this review: a login racing a revoke could leave a live
session for the revoked device; fixed by re-checking the device after the session exists (and by the guard).

**Legacy attribution-only terminals (found by the Phase 3 regression).** Frozen Phase 3 sessions and tests mint a session with a
`posTerminalId` and **no** `deviceId` (attribution only; no production path set it before B5.4). B5.4's first rule ("any sign of a device
without a record is tampering") broke those tests. The rule is therefore: a session **claims a device only when its blob carries a
`deviceId`**; a terminal id alone is an unbound session exactly as before (REQUIRED routes refuse it as unbound, VERIFY_IF_BOUND routes
treat it as unbound). A session with a `deviceId` and no authentic matching record is still tampering and is refused.

## B5.6 implementation notes (2026-11-12) — block, unblock, replace; what is built and what is deliberately not

Built on D10/D11 exactly as written; implementation is not acceptance — D10 beyond revocation remains **PROPOSED**. No migration, no new
permission, no frozen file: the M52 foundation already holds every column and trigger the workflow needs.

**Routes (all Owner-only + step-up, the two existing keys):** `POST /v1/devices/:id/block` (`devices:manage`, body `{reason: MAINTENANCE | SUSPECTED_COMPROMISE}`),
`POST /v1/devices/:id/unblock` (`devices:manage`), `POST /v1/devices/:id/replace` (`devices:activate`; returns the replacement code once, `no-store`).
Revoke (B5.3) is unchanged in shape. Bodies are strict; none names a tenant, branch, terminal, user or device.

**Rule (pure, `device-lifecycle.ts`, exhaustive 5 × 6 matrix test):** ACTIVE ⇄ BLOCKED, ACTIVE | BLOCKED → REVOKED (terminal). A block reason is
immutable (revoke to escalate). `REPLACING` is set only by the replacement flow. UNBLOCK works from REPLACING and MAINTENANCE and **never** from
SUSPECTED_COMPROMISE (the database refuses it too). REPLACE starts from ACTIVE (block-first) or re-issues from REPLACING; a MAINTENANCE- or
COMPROMISE-blocked device is **not** replaced directly (unblock it, or revoke it and enrol anew) — the stricter reading of "a lost or stolen
device is revoked, not replaced". Every live state has at least one way out (revoke is always available; a REVOKED device frees the terminal for
an ordinary code) — proven by a test, not asserted.

**Replacement is one transaction.** Start: the device becomes BLOCKED(REPLACING) and ONE code naming it is issued (any previous pending code is
cancelled; the 24 h per-terminal code cap and the strict device limit — net-zero, `live ≤ limit`, an unconfigured limit refuses early — apply).
Completion (the public activation of that code): the replaced device must still be BLOCKED(REPLACING) on the same terminal and tenant, no other
live device may hold the terminal, the proof of possession must verify, the issuer must still be ACTIVE; then the old device is revoked
(`REPLACED`), the limit is re-checked (a refusal rolls the **whole** transaction back — the old device is never revoked by an activation that does
not complete), the new device is inserted, the code consumed, and the old device linked (`replacedByDeviceId`, write-once). The old key can never
be registered again (thumbprint unique across revoked devices). A consumed, cancelled, expired or replayed code is the one generic `400`.

**Concurrency.** Every lifecycle action and every activation takes the same locks in the same order — per-terminal advisory lock → the terminal's
pending codes (`FOR UPDATE`) → the device (`FOR UPDATE`) — and decides on the row as locked. (A first version took the device before the codes and
deadlocked two parallel replacement starts; found by the concurrency test, fixed, pinned.) Tested: 4 parallel starts, a 7-way mix of
block / unblock / revoke / replace, activation racing unblock and revoke, two activations of one code, a login racing a block.

**Sessions.** Block and replacement start end every session of the device (also on an idempotent repeat, so a retry finishes a partial failure; a
failure after the state change surfaces as a 5xx and the next call completes it). Replacement completion ends the old device's sessions best-effort
(the device is already REVOKED, so the guard and refresh refuse it; a failure must not turn a completed replacement into an error).

**Idempotency.** State-based, not key-based: repeating block / unblock / revoke on a device already in that state is a `200` that writes no second
audit row; `replace` on a REPLACING device re-issues (rotates) the code. A stored `Idempotency-Key` response would have to persist a one-time
credential, so it is deliberately not used.

**Audit / events.** `device.blocked`, `device.unblocked`, `device.replacement_started`, `device.replaced` (same transaction as the change) and
`login_security_event` kinds `DEVICE_BLOCKED`, `DEVICE_UNBLOCKED`, `DEVICE_REPLACEMENT_STARTED`, `DEVICE_REPLACED`. Payloads: ids, statuses, fixed
reason codes, the code _id_ — never a code, digest, key, proof or token (tested against every secret the test produced).

**Offline and disconnected revocation limits (documented, not solved).** The server cannot reach a device that is offline: a blocked, replaced or
revoked device keeps its local UI and any locally queued work until it reconnects. What the server guarantees is that nothing it holds can be used
on arrival: its sessions are gone, its refresh needs a fresh proof from an ACTIVE device, a pre-signed login proof is refused, and every queued
request is authenticated on arrival. Revocation therefore takes effect at the next contact, bounded by the access-token life (≤ 10 min) for any
request already in flight. **A longer offline grace for bound sessions, flush-time re-authentication of a queued batch, and local data wipe on
reconnect need a separate design decision (Class B offline sales, rule 31).**

**Unresolved decisions (not invented here; the owner must decide):**

1. **Recovery authority beyond the Owner.** D11's exceptional platform recovery (`platform:devices:view` / `platform:devices:recover`, reason +
   ticket, ≤ 5 per 24 h, tenant-visible audit) needs two new platform permission keys (S0b-authorised) and a migration (platform actor columns).
   **Not built.** Consequence: if the Owner account itself is lost, there is no in-product recovery path for devices.
2. **Replacement limits.** D13 gives the device limit (no exemption) and B5.3 the 24 h code cap (5 per terminal, shared by issue and replacement).
   Whether replacements need a stricter per-terminal / per-tenant cap or a cool-down is **not decided**; none was invented.
3. **Direct replacement of a MAINTENANCE-blocked device** (built as "not allowed"; allowing it needs the owner's word).
4. **Whether a block should require a second approver** (D11 says Owner + step-up only; none built).
5. The **POS-only mandatory-device proposal** (`PROPOSAL-pos-mandatory-device-enforcement.md`): choose an option and approve its migration.

## B5.7 implementation notes (2026-11-12) — operation proofs for financial requests

Built on the proof kernel's `purpose: "op"` (B5.2). Implementation is not acceptance — D4's `op` clause and everything below remain **PROPOSED**.
No migration, no permission, no frozen file; **no production route requires an operation proof** (the mechanism is complete, tested and inert).

**Binding.** A proof's signed context is `{htm, htu, bdy, sid}` under a server nonce: the HTTP method; the request path **as sent** (no decoding, no
normalisation; a query string or fragment is **refused**, not ignored); the SHA-256 of the **exact body bytes** received; the SHA-256 of the
authenticated session id. The nonce is a stateless MAC bound to the device and purpose, valid 60 s of **server** time. A proof therefore cannot move
to another body (one byte), path, method, session or device, and it cannot be signed ahead of time.

**Verification (`OperationProofGuard`)** runs right after the registered-device guard, only for a route that requires a proof: server-derived context
(tenant, user, session, device, terminal from the `RequestContext`; an unbound or impersonated session is refused) → the single `X-Device-Proof`
header → the canonical request → **verify** (signature, nonce, purpose, context, tenant, device, terminal — no side effect) → the device's company
and branch against the caller's (device-narrowed) scope and the route's own company / branch parameters → **claim** (durable PostgreSQL ledger,
atomic, single use; after it the proof can never be used again) → audit → handler. A failed verification burns nothing; a claimed proof is spent even
if the handler fails, so a retry signs a new one — and the existing `Idempotency-Key` store makes that retry safe (one effect per key; the guard runs
before the idempotency interceptor, so a retry with a fresh proof is answered from the store). Nothing is read from the request except the proof, the
body it signs and the route parameters (which are only _compared_ with server-derived facts).

**Exact bytes.** A `preParsing` hook captures the raw body only for a state-changing request that carries `X-Device-Proof` (bounded to 256 KiB, then
`413`), and re-emits the same bytes to the normal parser. A deployment without the hook fails closed (`503`). `main.ts` installs it.

**Opt-in only.** `@RequireOperationProof()` (new routes) or a key in `OPERATION_PROOF_PERMISSIONS` — which is **empty and pinned empty**. Moving a Phase 3
financial key into that list would make the proof header mandatory for every client of the route (Owner Web included): that is a frozen-contract
change needing the owner's approval and a review of every consumer. The 12 money routes keep their B5.5 behaviour (verify-if-bound, no proof). The boot
assertion refuses to start with an operation-proof route that is public, platform-realm or not a state-changing method.

**Fail closed and secrets.** An unreadable proof store, device lookup or audit store is `503`; an operation that cannot be audited is not performed.
The audit row (`device.operation_authorised`) carries the method and the route **pattern** only — no body, hash, path id, proof or nonce; refusals are
`login_security_event` `DEVICE_OP_PROOF_REFUSED` with a fixed reason. Tested against a sentinel card number, an amount, every proof and every token
across audit rows, security events, claim rows and the process's stdout / stderr.

**Offline.** See `PROPOSAL-offline-queued-financial-operations.md`: the mechanism supports a safe _reconnect protocol_ (fresh online nonce per request,
original idempotency key, re-authentication, live device state) but **no acceptance policy for stale operations is invented** — rule 31 (online-only
financial operations, Class B only after a separately approved model) stands.

**Decisions needed:** (1) whether and when to make operation proofs mandatory for specific financial routes (and for which clients); (2) the
offline questions in the proposal; (3) whether the `Idempotency-Key` should additionally be part of the signed context (today it is not: replaying
the _effect_ is already prevented by the single-use claim plus the idempotency store, and adding it would extend the verified B5.2 kernel);
(4) whether a failed verification should count towards a per-device abuse limit (none exists; each refusal is a fixed-reason event).
