## Context

The owner requires the platform to support **multiple retail business types** in
one tenant (flower shop, perfume shop, bakery, gift/hamper shop, chocolate shop,
balloon/party shop, plant/nursery, general retail, custom) — explicitly **not** as
separate hard-coded verticals, but as one configurable catalog where a tenant's
declared "business type" only **suggests defaults** and never locks or restricts
what that tenant can actually sell. A flower shop must be able to also sell
chocolates, perfumes, toys, balloons, cakes and plants through the same POS, same
cart, same invoice, and the same inventory engine.

**Finding: this is substantially already the frozen v0.4 design, not a new
architecture.** `ARCHITECTURE.md` §15·17·18·19 already defines:

- One `product` → `variant` model, generic across "flowers, bouquets, arrangements,
  plants, gifts, add-ons, packaging-as-product, custom" — not a per-vertical entity.
- A single `fulfilment_strategy` enum (`STOCKED` · `BOM` · `CUSTOM`) that already
  covers every product-behavior example in the new requirement (a perfume/chocolate/
  toy/balloon is `STOCKED`; a predefined bouquet or a cake made from a recipe is
  `BOM`; a custom bouquet/hamper/gift box is `CUSTOM`) — "One catalog, three defined
  behaviours" (§R table, row on fictional-bouquet-stock).
- One inventory engine: raw materials, packaging and finished goods "share the same
  ledger and balance tables" (§16·20·21); one `AvailabilityService` for every
  channel (§22); one `inventory_movement` + `branch_inventory_balance` regardless of
  product kind.
- Base-UOM + `uom_conversion` (pack conversions, per-item conversions, fractional
  quantities via `NUMERIC(18,4)`, `packages/uom` enforcing per-UOM decimal rules)
  (§15·17·18·19) — the movement ledger **always** stores base-UOM quantities, so
  Piece/Box/Carton balances cannot drift, matching the new requirement's "do not
  maintain independent balances" rule exactly.
- Multiple identifiers (barcode/QR/SKU) per variant or material, each optionally
  carrying its own `pack_uom`/`pack_qty` (`item_identifier`, §15·17·18·19) — so a
  Box-of-12 and a loose Piece can already each carry their own scannable code
  against the same underlying item.
- A Super-Admin-owned, per-tenant, on/off **feature module** mechanism already
  exists and already includes `Production / BOM` as a toggle (§48) — the axis this
  ADR extends is not a new axis, it is a finer grain of an existing one.

So the bulk of the new requirement is **confirmation, not invention**. Two things
are genuinely new or under-specified against the frozen design, and this ADR
resolves them:

1. **"Business Type" as a named, tenant-facing preset concept** does not exist yet
   as a first-class entity — today a tenant simply _has_ an entitled module set.
   There is no registry of business-type presets, no default-template seeding
   concept, and no explicit rule (until now) that a business type must never gate
   runtime behavior.
2. **Fine-grained, Super-Admin-owned, per-tenant catalog capability configuration**
   (categories/subcategories, attribute templates, variant templates, UOM
   templates, batch/expiry behavior, BOM/recipe capability, custom
   composition/bundle capability, POS-visible vs. Customer-Web-visible capability)
   goes beyond today's coarse `Plan → feature module (on/off)` list — it needs a
   **per-tenant override surface**, still Super-Admin-only to _write_, that Owner/
   Admin then operates _within_.

A third, smaller gap: **per-selling-UOM pricing.** `ARCHITECTURE.md` prices a
_variant_ (base price + optional per-branch price), not a _variant at a specific
selling UOM tier_. The new requirement's chocolate/perfume/flour examples need a
Box of chocolates and a loose Piece of the same chocolate to carry **independent
selling and purchase prices**, not just independent barcodes (which already work).
This ADR records the gap; the schema resolution is deferred to Phase 3 (below), not
designed here.

## Decision

### 1. Business Type is a preset template, never a behavior lock

A new **`business_type_template`** platform-global reference concept (seed data,
Super-Admin-curated, analogous to `Plan`) — one row per template: `Flower Shop` ·
`Perfume Shop` · `Bakery` · `Gift/Hamper Shop` · `Chocolate Shop` ·
`Balloon/Party Shop` · `Plant/Nursery` · `General Retail` · `Custom`. A template
carries **only suggested defaults**: a starter set of categories/subcategories, a
recommended attribute template set, a recommended variant template set, a
recommended UOM template set, and a recommended capability preset (which of §2's
capabilities a business of this type typically wants enabled).

A tenant's `business_type_key` (nullable, set at provisioning, changeable later by
Super Admin) is used **exactly once, at the moment defaults are applied** — either
at provisioning or when Super Admin explicitly re-applies a template. It is **never
read at runtime to gate behavior**. Concretely:

- **No code anywhere checks `if (tenant.businessType === 'FLOWER')`** or equivalent.
  Runtime behavior is driven **only** by the tenant's actual enabled capabilities
  (§2), actual configured categories/attributes/UOMs, and actual product data — the
  same rule CLAUDE.md already states for permissions/entitlements/scope ("a job
  title is never any of them"), extended here to business type.
  `business_type_key` is descriptive/UX metadata (onboarding wizard copy, template
  seeding, Super-Admin reporting/segmentation), full stop.
- A tenant may enable **any combination** of capabilities regardless of its
  declared business type — a Flower Shop enabling Bakery-preset categories and
  Chocolate-preset UOM templates is a normal, fully-supported configuration, not an
  edge case requiring special-casing.
- Re-applying or changing a template **adds** suggested defaults; it never deletes
  or disables a capability, category, or product the tenant already has configured
  or is using — a destructive "switch business type" operation does not exist.

### 2. Tenant catalog capability configuration — extends §48, Super-Admin-owned

`ARCHITECTURE.md` §48's `Plan → feature module (on/off)` mechanism is extended with
a **finer-grained, per-tenant** configuration surface — still governed by the same
rule already in force ("a permission whose module is not entitled is inert") and
still on the **entitlement axis**, never the permission/role/scope axes (CLAUDE.md
§3 rule 13 is unchanged; this adds detail under the same axis, not a fifth axis).

Super Admin configures, per tenant (write access — Owner/Admin/Manager/POS never
gain write access to this surface, matching CLAUDE.md's Super-Admin-only pattern
for entitlements/limits):

- primary `business_type_key` (§1 — template selection, re-applicable, additive)
- enabled product capabilities: which `fulfilment_strategy` values are available
  (`STOCKED` is always on; `BOM` and `CUSTOM` are independently toggleable —
  `Production / BOM` already exists as a §48 module, `CUSTOM`/composition
  capability is new)
- enabled default categories/subcategories (seeded from the template, then
  tenant-editable by Owner within permission)
- enabled attribute templates, variant templates, UOM templates (same seed-then-
  edit pattern)
- inventory behavior toggles: lot/batch tracking, expiry tracking (already
  approved for raw flowers in Z-11 — this generalizes the same fields to any
  `inventory_item.kind`, not a new mechanism)
- BOM/recipe capability (existing `Production / BOM` §48 module)
- custom composition / bundle capability (new §48-style module — see §3 naming)
- POS-visible capability set and Customer-Web-visible capability set (a tenant may
  enable a capability for POS but withhold it from the storefront during rollout,
  or vice versa — two independent visibility flags per capability, not one)

Owner/Admin/Manager then **operate within** whatever Super Admin has enabled —
creating actual products, categories, attribute values, variants — exactly as
today's model already separates "does the plan include this module" (Super Admin)
from "may this user do this, within an enabled module" (RBAC + entitlement check,
unchanged). No new authorization axis, no new guard-pipeline step: this is data
(which modules/templates exist for tenant X), evaluated through the **existing**
entitlement check.

### 3. One generic catalog/inventory core — no per-vertical engines, generalized naming going forward

Reaffirming and generalizing the already-generic §15·17·18·19 design:

- **No `FlowerProduct`, `PerfumeProduct`, `BakeryProduct`, or any other
  vertical-specific product engine, table, or code path is ever created.** One
  `product` → `category` → `product_type/behavior` → `attributes` → `variant` →
  identifier (SKU/barcode/QR) → pricing → base UOM → conversion UOMs → inventory
  behavior → BOM/recipe → composition/bundle pipeline serves every business type,
  exactly the chain given in the requirement.
- `ARCHITECTURE.md`'s existing `custom_bouquet` / `custom_bouquet_component`
  entities are **historically-named, concrete instances of the generic `CUSTOM`
  fulfilment strategy** — they are not a separate mechanism. Those sections are
  **not rewritten** (CLAUDE.md: no history rewrite; this ADR does not touch
  historical decision text). Going forward, new schema, code, and documentation
  for the `CUSTOM` strategy use the vertical-neutral names **`custom_composition`**
  / **`composition_component`** (a custom bouquet, hamper, gift box, or bundle are
  all the same entity under this name) — `ARCHITECTURE.md`'s flower-specific
  wording remains valid as the worked example of the pattern, cross-referenced from
  the generalized name at the point of Phase 3/6 schema work, not replaced.
- One cart, one invoice, one order line model already supports mixed items
  (`ARCHITECTURE.md`'s Order aggregate is channel/kind-dimensioned, not
  product-type-dimensioned) — a single order containing a bouquet, a perfume, a
  chocolate, a toy, a balloon and a cake is **already the natural shape** of the
  existing `order` → `order_line` → (`variant` | recipe explosion | composition)
  model. This ADR states explicitly, as a standing rule: **no code path may assume
  an order/cart contains only one product type or one business-type's items.**

### 4. One POS, one inventory engine — reaffirmed as standing rules

- **There is one POS application** (already CLAUDE.md rule 2 — no Staff App, no
  fifth app; this ADR extends the same "no fragmentation" principle to POS
  _modes_: there is no per-business-type POS variant, skin, or code fork — enabled
  capabilities determine what a given tenant's POS surfaces, the binary is one).
- **Inventory is branch-scoped, never POS-scoped or product-type-scoped**
  (already CLAUDE.md rule 8 / `ARCHITECTURE.md` §16·20·21 — restated here because
  the new requirement's "all POS terminals in the same branch see the same
  authoritative stock" is exactly that existing rule, now confirmed to hold
  identically for every product type, not just flowers).
- **Standard retail** (perfume, chocolate, toy, balloon — `STOCKED`), **recipe/BOM**
  (bouquet, cake — `BOM`), and **custom composition** (custom bouquet, hamper, gift
  box — `CUSTOM`) all consume the **same** `inventory_movement` /
  `branch_inventory_balance` / `stock_reservation` tables and the same
  `AvailabilityService` — this was already true for flowers-vs-bouquets in the
  frozen design; this ADR confirms it holds for every business type without
  exception, and that no product-type-keyed inventory table is ever introduced.

### 5. Multi-UOM / MCU — reaffirmed mandatory, base-unit canonical, per-UOM pricing flagged as a Phase 3 gap

- Reaffirming §15·17·18·19 as already mandatory and already correct for the given
  examples (chocolate Piece→Box→Carton, perfume Bottle→Box→Carton, flour
  Gram→Kg→Bag): base/canonical UOM per item, `uom_conversion` for nested pack
  conversions, `packages/uom` for conversion math and decimal-rule enforcement,
  `packages/money` for all price arithmetic — **no binary floating point for money
  or quantities**, matching CLAUDE.md rule 15 and the existing UOM design exactly.
- Reaffirming: the movement ledger and `branch_inventory_balance` store **base-UOM
  quantities only** — there is no independent Piece/Box/Carton balance to drift,
  by construction (§16·20·21, unchanged).
- Reaffirming: `item_identifier` already supports a distinct barcode/QR/SKU **per
  pack level** (`pack_uom`/`pack_qty` per identifier row) — a Box-of-12 and a loose
  Piece can each be scanned independently today's design, resolving to the same
  underlying item/variant.
- **New gap, recorded not resolved here:** today's `variant` pricing model prices
  the variant once (base price ± per-branch price), not once _per selling UOM
  tier_. Selling a Box of 12 chocolates and a loose Piece at independent prices (not
  merely "price × 12") needs a new modeled relation — provisionally
  **`variant_uom_price(variant_id, uom_id, sell_price, purchase_price?,
branch_id?)`** — attaching price to (variant, UOM) rather than to variant alone,
  with the base-UOM price as the always-present default. **This schema element is
  deferred to Phase 3 design** (pricing module), not specified in full here, to
  avoid freezing a table shape before Phase 3's own review; it is recorded now so
  Phase 3 planning does not treat it as a late discovery or a retrofit.

### 6. Explicit architecture rules (binding, checked at Phase 3/5/6 design + review)

- No code checks `if (businessType === 'FLOWER')` / `if (isPerfume)` /
  `if (isBakery)` or any equivalent string/enum switch on business type or vertical
  identity. Behavior is driven by `fulfilment_strategy`, enabled capabilities, and
  configured data — never by a business-type label.
- No vertical-specific product/inventory table, entity, or service
  (`FlowerProduct`, `PerfumeInventoryService`, etc.) is ever created. One catalog
  core, one inventory core, per this ADR and §15·17·18·19/§16·20·21.
- The core `product`/`variant` table does not grow dozens of nullable
  vertical-specific columns (perfume volume, bouquet stem count, bakery
  shelf-life…) — such attributes are **typed attribute-template values**
  (attribute key + typed value, scoped to category/product type), matching the
  requirement's "explicit typed attributes/templates" instruction and the existing
  §15 "never hardcoded columns" rule for variant options.
- Branch remains the operational inventory boundary; POS terminal remains
  identity/origin/register/audit only (unchanged, CLAUDE.md rule 8, restated for
  clarity against the new requirement's identical wording).
- Super Admin controls capability _availability_ (the entitlement axis); Owner/
  Admin/Manager manage actual business data _within_ what is available (the
  permission + scope axes) — this is the existing four-axis model (CLAUDE.md rule
  13), not a new one.

### 7. Binding confirmations (owner-required, 2026-09-05 amendment — locked before first commit)

The following are stated here explicitly, as **binding requirements**, not
inferences left implicit in §1–§6 above:

1. **Business Type is never used as a runtime behavior discriminator.** No
   controller, service, guard, pricing rule, POS screen, or Customer Web surface
   ever branches on `tenant.business_type_key` or any business-type label. It is
   template-seeding/UX metadata only (§1), full stop — not "usually" or "in the
   common case."
2. **Mixed-cart support is a binding requirement, not only "the natural shape" of
   the existing order model.** A single order/cart/invoice containing items of
   different `fulfilment_strategy`/category/business-type origin (a bouquet, a
   perfume, a chocolate, a toy, a balloon and a cake in one sale) **must** work
   end to end — pricing, tax, inventory reservation/consumption, and GL posting —
   with no code path that assumes single-category or single-business-type cart
   contents. Phase 3/5/6 acceptance tests must include a mixed-cart case; its
   absence would be a gap, not an acceptable simplification.
3. **Multi-UOM requires UOM-specific SELLING price.** This is a required
   capability, not an optional enhancement — §5's `variant_uom_price`-shaped
   relation (or equivalent) is required Phase 3 scope, not a "nice to have"
   deferred past Phase 3.
4. **Multi-UOM must also leave an explicit, designed-for path for UOM-specific
   PURCHASE price/cost** — distinct from selling price (a Box may be purchased at
   one per-unit cost and sold at a different per-unit margin than a loose Piece).
   Phase 3's pricing/procurement design must accommodate both `sell_price` and
   `purchase_price` per (variant, UOM), even if purchase-side UOM pricing is fully
   wired only once Phase 5 procurement lands — the schema shape must not need to
   be revisited to add it later.
5. **UOM-specific barcode and SKU/identifier, where applicable, is required** —
   already structurally supported today via `item_identifier.pack_uom`/`pack_qty`
   (§5); this confirms it explicitly as a locked requirement, not an incidental
   side effect of the existing identifier design.
6. **Authoritative stock remains one normalized/base representation.** No
   independent Piece/Box/Carton balance is ever persisted or trusted — the
   movement ledger and `branch_inventory_balance` store base-UOM quantities only
   (§5), by construction, with zero exception for any business type or product.
7. **Capability enablement is Super-Admin-controlled per tenant.** Only Super
   Admin can enable/disable a catalog capability for a tenant (§2); Owner/Admin/
   Manager/POS/Staff never gain write access to the capability-configuration
   surface itself, matching the existing Super-Admin-only pattern for
   entitlements, limits, and secrets (CLAUDE.md §6, §48).
8. **A tenant can combine capabilities from multiple preset business types.**
   Enabling a template (§1) is additive and non-exclusive — a tenant is never
   restricted to "the capabilities of its one chosen business type"; Super Admin
   may freely enable any capability from any template's recommended preset, in any
   combination, on any tenant, independent of that tenant's declared
   `business_type_key`.

## Consequences

- **Low implementation risk for most of this ADR**: §3–§4's "one generic core, one
  POS, one inventory engine" are already the frozen design: Phase 3/5/6 do not need
  to be replanned to accommodate them, only to build them as already specified,
  now with an explicit cross-tenant-vertical framing and the generalized
  `custom_composition` naming going forward.
- **Genuine new work identified for Phase 3 planning:**
  - `business_type_template` reference table + template-application (seed) logic —
    additive to the Phase 1 plan/entitlement schema family, not a rewrite of it.
  - Tenant catalog capability configuration surface (Super-Admin write API/UI +
    Owner-facing read/consume) — additive to §48's existing feature-module
    mechanism; needs its own Super-Admin-only permission key(s), defined during
    Phase 3 planning (not pre-declared in this ADR, matching how Phase 1/2 defined
    their own permission keys in their own plan documents, not in architecture
    docs).
  - `variant_uom_price` (or equivalent) — per-selling-UOM pricing, needed before
    Phase 3's pricing module schema is frozen (see Schema/migration risk below).
- **Documentation, not schema, changes today.** This ADR does not modify
  `packages/db/prisma/schema.prisma` (which does not yet contain catalog/inventory
  models — those start in Phase 3/5). No migration is created by this ADR.
- **Provisioning flow gains one step** (Phase 3, not Phase 1): applying a business
  type template's defaults during tenant provisioning or on-demand Super-Admin
  action. This does not change the Phase 1 provisioning transaction shape
  (`docs/phase-1/PHASE-1-PLAN.md`'s "provisioning in one transaction" pattern is
  reaffirmed as the pattern to extend, not replaced).
- **Naming migration is forward-only.** `custom_bouquet` remains the correct name
  for what is already built/documented under v0.4; `custom_composition` is the name
  for new schema/code from Phase 3/6 onward. No renaming pass over existing
  `ARCHITECTURE.md` prose is performed by this ADR.

## Non-goals (explicitly out of scope for this ADR)

- No Product/Category/Attribute/Variant/UOM/Inventory domain code, migration, or
  API is implemented by this ADR — it is architecture/documentation only, per
  instruction.
- No change to Phase 2-core's remaining scope (Task 2.7 localization, Task 2.8 CI
  verify) — this ADR does not touch `PHASE-2-CORE-PLAN.md`'s task list.
- No exact permission-key names, exact template seed data, or exact
  `variant_uom_price` column list are finalized here — those are Phase 3 planning
  deliverables that must cite this ADR, not restate or re-litigate it.
- No decision on whether `business_type_template` rows are platform-global-only or
  ever tenant-cloneable/custom — "Custom" as a template option already covers a
  tenant that fits no preset; a tenant-authored _template_ (as opposed to a
  tenant's own product data) is left to Phase 3 design if ever needed.

## Risks / conflicts

**Conflicts with current architecture: none found.** Every structural requirement
in the owner's message (one catalog core, one POS, one inventory engine, base-unit
canonical UOM, no vertical hard-coding) is already the direction ARCHITECTURE.md
v0.4 took; this ADR found no case where the new requirement asks for something the
frozen design forecloses or contradicts.

**Schema / migration risks introduced by this requirement:**

1. **Per-selling-UOM pricing (§5) must be designed _before_ Phase 3's catalog/
   pricing schema is frozen**, not retrofitted after. Retrofitting a
   `variant_uom_price`-shaped table onto an already-shipped single-price `variant`
   design would need a backfill (assume the existing base price applies at the base
   UOM) and a pricing-resolution code path change touching every price-read call
   site (POS cart, Customer Web, price lists, promotions) — moderate migration risk
   if deferred past Phase 3's initial schema, low risk if designed in from the
   start (which this ADR recommends).
2. **`business_type_template` + tenant capability configuration is new schema**
   additive to the Phase 1 plan/entitlement family (`plan`, `plan_version`,
   `tenant_entitlement` or equivalent). Because Phase 1's entitlement tables are
   already in production use (Phase 1 is complete, tagged `phase-1-complete`), this
   addition must be a pure additive migration (new tables + a nullable
   `tenant.business_type_key` FK) — no column removed or retyped on any
   already-shipped Phase 1 table. This is a normal additive migration, not a
   structural risk, provided it lands in Phase 3 as planned and not retrofitted
   later after tenants already have catalog data.
3. **Typed attribute-template design (§6) carries the usual EAV-pattern risk** —
   over-generalizing into a fully schemaless attribute system can make querying/
   reporting/indexing hard. Phase 3 planning should bound this explicitly (a
   closed set of attribute _value types_ — text/number/enum/boolean/date — rather
   than arbitrary JSON), the same discipline `ARCHITECTURE.md` already applies to
   "extensible concepts are strings + reference tables, not enums" elsewhere in the
   design.
4. **No RLS/tenant-isolation risk identified.** `business_type_template` is
   platform-global reference data (RLS-exempt, like `Country`/`Currency` in
   `packages/db`'s Phase 2 localization tables) written only by Super Admin; tenant
   capability configuration is a normal tenant-scoped, RLS-protected row like any
   other entitlement — no new isolation boundary is introduced.
5. **No conflict with the Phase 2-core realtime/outbox/idempotency work** (Tasks
   2.0–2.6, complete) — catalog capability changes are ordinary tenant-scoped
   writes and will go through the same outbox/audit path as any other Super-Admin
   tenant configuration change, once Phase 3 implements them. Nothing about this
   ADR requires touching `apps/realtime`, `apps/worker`, or the outbox schema.
