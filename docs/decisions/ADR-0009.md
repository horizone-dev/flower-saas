# ADR-0009 — Realtime via transactional outbox → Redis Streams → gateway; a distinct runtime role, co-deployable early

- **Status:** Accepted (2026-09-03, V3 requirements revision; deployment nuance
  added Phase 0)
- **Related:** architecture §13–14, §49; [ADR-0001](ADR-0001.md)

## Context

Same-branch POS terminals and that branch's Customer Web slice must see each other's
changes within ~1–2 seconds. Realtime must never become a second source of truth,
and a lost/duplicated/out-of-order event must be recoverable. Separately: the owner
asked that we **not force a separately deployable realtime service** if realtime can
initially live inside the API, and that a retained separate app be justified.

## Decision — pipeline

`PostgreSQL (domain write + outbox row, 1 txn)` → `outbox dispatcher (SELECT … FOR
UPDATE SKIP LOCKED)` → `Redis Stream (per tenant, retained 24h — Z-7)` → `realtime
gateway (stateless, consumer group)` → `WebSocket clients (SSE fallback)`.

- Every event: `{ event_id, seq (per-tenant monotonic), tenant_id, branch_id, type,
resource_type, resource_id, resource_version, occurred_at, actor_summary }`.
  Payload is a summary; the client refetches for detail.
- **Realtime is an accelerator, never the source of truth.** Every screen is
  buildable from REST; a confirm action always re-validates server-side.
- **Subscription authorization:** the gateway resolves the session → tenant + branch
  scope and only permits `tenant:{t}:branch:{b}:*` topics it is authorized for.
  Topics are **server-derived**; the client cannot name an arbitrary topic. Re-checked
  on every subscribe and on token refresh; session revocation drops the socket.
- **Recovery:** client tracks `last_seq` per topic → replay from the Stream on
  reconnect; beyond retention → full REST resync. Dedup by `event_id`; apply-if-newer
  by `resource_version`.
- `packages/realtime-client` encapsulates subscribe / resume / dedup / backoff so
  all four apps behave identically.

## Decision — deployment

`realtime` is a **distinct runtime role with its own bootstrap** (`apps/realtime`),
**not** necessarily a separately deployed service:

- **Phases 0–6 (default): co-deploy `realtime` with `api`** — same image, same
  process group or the same container — because socket volume is low and
  deployment-independence buys nothing yet.
- **Split it out** into its own scaled deployment when (a) sustained WebSocket
  connection counts or fan-out rate pressure the API's event loop, or (b) we need to
  deploy/restart the REST API without dropping every socket, or (c) the gateway
  needs a different instance count than the API. This is a config/infra change, not
  a code change.

**Why keep the code separate** even while co-deployed: the WebSocket gateway has a
fundamentally different concurrency and lifecycle profile from the REST request
path (long-lived connections, consumer-group offsets, backpressure). Keeping it in
its own module/bootstrap keeps those concerns out of the request pipeline and makes
the eventual split a no-op. It **never** contains authoritative business logic — it
only authorizes topics and forwards events (CLAUDE.md rule 1).

## Consequences

- **Positive:** at-least-once publish with effectively-once effects (see the
  amendment below); no event lost on crash; the split is deferred until it pays for
  itself; the request path stays clean.
- **Negative:** one more runtime role to reason about in Phase 0 (mitigated: it is a
  boot-only stub until Phase 2).

## Amendment (2026-09-04, Phase 2-core Task 2.0 — see [ADR-0017](ADR-0017.md))

Two refinements to the pipeline above, decided with the owner's Phase 2-core
constraints. The original decision stands; these make it precise.

### A. Delivery semantics — "at-least-once publish, effectively-once effect"

The "Consequences" line originally read **"exactly-effectively-once publish"**.
There is **no transport-level exactly-once** between PostgreSQL and Redis. The
guarantee is:

- the domain write and its `outbox` row commit **atomically** (one txn);
- the dispatcher publishes **at-least-once** — a crash after the Redis `XADD` but
  before the PostgreSQL `dispatched_at` ack **re-publishes** the row on restart;
- `event_id` **and** `seq` are assigned **once** and are **immutable** — a retry
  carries the identical values (ADR-0017 §1–2, constraint FC-1);
- downstream consumers and the `packages/realtime-client` reducer are **idempotent
  on `event_id`**, so the **business effect is effectively-once**.

"Crash after publish, before ack → duplicate delivery with identical
`event_id` + `seq`" is an explicitly tested case (Phase 2-core task 2.4).

### B. Live fanout is Redis **Pub/Sub via a relay**, not a gateway consumer group

The original pipeline said `Redis Stream → realtime gateway (stateless, consumer
group) → clients`. A Redis **consumer group distributes** entries among its
members, so with N gateway instances each event reaches only one instance and the
sockets on the other N−1 miss it. Corrected pipeline:

```
PostgreSQL outbox
  → outbox dispatcher (SKIP LOCKED; assigns seq once, persists before XADD)
  → durable Redis Stream per tenant  (rt:stream:{tenantId} — event history / resume)
  → realtime relay                    (one logical consumer of the stream)
  → Redis Pub/Sub live channel        (rt:live:{tenantId} — live multi-gateway fanout)
  → every realtime gateway instance
  → authorized branch/resource subscriptions → WebSocket clients (SSE fallback later)
```

- The **relay** may use a consumer group for **its own** scaling / restart-resume
  (that is not socket broadcast).
- **Live delivery is at-least-once**; the gateway and client dedup by `event_id`.
- **Resume / replay always reads the durable Stream**, never Pub/Sub. The client's
  **resume cursor is the Redis Stream entry ID**, not `seq` (ADR-0017 §3).

### C. `seq` is a logical ordering / diagnostic value, not the resume cursor

`last_seq` per topic (original "Recovery" bullet) is kept for **UI ordering and
the heartbeat high-water mark only**. The resync trigger is **retention-based**
(stored stream ID below the stream's retained floor), **not** a per-topic
arithmetic `seq` gap — that per-topic test was the F8 bug. See ADR-0017 §6–7.

### D. Separate processes (deployment nuance otherwise unchanged)

The co-deploy-through-Phase-~6 nuance stands, but `api`, `realtime`, `worker` and
`scheduler` run as **distinct OS processes / Compose services**, each with its own
failure / restart / scaling boundary — co-deployed ≠ same process. See the
[ADR-0013](ADR-0013.md) amendment (same date) for the shared-backend-module
extraction that lets all of them reuse the authoritative domain logic without a
transport dependency.
