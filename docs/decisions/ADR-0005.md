# ADR-0005 — Double-entry general ledger as an append-only projection

- **Status:** Accepted (2026-09-03, ZF-1 … ZF-9)
- **Related:** architecture §F; [`../architecture/DOMAIN-MODEL.md`](../architecture/DOMAIN-MODEL.md); [ADR-0006](ADR-0006.md)

## Context

Earlier drafts risked double-counting: an order, its payment and a manual "income"
row could each be read as revenue; customer credit could look like cash; an advance
could look like a sale; a purchase and its supplier payment could both look like an
expense.

## Decision

- **The general ledger is an append-only _projection_, not an input.** Each
  posting-worthy business event produces exactly **one balanced `journal_entry`**
  (Σ debits = Σ credits) via a deterministic posting template. Nobody keys revenue
  by hand next to an order.
- **Idempotency:** every `journal_entry` carries a unique `source_kind + source_id`
  (`ORDER_SETTLEMENT:{id}`, `PAYMENT:{id}`, `CASH_MOVEMENT:{id}`, …). Re-posting the
  same source is a no-op — this is what structurally prevents double-counting.
- **Immutable:** entries and lines are never edited. A correction is a **reversing
  entry + a new entry**, both audited.
- **One GL per company** (each company = a legal entity with its own trade licence +
  VAT registration). Branch, POS terminal and shift are **journal-line dimensions**,
  so branch/POS/shift P&L is a query, not a separate ledger (ZF-3). Tenant
  consolidation is a reporting rollup.
- **Synchronous posting inside the operational transaction** for core events (sale,
  refund, payment, cash movement, expense, purchase receipt, consumption, wastage);
  async via the outbox only for rollups and period jobs (ZF-2).
- The posting engine resolves stable **account keys** (`CASH`, `AR`, `AP`, `GRNI`,
  `VAT_OUTPUT`, `SALES_REVENUE`, `COGS`, …) to the company's mapped `account` — it
  never hard-codes an account id.
- **Contra-revenue** for discounts and returns (ZF-7). **Perpetual weighted-average**
  COGS (ZF-8). Monthly **soft-close** accounting periods with an audited,
  permissioned back-posting path (ZF-6).
- DB-enforced invariants: Σ(Dr) = Σ(Cr) per entry; `(source_kind, source_id)`
  unique; posting into a `LOCKED` period rejected at the service layer.
- **Scope at launch (ZF-9):** ship management P&L + VAT return + AR/AP + cash/Z
  first; full statutory statements + external accounting-package sync are Phase 10 /
  class C–D. This is an internal management ledger, **not** a certified accounting
  product — a tenant's statutory filing still goes through their accountant.

## Consequences

- **Positive:** a trial balance always ties; every Owner figure reconciles to the GL
  and to source transactions; VAT return = VAT Output − VAT Input from the GL.
- **Negative:** more upfront modelling and a posting engine before the first sale
  (Phase 3); every core write path must call the engine inside its transaction.
- **Financial test suite** (Phase 3+) is build-blocking: every posting balances;
  credit ≠ cash; advance received ≠ revenue; refund reverses revenue + VAT; purchase
  ≠ payment; subledger-to-control reconciliation.

## Alternatives considered

- **Single-entry money-movement ledger** — rejected (ZF-1): cannot structurally
  prevent double-counting; no real P&L / VAT return.
- **Post asynchronously via the outbox for everything** — rejected (ZF-2): the GL
  and the cash drawer could diverge on a crash between the operational commit and
  the posting.
