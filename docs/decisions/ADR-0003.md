# ADR-0003 — Branch is the operational data boundary; POS terminal is identity only

- **Status:** Accepted (2026-09-03, V3 requirements revision)
- **Related:** architecture §4–5, §13, §F.5; [ADR-0004](ADR-0004.md)

## Context

The original design treated the POS terminal as a first-class isolation axis. V3
demotes it: same-branch POS terminals and that branch's Customer Web slice must
operate on the **same authoritative branch data** and see each other's changes in
~1–2 seconds. But physical **cash** is terminal-specific.

## Decision

- **Branch (`branch_id`) is THE operational data boundary.** Orders, order lines,
  payments, deliveries, inventory movements, balances, reservations, wastage, staff,
  schedules, attendance and branch reports are branch-scoped. The guard pipeline
  resolves a resource's `branch_id` and checks it against the user's branch grants;
  list endpoints inject a branch filter.
- **A POS terminal id provides identity / origin / cash-session / audit / reporting
  context only — never isolation.** Same-branch terminals are not isolated from each
  other.
- **The one exception is cash:** `cash_register`, `register_session` and every
  `cash_movement` are scoped to a single `pos_terminal_id`. POS-01's drawer is never
  mixed with POS-02's. This is a _register isolation_ rule tested separately from
  branch isolation (Phase 4).
- **Multi-branch access is explicit** — named branch grants, optionally with a
  per-branch permission overlay. No implicit "all branches in the company".

## Consequences

- **Positive:** matches how a florist chain actually operates (staff move between
  terminals; a manager watches all terminals; the drawer stays per-till).
- **Negative:** the isolation test matrix has two axes (branch **and** register for
  financial rows) — accepted; both are in the CI probe/financial suites.
- Realtime topics are `tenant:{t}:branch:{b}:{domain}` — never per-terminal for
  operational data; register figures are pushed only to the owning terminal + branch
  manager screens.
