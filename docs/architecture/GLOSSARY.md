# Flower SaaS — Glossary

Canonical definitions. When a term here conflicts with usage elsewhere, this file
wins.

| Term                                        | Definition                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                       |
| ------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Platform**                                | The Flower SaaS provider. Operates the Super Admin realm; owns plans, entitlements, limits and all external secrets.                                                                                                                                                                                                                                                                                                                                                                                                                                                             |
| **Tenant**                                  | A florist business that subscribes to Flower SaaS. **The isolation root** — every tenant-owned row carries `tenant_id`.                                                                                                                                                                                                                                                                                                                                                                                                                                                          |
| **Company**                                 | A legal entity within a tenant (own trade license + VAT/TRN registration). **One general ledger per company.** A tenant may have several.                                                                                                                                                                                                                                                                                                                                                                                                                                        |
| **Branch**                                  | A physical shop / operating location within a company. **THE operational data boundary** — orders, inventory, staff, cash and reservations are branch-scoped.                                                                                                                                                                                                                                                                                                                                                                                                                    |
| **POS terminal** (`pos_terminal`)           | A named point-of-sale station within a branch. Provides **identity / origin / cash-session / audit / reporting** context only — **never an isolation boundary**. Same-branch terminals share authoritative branch data.                                                                                                                                                                                                                                                                                                                                                          |
| **POS device** (`pos_device`)               | A registered browser/PWA install bound to a server-issued credential + non-extractable key. Distinct from a POS terminal (a terminal may be served by different devices over time).                                                                                                                                                                                                                                                                                                                                                                                              |
| **User**                                    | A login account. Belongs to a tenant. Has credentials, MFA, roles, permission grants, data scope, `account_type`, status. Disabling a user ends sessions and touches nothing else.                                                                                                                                                                                                                                                                                                                                                                                               |
| **Staff**                                   | An employment profile. Belongs to a tenant + a home branch. `staff.user_id` is **nullable** — a florist who never logs in still exists, is scheduled, is attributed sales, and punches via a device. Terminating staff preserves all history.                                                                                                                                                                                                                                                                                                                                    |
| **`acting_user_id` / `created_by_user_id`** | The authenticated identity on a transaction. **Never overwritten.**                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                              |
| **Staff attribution**                       | `order_staff_attribution` rows (`SALESPERSON`, `FLORIST`, `CASHIER`, `APPROVER`, `DRIVER`) — many per order, separate from the authenticated user, audited on change.                                                                                                                                                                                                                                                                                                                                                                                                            |
| **Role**                                    | A named bundle of permissions. System roles are seeded per tenant; custom roles allowed. A user may hold multiple roles. **A job title is not a role.**                                                                                                                                                                                                                                                                                                                                                                                                                          |
| **Permission**                              | A key `domain:action[:qualifier]` from a central, versioned, code-defined registry. Effective set = (∪ roles ∪ grants − denies), filtered by entitlement, intersected with the target's scope. **Deny wins.**                                                                                                                                                                                                                                                                                                                                                                    |
| **Data scope**                              | A separate assignment: `company` (ids or ALL) + `branch` (ids or ALL) + optional per-branch permission overlay.                                                                                                                                                                                                                                                                                                                                                                                                                                                                  |
| **Entitlement**                             | Whether the tenant's **plan** includes a feature module. Orthogonal to permission. A permission whose module is not entitled is inert.                                                                                                                                                                                                                                                                                                                                                                                                                                           |
| **Limit**                                   | A numeric plan ceiling (companies, branches, POS terminals, devices, users, owner-users, concurrent POS sessions, concurrent Owner sessions, sessions per user, storage bytes). Enforced by `LimitService`.                                                                                                                                                                                                                                                                                                                                                                      |
| **`RequestContext`**                        | The immutable per-request object holding `tenant_id`, `branch_id`, user, session, device, permissions — populated **only** from the authenticated session.                                                                                                                                                                                                                                                                                                                                                                                                                       |
| **`ScopedRepository`**                      | The mandatory data-access wrapper that injects tenant + branch filters. Raw model access is ESLint-forbidden in scoped modules.                                                                                                                                                                                                                                                                                                                                                                                                                                                  |
| **RLS**                                     | PostgreSQL Row-Level Security. A **backstop** on every tenant table (`tenant_id = current_setting('app.tenant_id')`); the app connects as a non-superuser role that cannot bypass it.                                                                                                                                                                                                                                                                                                                                                                                            |
| **Fulfilment strategy**                     | A per-variant declaration: `STOCKED` (finished-good item, decremented on sale) · `BOM` (make-to-order, components reserved/consumed, no finished stock) · `CUSTOM` (composition chosen at POS).                                                                                                                                                                                                                                                                                                                                                                                  |
| **BOM / Recipe**                            | A predefined component list for a `BOM` variant. Explodes to component requirements on sale/production; versioned.                                                                                                                                                                                                                                                                                                                                                                                                                                                               |
| **Custom bouquet**                          | A composition chosen at the point of sale. Component names / quantities / UOM / unit cost / selling price are **snapshotted**.                                                                                                                                                                                                                                                                                                                                                                                                                                                   |
| **Movement ledger**                         | The append-only `inventory_movement` table. Quantities are never overwritten; `branch_inventory_balance` is a derived projection reconciled nightly.                                                                                                                                                                                                                                                                                                                                                                                                                             |
| **Reservation**                             | A `stock_reservation` row. Created on order confirm (never on add-to-cart), consumed on production/hand-off, released on cancel/expiry.                                                                                                                                                                                                                                                                                                                                                                                                                                          |
| **`AvailabilityService`**                   | The single code path any channel uses to answer "can I sell N of this?".                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                         |
| **Register** (`cash_register`)              | A cash drawer, **scoped to a single POS terminal**. POS-01's cash is never mixed with POS-02's.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                  |
| **Register session / POS shift**            | `register_session` — open float → cash movements → physical count → close → Z-Report. One entity for both concepts.                                                                                                                                                                                                                                                                                                                                                                                                                                                              |
| **Cash movement**                           | An append-only, typed, source-referenced entry in a register session's drawer ledger. The calculated balance is never edited directly — only via an `ADJUSTMENT` movement with reason + approval.                                                                                                                                                                                                                                                                                                                                                                                |
| **X-Report**                                | An **interim, repeatable** computed snapshot of the current open register session. **Never closes** the register.                                                                                                                                                                                                                                                                                                                                                                                                                                                                |
| **Z-Report**                                | The **finalized, immutable** closing snapshot of one register session. Frozen at close, hash-chained, gapless `z_number` per register. Never recomputed from mutable order data. Post-close fixes are reversing entries + an adjustment note.                                                                                                                                                                                                                                                                                                                                    |
| **Branch business-day close**               | Optional per-tenant aggregate of all sessions + non-cash / online activity for a business day, with its own number series. Phase 10.                                                                                                                                                                                                                                                                                                                                                                                                                                             |
| **General ledger (GL)**                     | An **append-only projection** of operational events. One balanced journal entry per business event, keyed by unique `source_kind + source_id`. Not an input; nobody keys revenue by hand.                                                                                                                                                                                                                                                                                                                                                                                        |
| **Journal entry / line**                    | `journal_entry` (balanced: Σ Dr = Σ Cr; immutable) 1─* `journal_line` (account + Dr/Cr + dimensions: company / branch / POS / shift).                                                                                                                                                                                                                                                                                                                                                                                                                                            |
| **Account key**                             | A stable string (`CASH`, `AR`, `AP`, `GRNI`, `VAT_OUTPUT`, `SALES_REVENUE`, `COGS`, `INVENTORY`, …) the posting engine resolves to a company's mapped `account`. The engine never hard-codes an account id.                                                                                                                                                                                                                                                                                                                                                                      |
| **Accounting period**                       | `accounting_period` (company, period, `OPEN` / `SOFT_CLOSED` / `LOCKED`). Posting into a non-open period is an audited, permissioned adjustment.                                                                                                                                                                                                                                                                                                                                                                                                                                 |
| **Contra-revenue**                          | Discounts and sales returns booked to their own accounts so gross / discount / net are all visible (ZF-7).                                                                                                                                                                                                                                                                                                                                                                                                                                                                       |
| **GRNI**                                    | Goods Received Not Invoiced — a liability holding account between receiving goods and posting the supplier bill.                                                                                                                                                                                                                                                                                                                                                                                                                                                                 |
| **Subledger**                               | Detailed transaction records (`ar_transaction`, `advance_transaction`, `supplier_balance`) that **reconcile to** a GL control account, never replace it.                                                                                                                                                                                                                                                                                                                                                                                                                         |
| **Money**                                   | `amount_minor BIGINT` + `currency_code` + `currency_exponent`. KWD / BHD / OMR are 3-decimal. All math via `packages/money`. No binary floating point.                                                                                                                                                                                                                                                                                                                                                                                                                           |
| **Transactional outbox**                    | A domain write + its `outbox` row commit together; a `SKIP LOCKED` dispatcher fans out to the event bus, BullMQ, Redis Streams and reporting. Nothing lost for money / stock / audit / integrations.                                                                                                                                                                                                                                                                                                                                                                             |
| **Idempotency-Key**                         | A caller-supplied key on every external-facing or retryable write; a dedup table returns the original result on retry.                                                                                                                                                                                                                                                                                                                                                                                                                                                           |
| **Realtime topic**                          | A server-derived channel string `tenant:{t}:branch:{b}:{domain}`. Clients subscribe; they cannot name arbitrary topics.                                                                                                                                                                                                                                                                                                                                                                                                                                                          |
| **`seq`**                                   | A per-tenant monotonic event sequence number; clients track `last_seq` per topic for resume-from-seq.                                                                                                                                                                                                                                                                                                                                                                                                                                                                            |
| **Attendance ingest API**                   | `POST /v1/attendance/ingest` — the single signed, idempotent entry point for all biometric / RFID / connector attendance events. Hardware never touches PostgreSQL.                                                                                                                                                                                                                                                                                                                                                                                                              |
| **Class A / B / C (offline)**               | A = safe offline (queued, idempotent). B = conditionally safe cash-only STOCKED sale behind a tenant flag. C = online-only, hard-blocked (all inventory / reservation / payment / ledger / cross-branch operations).                                                                                                                                                                                                                                                                                                                                                             |
| **Runtime role**                            | One of `api` / `worker` / `scheduler` / `realtime` — separate services deployed from **one image**. `worker` and `scheduler` import `apps/api` domain modules; they never duplicate business logic.                                                                                                                                                                                                                                                                                                                                                                              |
| **Probe suite**                             | The automated cross-tenant / cross-branch penetration test in CI. Build-blocking.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                |
| **Business Type (template)**                | (ADR-0018) A named catalog preset (Flower Shop, Perfume Shop, Bakery, …) selected per tenant. Supplies **suggested defaults only** — categories, attribute/variant/UOM templates, a recommended capability preset — applied once, at provisioning or explicit re-application. **Never** read at runtime to gate behaviour; a tenant may enable any capability regardless of its declared type.                                                                                                                                                                                   |
| **Tenant catalog capability**               | (ADR-0018) A Super-Admin-owned, per-tenant configuration of which catalog capabilities are available: enabled `fulfilment_strategy` values, default categories/attribute/variant/UOM templates, inventory behaviour toggles, BOM/recipe capability, custom composition/bundle capability, independent POS-visible / Customer-Web-visible flags. Same entitlement axis as §48's feature modules, not a new one; Owner/Admin operate within what is enabled.                                                                                                                       |
| **Custom composition / bundle**             | (ADR-0018) The vertical-neutral name, used in new Phase 3/6 schema and code, for the mechanism documented as **Custom bouquet** above — a `CUSTOM`-fulfilment-strategy composition (bouquet, hamper, gift box, bundle) chosen at the point of sale, with components snapshotted. Same mechanism, generalized name; the historical `custom_bouquet` naming in `ARCHITECTURE.md` is not rewritten.                                                                                                                                                                                 |
| **Invoice payment status**                  | (ADR-0019) A third state machine on the order/invoice, independent of order fulfilment status and payment status: `UNPAID → PARTIAL → {PAID                                                                                                                                                                                                                                                                                                                                                                                                                                      | SETTLED} · PARTIALLY_REFUNDED → REFUNDED · CANCELLED/VOID`. System-derived only, never hand-edited. UNPAID = no obligation satisfied; PARTIAL = outstanding > 0 after valid allocations/adjustments. |
| **PAID vs SETTLED**                         | (ADR-0019) **PAID**: outstanding = 0, satisfied entirely by actual monetary value (payment allocation and/or eligible advance applied), zero non-payment adjustment involved. **SETTLED**: outstanding = 0, with at least part extinguished by an approved settlement discount/write-down/adjustment. Never reported interchangeably — a `SETTLED` invoice's collected amount is never shown as if it equalled the invoice total; a settlement discount is never reported as money paid.                                                                                         |
| **Payment vs. payment allocation**          | (ADR-0019) A **Payment** (money actually received) increases an unapplied/available customer amount; it does not by itself reduce any invoice's outstanding. A **Payment Allocation** applies some or all of that available amount to one specific invoice, reducing its outstanding and consuming the pool by the same amount. The two are never summed as independent reductions — never double-counted.                                                                                                                                                                       |
| **Settlement**                              | (ADR-0019) A **grouping/workflow header**, not a balance-affecting ledger amount — it references the component entries (Payment, Payment Allocation, Settlement Discount, Advance Applied, Credit Note/Write-off) that actually moved value; it carries no value field of its own. Applies one received payment across a customer's open invoices. Default allocation: AUTO FIFO, ordered deterministically by each invoice's authoritative posting/issue sequence with an id-based tie-breaker — never database row-return order.                                               |
| **Manual payment allocation**               | (ADR-0019) A settlement-screen toggle, default OFF. OFF = automatic FIFO. ON = the authorized user allocates the payment invoice-by-invoice, server-validated (total ≤ received, no invoice over its own outstanding, no negative remainder, ineligible invoices excluded, unallocated remainder clearly shown).                                                                                                                                                                                                                                                                 |
| **Settlement discount**                     | (ADR-0019) A settlement-screen toggle, default OFF, structurally distinct from a sale-time discount (ZF-7): applied post-sale, invoice-by-invoice, against an existing receivable; requires reason/applied-by/approval/approved-by/timestamp/audit; never rewrites the original invoice total. When combined with AUTO allocation, the server deterministically recalculates the FIFO payment allocation against each invoice's post-discount remaining outstanding and surfaces it for confirmation before finalizing — the client is never authoritative for this calculation. |
| **Customer ledger / subledger entry kinds** | (ADR-0019) `ar_transaction`/`advance_transaction`'s append-only entry taxonomy: `INVOICE · PAYMENT · PAYMENT_ALLOCATION · SETTLEMENT_DISCOUNT · CREDIT_NOTE · ADVANCE · ADVANCE_APPLIED · REFUND · WRITE_OFF · ADJUSTMENT · REVERSAL` — `SETTLEMENT` is deliberately not an entry kind (it is the header concept above). Structurally separates money received, money applied, non-cash reductions, advance-side balances, refunds and corrections.                                                                                                                              |
| **Reconciliation invariant (receivables)**  | (ADR-0019) `outstanding = original obligation − Σ payment allocations − Σ advance applied − Σ settlement discounts − Σ credit notes/write-downs + Σ reversals/valid adjustments` — always provable from the subledger event stream, never a manually edited balance; mirrors how `branch_inventory_balance` is provable from `inventory_movement`.                                                                                                                                                                                                                               |
| **Cancellation charge**                     | (ADR-0019 Part B) A first-class, separately-recorded fee arising from a policy-driven cancellation — never a silent reduction folded into a smaller refund figure. Has its own entry kind (`CANCELLATION_CHARGE`) and reversal (`CANCELLATION_CHARGE_REVERSAL`), a stored policy version + calculation base, and is manager-overridable with full audit. Structurally distinct from every discount type (sale, invoice, promotion, settlement).                                                                                                                                  |
| **Account credit**                          | (ADR-0019 Part B) The non-cash resolution of a cancellation when money does not leave the business. Modeled as the same `ADVANCE` entry kind already used for over-payments (§1/§11), distinguished only by a source reference to the cancellation — never a second, parallel balance-bearing concept, so it can never double-count against `advance_balance`.                                                                                                                                                                                                                   |
| **Refund status**                           | (ADR-0019 Part B) A lifecycle independent of Order/Invoice/Payment status: `NONE → PENDING → {COMPLETED \| PARTIAL \| FAILED} · REVERSED`, tracking one specific refund/account-credit resolution's own progress.                                                                                                                                                                                                                                                                                                                                                                |
| **Inventory-disposition status**            | (ADR-0019 Part B) A per-order-line lifecycle, independent of the financial cancellation: `PENDING_DISPOSITION → {RESERVATION_RELEASED \| RETURNED_TO_STOCK \| FINISHED_GOOD_STOCK_IN \| REUSABLE_COMPONENT_RETURN \| WASTAGE \| SPOILAGE \| SCRAP \| …}`. Decided from the item's physical state, never derived from a cancellation charge amount.                                                                                                                                                                                                                               |
| **Six independent lifecycle states**        | (ADR-0019 Part B) Order status, Invoice payment status, Payment status, (derived) Receivable status, Refund status, and Inventory-disposition status — never collapsed into one field. A single cancelled order legitimately shows different values on all six simultaneously.                                                                                                                                                                                                                                                                                                   |
