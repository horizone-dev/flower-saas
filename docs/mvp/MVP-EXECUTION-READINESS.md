## 3. Execution order once approvals exist (each step ends green before the next; one verified commit per task)

1. **Approvals recorded** in the decision documents, and `inventory-release-gate.test.ts` updated _in the same reviewed change_ to "exactly the approved set live".
2. **Migrations (forward-only, one per task, each applied first to a copy of the staging DB with RLS / cross-tenant probes + schema-drift gate):** H → I → K → L → (M with D-1a) → **J with C-2** (accounts + `ACCOUNTING_REFERENCE_ACCOUNTS` + the pins that count the chart) → (O with PR-1) → (production migration only if B2).
3. **Permissions:** 3 new keys + S0b baseline facts + role-template grants + route-inventory pins (no other role change).
4. **Inventory routes (13) + costing confirmation + Owner Web receiving / opening / adjustments / counts / valuation / recipes** — no frozen sale involved; can ship and be used for stock-taking before the sale hook.
5. **Frozen amendments, in this order, each with its own disposable-copy proof, pins re-baselined in the same patch:** (a) sale hook + cancel hook (C-3; stock locks first, one ascending pass, before the customer-account lock — proved) → (b) E-5 recorder lookup + reconciliation join → (c) return route, audit action, route-inventory pin → (d) cash sale → drawer (E-5 sale).
6. **Accounting on:** inventory journals posted by the same transactions; nightly reconciliation job scheduled with its alert channel; accountant reviews real staging numbers against the worked examples.
7. **POS:** stock-based availability, return screen, bouquet availability; **Owner Web:** remaining controls.
8. **Tests at every step:** the existing disposable suites become the acceptance suite of each patch; then **browser journeys** (stock-taking → sale with deduction → partial return with wastage → cash refund → bouquet sale / cancel → (B2 run)); then the full regression and the frozen pins.
9. **Staging:** load / latency on a representative environment (closes or fails `HG3b-SALE-LATENCY`), backup-restore drill with the new tables, security review S-1 findings closed, accountant sign-off, owner acceptance.
10. **Production** only after all of the above, behind the per-company costing lock (a company with no method is byte-for-byte unchanged).

Track C (customer-linked paid returns), B2 and custom bouquets slot in after step 5(c) as their own approvals arrive; none is skipped from the MVP scope.

## 4. Hot-item lock contention and `HG3b-SALE-LATENCY` (reviewed, not closed)

**Measured (local container, not a capacity claim):** about **+20 ms per stocked line** on a ≈ 115 ms sale (a bouquet pays per component); with **distinct items** no per-sale penalty (round time +17 %); with the **same hot items in every concurrent sale ≈ 2×** (≈ 12 → ≈ 6 sales / s for one SKU), because the stock row is locked first and held to commit — the price of "re-check availability inside the lock" (rule 23) and of the lock order that removed the deadlocks. Zero deadlocks in every run.

**Assessment for a florist:** sales spread over many SKUs, so the typical shop floor is the distinct-item case; the exposure is one extremely popular SKU rung by several tills in the same second (a promotion day). **Options:** (a) accept and document (recommended for the MVP; simplest and correct); (b) add a per-SKU rate alarm to the staging test and revisit only if the representative run shows it matters; (c) shorten the critical section by allocating company counters after the stock phase **only if** the whole order hierarchy is re-proven (not recommended without evidence). **The gate stays OPEN:** it needs a representative environment, a named load profile and an owner-agreed bound — proposal for the owner to confirm or change: single-sale p95 ≤ 500 ms and no deadlock at 10 concurrent registers across ≥ 50 SKUs, hot-SKU rate reported, not bounded.
