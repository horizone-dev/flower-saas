## 1. F-6 — VAT fail-closed

**Root cause (verified in code).** The frozen sale path (`order.repository.ts`) resolves the line's tax and, when no category is assigned (`reason = NO_CATEGORY_ASSIGNED`), records `rateBps = null` and **tax 0** (§A5 of the frozen 3b.4 contract). A product activated without a VAT category therefore sells at 0% VAT, silently. Legitimate zero-rated / exempt goods carry an explicit category (`ZERO_RATED` / `EXEMPT`, resolved as a real rate row) and are a different state.

**Applied now (inside existing contracts, defence in depth, all real-API):**

| Layer        | Change                                                                                                                                                                                                                                                                                      | Proof                                                                                                                                                                              |
| ------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| POS checkout | After the server prices the order, any line with no `taxCategoryKey` blocks payment: named message, Confirm disabled even with enough cash, fail-closed if the lines cannot be read.                                                                                                        | 6 unit tests (+2 mutants caught) · browser: a seeded legacy ACTIVE product with no category is refused, a classified one still reaches payment · DB check: 0 invoiced lines for it |
| Owner Web    | A missing effective category is a blocking readiness step; the variant "Activate" button is disabled with the reason; the server action re-checks the effective category before calling the activate API (a stale page or forged form cannot activate). Zero-rated / exempt / reduced pass. | 4 new unit tests (+mutant caught) · browser: button disabled, then enabled after the category is set                                                                               |

**Limit, stated plainly:** these are client-side guards. A direct API call can still activate an unclassified variant or sell it. The authoritative fix needs the amendment below.

**Prepared amendment — NOT applied (needs owner approval; changes frozen behaviour):**
`docs/decisions/proposed-migrations/DRAFT-F6-variant-activation.patch` — `variant.repository.ts`: activation refuses `409 VARIANT_TAX_CATEGORY_REQUIRED` when neither the variant nor its product has a category (same shape as the existing `VARIANT_BASE_UOM_REQUIRED`).
`DRAFT-F6-order-line-fail-closed.patch` — `order.repository.ts` (frozen sale path): a line in a **VAT-regime** country whose resolution is `NO_CATEGORY_ASSIGNED` or `NO_RATE_FOR_CATEGORY` is refused `422 ORDER_LINE_TAX_NOT_CONFIGURED`; a country with no VAT regime, and explicit zero-rated/exempt, pass. Both patches `git apply --check` clean.
`draft-f6-variant-tax-fail-closed.integration.test.ts.txt` — 6 real-PostgreSQL tests (refusal with no state change and no audit row; product-default inheritance; variant override; `ZERO_RATED` / `EXEMPT` / `REDUCED` activate). **6/6 green with the hunk applied; the refusal test fails with the hunk reverted (mutation proven).**
**Measured blast radius of the activation hunk:** applied temporarily and run against 3 existing catalog suites → **10 existing tests in 2 files fail** (`catalog-variants`, `catalog-uom`) because they activate variants without a category. Those fixtures must be given a category in the same reviewed change; the remaining catalog / orders / sales suites were **not** run against the hunk. ## 4. Inventory — requirement review and recommendation

> **CORRECTED LATER THE SAME DAY.** This section assumed weighted average as the only method and treated a quantity-only bridge as defensible. The approved requirement is TWO company-level methods (Lot/Layer Actual Cost with FEFO + FIFO fallback, and Perpetual Weighted Average), exactly one per company, permanently locked at the Setup Wizard; no quantity-only accounting shortcut is enabled. The authoritative text is `INVENTORY-DUAL-METHOD-ARCHITECTURE.md`; the table and blockers below are kept only as history.

**Requirement evidence in the repository.** CLAUDE.md rule 20: perpetual weighted-average COGS; ARCHITECTURE §inventory: "weighted-average by default", "the company's selected costing method"; ROADMAP Phase 5 and ADR-0020 explicitly **defer** "the inventory costing method". I found **no** text making the method mandatory and **permanently locked** per company; that requirement comes from your original brief and I treated it as binding. It needs a written decision (below) because the repository does not record it.

**What exists:** a proven quantity ledger draft (`DRAFT-G`, 12 DB tests, 5/5 mutants), and — new — a pure exact weighted-average engine (`stock/weighted-average-cost.ts`, 8 tests incl. a 200-run conservation property; mutant: removing the no-negative-stock refusal is caught; the "issue-everything" special case is mathematically equivalent to the formula and is a documented guard, not a behaviour). **What does not exist:** a costing-method field, inventory / COGS / GRNI accounts (the frozen chart has 14 accounts and none), the sale hook, receiving, any stock route or permission.

**Recommendation (not approved):** do **not** assume valuation can be omitted. Build B on the proven ledger + engine. The no-stock pilot (availability flag only, as today) is the lowest-risk alternative.
