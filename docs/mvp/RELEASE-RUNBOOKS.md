# Release runbooks (controlled single-shop pilot)

Status 2026-11-14 · UNCOMMITTED · procedures to execute, **none executed on a real staging host yet**. Items marked ▢ are gates; none is claimed green.

## 1. Staging environment

**Topology:** HTTPS reverse proxy → one origin. POS `/v1/*` is proxied to the API (`API_PROXY_TARGET`), Owner Web calls the API server-side (`API_BASE_URL`). **HTTPS is mandatory:** the API's refresh cookie is `Secure` (always) and Owner Web's session cookie is `Secure` in production, so plain-HTTP staging cannot log in (localhost excepted). `NODE_ENV` accepts only `development|test|production`; staging therefore runs **production mode**.

**API environment (production mode refuses to boot otherwise):** `NODE_ENV=production`; `DATABASE_URL` (application role `flower_app`, NOBYPASSRLS) and `PLATFORM_DATABASE_URL` (platform role); `REDIS_URL`; `AUTH_JWT_SECRET` (random, not the dev default); `CORS_ORIGINS` explicit https origins (no `*`, no localhost; unused when single-origin); `SECRETS_PROVIDER` — **see R-1 below**; `DEVICE_TRUSTED_PROXY_HOPS` = the real number of proxies (0 if none); `DEVICE_ACTIVATION_PEPPER` only if registered devices are used (Phase 4, not part of the pilot).
**R-1 (verified):** `dev` is refused in production and `kms` throws "no managed KMS crypto provider is wired yet", so **the API cannot start in production mode today.** Prepared fix, unapplied: `patches/R1-secrets-disabled-provider.patch` (a fail-closed `SECRETS_PROVIDER=disabled`: it can never hold or reveal a secret; the pilot stores none). Needs owner + security approval.
**Images:** `docker build -f infra/docker/node-service.Dockerfile --build-arg APP=api -t flower/api .`; web apps with `infra/docker/web.Dockerfile` — POS single-origin: `--build-arg APP=pos-pwa --build-arg API_PROXY_TARGET=http://<api-host>:3001 --build-arg NEXT_PUBLIC_API_BASE_URL=` (Next bakes both at build; fixed this session: turbo's strict env mode used to strip them). Owner Web needs only `API_BASE_URL` at **run** time.
**Deploy order:** database up → `prisma migrate deploy` as the migration role (forward-only) → `db:seed` (permission registry, Starter plan, GCC reference data, tax categories and rates, business-type templates; idempotent) → API → web apps → smoke: `GET /healthz`, `GET /readyz`.
**Superseded by §7** (the migration runner, staging Compose and the platform-operator bootstrap now exist and were exercised locally). The Owner Web, POS, API and migrate images all build from the frozen lockfile.

## 2. Repeatable journey (Owner Web → POS → Invoice → Sales Report)

`pnpm install --frozen-lockfile` → `pnpm -w build` → `pnpm --filter @flower/pos-pwa exec playwright install --with-deps chromium` → `pnpm --filter @flower/pos-pwa test:e2e`. Asserts: owner signs in with authenticator MFA, creates a product, price, VAT category, activates it; cashier sells in the POS (server VAT, TAX INVOICE with TRN/address, print-medium content, history, reprint); the owner's Sales Report shows the same totals; 17 database checks (one invoice per sale, balanced journals, VAT payable, cash ledger = recorded tender, no duplicate after a retried payment, the unclassified product never sold). Deterministic: fixed ports 3001/3300/3400 with a pre-flight, disposable containers, no retries, teardown in `finally`. CI: `.github/workflows/mvp-browser-journey.yml` (parses as valid YAML; ▢ **not yet run on GitHub**). The rehearsal grants the cashier `catalog:view` and creates users by SQL — both disappear once F-1 / F-7 are approved.

## 3. Backup and restore drill

**Automated core (runs in CI-style containers):** `apps/api/src/verification/backup-restore-drill.integration.test.ts` — real sales, `pg_dump -Fc`, `pg_restore` into a separate database, identical fingerprint (row counts of 20 financial/security tables, trial balance per account, invoice/payment totals, trigger and constraint counts, FORCE-RLS count), `flower_app` non-bypass, append-only ledger still refuses UPDATE, a post-backup row absent (= the recovery point).
**Production drill (▢ not done):** (1) managed nightly logical backup + WAL/PITR; (2) on a **separate host**, pre-create the cluster roles (`flower_app`, `flower_platform`, `flower_migrate`, …) then `pg_restore --no-owner`; (3) run the same fingerprint SQL on source and restore, plus `prisma migrate status`; (4) boot the API against the restore and run the browser journey read-only checks (history, reprint, report); (5) record RPO (time since last backup/WAL) and RTO (wall-clock); proposed targets RPO ≤ 15 min, RTO ≤ 4 h. Redis is rebuildable (sessions + replay cache: a loss logs everyone out and drops cached idempotent replays, it never loses a sale).

## 4. Physical receipt printer verification (▢ not done — browser print is verified, a printer is not)

Record: model, paper width (80 mm assumed → 72 mm printable), connection (USB/Bluetooth/network), driver, browser and print-dialog defaults (scale 100 %, margins none, headers/footers off), kiosk-printing yes/no. Print five receipts from the POS and compare each to the screen: ① cash sale ② card sale ③ split card + cash ④ customer sale (named) ⑤ reprint (shows "(COPY)"). Pass criteria: every line present and not clipped; TAX INVOICE title, seller name, **TRN**, address; invoice number; per-line VAT, VAT summary, total; payments as recorded (no "change"); amounts match the screen to the minor unit; Arabic text renders if used; cut/feed correct; one page per receipt. Also: a sale whose seller has no TRN prints "INVOICE" with the incomplete-header marker, never "TAX INVOICE". Sign-off by the shop manager and the operator.

## 5. Rollback

Keep the previous API and web images tagged and deployable. **Migrations are forward-only** — rollback means redeploying the previous image against the migrated schema, so every pilot migration must be backward-compatible with the previous image (the F-1 SQL is a data-only insert; draft H/G are additive nullable). Steps: ① stop selling on the till (Rule 31: offline = paper log, §7 of `PILOT-RUNBOOK.md`); ② redeploy previous images; ③ smoke `/readyz` + one sale + one reprint; ④ if data is wrong, restore from the verified backup into a **new** database and swap the connection (never restore over production); ⑤ announce and record the cause. ▢ Rehearse once on staging.

## 7. Staging stack, migration runner, bootstrap — what exists and what was verified (2026-11-14, local Docker only)

**Nothing here was run on a remote host, and no real credential exists anywhere in the repository.** Files: `infra/staging/{docker-compose.staging.yml, Caddyfile, Caddyfile.local, .env.example, preflight.mjs}`, `infra/migrate/{Dockerfile, migrate.mjs, provision-db-roles.mjs, seed.mjs, generate-approved-manifest.mjs, approved-migrations.json, verify.mjs}`, `apps/api/src/tooling/*` (operator bootstrap).

**Migration runner** (separate image, frozen lockfile): default mode is read-only `check`; `MIGRATION_MODE=deploy` applies. It refuses — before touching the database — a missing `MIGRATION_DATABASE_URL`, any migration folder not in `approved-migrations.json` (an uncommitted Phase 4 / MVP draft, a "DRAFT" name, a changed file hash), a verified-folder-that-is-not-the-folder-Prisma-applies, and database drift (an applied-but-unapproved or unfinished migration); a second concurrent runner exits 3 on an advisory lock; after applying it re-verifies every approved migration is finished exactly once. The manifest is generated from the migrations **committed at git HEAD** (49): committing a regenerated manifest is the explicit approval act. `verify.mjs` runs 20 checks against a throwaway PostgreSQL container (below). A real hole was found and fixed while writing it: Prisma applies the db package's folder, not the folder that was verified.

**Staging Compose** (project `flower-staging`; only Caddy publishes ports): `postgres`, `redis` (password), `minio` (built from the pinned source the tests use), then `backup` (a verified `pg_dump -Fc`) → `migrate` → `roles` (gives `flower_app` / `flower_platform` their login passwords from env) → `seed` → `api` → `pos`, `owner-web` → `caddy`. Every secret is `${VAR:?}`; `preflight.mjs` refuses placeholders, short/repeated/reused secrets, localhost hosts, a wildcard `ADMIN_CIDR`, `dev` vault, `:latest` images and a git-tracked env file. Caddy: automatic HTTPS, HSTS and security headers, the **platform realm is blocked on the shop hosts and served only from `OPS_HOST` to `ADMIN_CIDR`**.

**First-operator bootstrap** (existing primitives only; no route, no hardcoded or shared credential): `docker compose --profile bootstrap run --rm -it bootstrap-operator --email … --name "…"` — an interactive CLI that **refuses without a terminal**, reads the password hidden (never an argument/env/file), generates the TOTP secret and stores the factor only **after the operator enters a live code** (so MFA cannot be skipped), refuses a repeat or a second operator unless explicitly flagged, and stores only an argon2id hash. Then: operator signs in (password + code) on `OPS_HOST` → `POST /v1/platform/tenants` returns **one** one-time Owner invite (48 h, hash stored) → the Owner redeems it (`/v1/auth/set-password`) → enrols an authenticator (`/v1/auth/mfa/enrol` + `confirm`; **Owner Web has no screen for this yet — it is an API call today**) → every later login needs the code. Pilot cashier onboarding stays **blocked**: F-7 is not active (404), and creating users by SQL is not acceptable.

**Verified (locally, Docker Desktop):** runner 20/20 on a disposable database; bootstrap procedure test 6/6 on real PostgreSQL/Redis; the whole stack booted in production mode (`backup → migrate → roles → seed → api → pos/owner-web → caddy`, all healthy; the API image used for this was built from a **disposable copy with the unapproved R-1 patch**, because production mode cannot boot without it); over HTTPS: HTTP→HTTPS redirect, HSTS/nosniff/frame/referrer headers, the shop host proxies `/v1` and returns 404 for `/v1/platform/*`, the operator host allows only the platform realm and only from the allowed network (403 otherwise), `/readyz` all `ok`, refresh cookie `HttpOnly; Secure; SameSite=Lax; Path=/v1/auth`, nothing but Caddy published (5432/6379/9000/3001 closed), no secret in any service log, platform login with TOTP → tenant provisioned → Owner invite redeemed → Owner login, backup restored into a **new** database with an identical fingerprint. **Not verified:** a remote host or a real certificate authority (ACME), Owner Web's own session cookie in a browser over HTTPS (production-mode + code only), the physical printer, GitHub CI, a real rollback to a previous good image (only one good image exists).

**Remaining production boot blocker:** R-1 (the API cannot start in production mode without the unapproved patch or a KMS provider).

## 8. Release record, rollback and acceptance sheets (2026-11-15)

**Image immutability.** A tag can be re-pointed; an image ID cannot. Before any deployment run `node infra/staging/release-images.mjs infra/staging/.env.staging --out release-images.json` and keep the file with the release: it records the immutable ID of the API, POS, Owner Web and migration images. Tag every build with the git commit (never `:latest`; `preflight.mjs` refuses it). `node infra/staging/hash-artifacts.mjs` prints the SHA-256 of every reviewed artefact, so an approval names exactly what was reviewed.

**Rollback (commands).** Keep the previous four images and their `release-images.json`.

1. Stop sales on the till (Rule 31: the till is online-only; use the paper log of §7 of `PILOT-RUNBOOK.md`).
2. Application rollback: put the previous tags in `.env.staging` (`API_IMAGE`, `POS_IMAGE`, `OWNER_IMAGE`) and run `MIGRATION_MODE=check docker compose -f infra/staging/docker-compose.staging.yml --env-file infra/staging/.env.staging up -d api pos owner-web caddy` (the runner in `check` mode is read-only; the previous image must be compatible with the migrated schema — migrations are forward-only and every pilot migration must be additive).
3. Data rollback (only if data is wrong): `docker compose … run --rm backup` first (never skip: it protects the current state), restore the chosen dump into a **new** database (`pg_restore --no-owner`, as `smoke-local.sh` does), compare row counts, then point `POSTGRES_DB` at it and redeploy. **Never restore over the live database.**
4. Smoke: `/readyz` all `ok`, one sale, one reprint, the Owner sales report. Record cause and timings.
   Rehearsed locally: the backup → restore-into-a-new-database step (identical fingerprint). **Not rehearsed:** redeploying a previous good application image (only one good image set exists).

**Local staging smoke (repeatable).** `bash infra/staging/smoke-local.sh <api-image> <migrate-image> <pos-image> <owner-image>` builds a disposable stack with random secrets (git-ignored), checks start order, HTTPS/HSTS/TLS versions, host isolation, production-mode health, operator bootstrap with TOTP, two tenants, the Owner Web enrolment spec over HTTPS, secrets-not-in-logs, **tenant isolation with real data** and backup→restore, then removes the stack. The API/migrate images must contain the approved R-1 behaviour.

**Receipt-printer acceptance sheet (to be filled at the shop; NOT done).** Record: printer model · paper width (80 mm roll, 72 mm printable) · connection · driver · browser · print dialog (scale 100 %, no margins, no headers/footers) · kiosk printing yes/no. Print and compare with the screen: ① cash ② card ③ split card + cash ④ named customer ⑤ reprint ("(COPY)"). Pass only if, for every receipt: title **TAX INVOICE**, seller name, **TRN**, address, invoice number, per-line VAT, VAT summary, total, payments as recorded and **no "change"**; amounts equal the screen to the minor unit; nothing clipped; one page; cut/feed correct; Arabic renders if used. A seller without a TRN must print "INVOICE" with the incomplete-header marker, never "TAX INVOICE". Sign-off: shop manager + operator + date.
