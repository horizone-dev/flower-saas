# Cash refund ↔ register session — the smallest correct connection (E-5)

2026-11-15 · **DESIGN + DISPOSABLE PROOF · NOT APPROVED · nothing is wired.** The Phase 4 recorder, mapper, reconciliation and every cash-register file are **unchanged**; the proof composes them in test code only (`stock/returns/sale-return-cash.integration.test.ts`, 12 tests, both costing methods, real PostgreSQL). Companions: `PAID-SALE-RETURN-DESIGN.md` (M9 is this document), `MVP-EXECUTION-READINESS.md`.

## 1. What already exists, and the one gap

- The E-5 recorder already takes a **refund** source and writes one signed `CASH_REFUND` drawer movement (`mapCashSource`: CASH only, positive at the source, negative in the drawer), once per source event (`UNIQUE (tenantId, sourceKind, sourceId, type)` + advisory lock + `ON CONFLICT DO NOTHING`), into the **open** register session of the **verified** terminal (device ACTIVE, session read `FOR SHARE`, company / branch / currency must match), refusing a late event (`SOURCE_PREDATES_SESSION`), a COUNTING session (S-2, fail closed) and a missing terminal / actor. The GL bridge already classes `CASH_REFUND` as **OWN_JOURNAL** (the refund's own journal, exactly once).
- **The gap:** it looks the refund up in the frozen `refund` table, and that table cannot hold a walk-in refund (PAID-SALE-RETURN-DESIGN §1). A walk-in return's refund legs live in `sale_return_refund` (DRAFT-O). `cash_movement.sourceKind` is a free-form key with a shape check only (no vocabulary, no foreign key) — so **no schema change is needed**.

## 2. The smallest connection (three small steps, none of them a new accounting engine)

1. **Source lookup** — the recorder's `loadSource(REFUND, id)` and the source-reconciliation join each read `refund` **or** `sale_return_refund` (a `UNION` of two reads; the leg's time is its return header's `createdAt`). Mapper, sign rule, classifier, vocabulary, types and the unique key are untouched; a return leg is "a local refund source row" with `sourceKind = 'REFUND'`. (A new `sourceKind` was rejected: it would widen the mapper, classifier, window reconciliation and vocabulary for no benefit.)
2. **Composition** — the (future, approval-blocked) return route calls the recorder for every refund leg **inside the same scoped transaction**, after the return, stock and journals, with the **strict policy**: any outcome other than RECORDED / ALREADY_RECORDED / NOT_ELIGIBLE aborts everything (owner decision E-5.2; recommended).
3. **Reconciliation** — today `classifyMovementBacking` reports a leg-backed movement as `SOURCE_MISSING`; with step 1's extra read it is `BACKED` (both shown in the proof). Without step 1 a cash return would raise a false discrepancy at drawer close.

## 4. Decisions this leaves to the owner (none assumed)

- **E-5.2 refusal policy** — strict abort (recommended: money and drawer never disagree) versus record-later. **Recommendation: strict.**
- **PR-7 drawer floor** — the ledger lets expected cash go **below zero** (the database protects only the opening float); the proof shows a 252.00 refund against a 200.00 float recording. Options: allow and let the count variance show (simplest), or refuse a cash refund above the drawer's expected cash and require a manager top-up / cash-in (needs the unapproved cash-in policy). **Recommendation: refuse above the drawer unless a manager with step-up approves.**
- **PR-8 who may refund cash** — the recorder requires a verified terminal and an actor but does not require actor = the session's cashier. **Recommendation:** the route needs `credit_notes:issue` + `refunds:execute` (both step-up) **and** the actor must be the session's cashier or hold a manager approval; a cash refund with no open register session is refused (the till must be open).
- **A refund of goods sold in an earlier, closed session** is paid from today's open session (the leg's time is now). Accountant: nothing special (the cash GL is company-wide); the drawer variance shows it.
