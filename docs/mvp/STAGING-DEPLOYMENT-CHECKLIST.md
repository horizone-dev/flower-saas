## 1. Hosting requirements

- One Linux host with Docker Engine and the Compose plugin; the stack is Compose project `flower-staging` (postgres, redis, minio, backup, migrate, roles, seed, api, pos, owner-web, caddy; `bootstrap-operator` behind the `bootstrap` profile). **Sizing has not been measured**; pick it from a first deployment and record it, do not assume.
- Public DNS A records for three names, ports 80 and 443 reachable from the internet (ACME): `POS_HOST` (till), `OWNER_HOST` (Owner Web), `OPS_HOST` (operator). Only Caddy publishes ports.
- `OPS_HOST` serves **only** `/v1/platform/*` and **only** to `ADMIN_CIDR` (a real office/VPN egress range, never `0.0.0.0/0`). The staff-invite route (F-7b) is on this host.
- The till host blocks the platform realm; the API runs as the non-superuser `flower_app` (RLS enforced) and a separate audited `flower_platform` role.
- Disk for the PostgreSQL volume, the `flower-staging-backups` volume **and an off-host copy of the backups (OPEN: destination, encryption, retention, RPO/RTO are owner decisions)**.

## 2. PostgreSQL version pin — PROPOSED, awaiting owner approval (gate E4)

**Mechanism (built, verified):** `infra/staging/postgres-image.pin` holds the ONE reference; `postgres` and `backup` both use `${POSTGRES_IMAGE}`. `preflight.mjs` refuses `postgres:17`, `:latest`, a bare major, another major, a variant tag, **a tag without a digest**, and any value that differs from the pin file (a plain `17.<minor>` tag is accepted only with `--local`); it also refuses a pin file that is weak or missing. `check-release.mjs` re-checks the **resolved** compose (both services, same image, equal to the pin). The CI workflow has three negative steps that check each refusal **for the right reason**; 10 mutants of these guards were each caught (see the PR description).

**Proposed value:** `postgres:17.11@sha256:ff87138949ad9a46f32ff23bd6852b52ce024a13dffe9b4087be98292cdd3b4f` (registry index digest, linux/amd64 + arm64; PostgreSQL 17.11 on Debian 13, `pg_dump`/`pg_restore` 17.11 in the same image). **Alternative:** `postgres:17.12@sha256:97fb53376be3e4fb1a8a61421daa69dcc3bf2fa39bda3259f5245f9a455af1a9`, a one-line change of the pin file.

**Safety assessment of 17.11 (facts from postgresql.org on 2026-11-27, and from this repository):**

| Question                              | Finding                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                    |
| ------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Is 17.11 the current minor?           | **No.** 17.12 was released 2026-11-12; 17.11 on 2026-08-13. PostgreSQL's policy is to run the current minor. Major 17 is supported until 2029-11-08.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                       |
| What does 17.12 fix that 17.11 lacks? | About 48 CVE-identified issues: use-after-free and buffer overruns (some reachable with crafted input to `ts_rank_cd`, `tsvector_delete`, COPY, portals), **two row-level-security fixes** (`ON CONFLICT` evaluated user quals before RLS policies, CVE-2026-120154; `DROP OWNED BY` removing restrictive RLS policies from tables the role does not own, CVE-2026-116311) and one view fix (`ON CONFLICT DO UPDATE` through a view could reach rows the view hides, CVE-2026-16237), privilege-check gaps (casts in `to_json()` and foreign-key checks) and PL/Perl, PL/Tcl, dblink and pg_restore hardening. Individual CVSS scores were not assessed here.                                                              |
| Practical exposure in staging         | Almost all of these need an authenticated session that runs crafted SQL. The API connects as the non-superuser `flower_app`, queries are parameterised, and only Caddy publishes a port (`check-release` and `smoke-local.sh` assert 5432 is not published). The realistic path is therefore **application SQL injection first**, then these bugs as escalation; this repository's tenant isolation depends on RLS, and two of the fixes concern RLS policies directly (an attacker needs to control SQL text, such as a crafted qual in an `ON CONFLICT` statement or a `DROP OWNED BY`, which the application does not allow unless it has an SQL-injection flaw; this was reasoned from the release notes, not tested). |
| Data-integrity fixes that apply to us | The two **GIN trigram indexes** on `product."nameEn"` and `product."nameAr"` (GIN VACUUM and posting-tree bugs can make a search miss rows): `REINDEX` them if staging runs 17.11 for long. **Do not apply:** no `bpchar`/`CHAR(n)` column, no GiST trigram index, no `REINDEX CONCURRENTLY`, and **no incremental backups** (the backup job is a plain `pg_dump -Fc`, so the 17.12 warning about incremental backup files does not touch it).                                                                                                                                                                                                                                                                             |
| Why 17.11 at all                      | It is the only version on which every frozen report performance gate passes (Finding A is a 17.12 plan regression, PR #50), and it is what the CI test stack pins (#51). Staging on 17.11 keeps staging and tests on the same engine. Finding A was measured on large synthetic ledgers; it has **not** been measured at alpha data volumes.                                                                                                                                                                                                                                                                                                                                                                               |
| What the digest costs                 | A digest freezes the OS layer: `postgres:17.11` was rebuilt on 2026-11-05, so a floating tag changes silently and a digest never receives Debian fixes. Refresh the digest deliberately (`docker buildx imagetools inspect postgres:17.11`), review, then change the pin.                                                                                                                                                                                                                                                                                                                                                                                                                                                  |

**Conditions I recommend if the owner approves 17.11 for staging** (each is the owner's to accept or change): staging only, never production; the database stays unreachable from outside the compose network; the two GIN indexes are reindexed before any search-quality check; the decision is **time-boxed**: re-decide when the next PostgreSQL minor is released or before any user outside the internal alpha, whichever comes first. The deferral of the Finding A amendment makes 17.11 a growing security debt; the exits are a verified bounded variant of the amendment (PR #56 lists the options) or accepting 17.12 plan behaviour.

### 2a. Deferred issue — PostgreSQL 17.12 report-plan regression (Finding A / B): **OPEN, DEFERRED by the owner on 2026-11-27 (option 1)**

This pin does **not** resolve it; it only keeps staging on the engine where the frozen report gates pass.

- **What:** on PostgreSQL 17.12 two frozen report probes change from an index scan to a per-row sequential scan: sales `creditNotesWithoutRevenueJournal` and tender-totals `allocatedPaymentsWithoutReceiptJournal` (`LEFT JOIN LATERAL … LIMIT 1 … IS NULL`). Finding B (dense-window JIT) is cleared by the same change. On 17.12 the frozen performance tests fail (8–10 tests in 3 report files); on 17.11 they pass.
- **Evidence kept:** PR #50 (plan comparison, 17.11 vs 17.12), PR #51 (CI test stack pinned to 17.11, `verify` green), PR #56 (the `NOT EXISTS` rewrite, **DRAFT / BLOCKED, review only, not merged**; its bounded-read tests are **not weakened**: the F-1 tender repro reads about 60,000 rows against bounds of 515–620, and F-2 sales is likewise an open measured finding of that candidate).
- **Unchanged by design:** the frozen financial SQL, and the 25,000-document density protection (`SALES_REPORT_MAX_DOCUMENTS`).
- **Digest note:** the `postgres:17.12` tag was re-pushed after the local images used for that evidence were pulled (index digest `0d938e97…f6ac` then, `97fb5337…af1a9` in the registry on 2026-11-27). The numbers above were measured on the earlier build; re-measure on the exact digest if 17.12 is ever chosen.
- **To close it:** an owner-approved decision on the frozen SQL amendment (a verified bounded variant, PR #56 lists the options) or an owner decision to accept the 17.12 plan behaviour, then a re-measurement on the chosen digest. Until then this section and PR #56 are the record.

## 4a. Images, logging, monitoring, MinIO (what exists after 2026-11-27, what is still open)

- **Immutable images.** `preflight.mjs` (without `--local`) now **refuses** an application image that is a tag: `API_IMAGE`, `POS_IMAGE`, `OWNER_IMAGE`, `MIGRATE_IMAGE` must be `name@sha256:<64 hex>` or a bare `sha256:<64 hex>` (what `release-images.mjs` records). `redis` and `caddy` are pinned **by digest in the Compose file** (the floating `redis:7` and `caddy:2` had already moved off the images every rehearsal ran), and `check-release.mjs` refuses a tag for either. A digest is the **image the registry serves now**; refreshing a pin is a reviewed change, not a pull. Still open: **no registry exists** (G3), so the images are built on the host or loaded from `docker save` archives; never run `docker image prune` or `docker system prune` on the host (G16). Running containers are checked again by `host-readiness.sh`.
- **Logging.** Every service now logs with `json-file`, `max-size: 10m`, `max-file: 5` (`x-logging` in the Compose file); `check-release.mjs` refuses a service without it and `host-readiness.sh` checks the **running** containers. Log content is not checked for secrets here (gate A9). Shipping logs off the host is **not built** and not decided.
- **Monitoring.** There is no metrics stack and no alert channel; none was invented. What exists and can run from cron on the host: `host-readiness.sh` (exit non-zero and a list of failures; it prints no secret). **Open owner decisions:** who is told, by what channel, and who reads it; whether to route a health path (`/healthz`, `/readyz` are not reachable through the public hosts; a Caddyfile and code change, **not made**); an external uptime probe can only fetch the POS home page.
- **DNS and TLS.** Three A records (`POS_HOST`, `OWNER_HOST`, `OPS_HOST`) and ACME are **host work**; the owner names who owns the DNS zone and who renews if ACME fails. `host-readiness.sh` fails when a certificate expires within 14 days or cannot be read on port 443. The `ADMIN_CIDR` rule trusts the source address Caddy sees (G4): test it from inside and outside the range.
- **MinIO.** No first-party code imports an S3 or MinIO client, so the bucket holds **no business data** at this tip. **Decision proposed for the owner: exclude the MinIO volume from backups and from the restore drill for the alpha, and make "adds an upload or storage write" a release-blocking change that must first add the volume to the backup, the restore drill and the readiness check.** Not decided until the owner says so.
- **Host.** Firewall, SSH, patching, time sync and a reboot test are host work; `host-readiness.sh` only checks the clock and the disk. After a reboot Docker restarts `unless-stopped` services but does not honour `depends_on` ordering and does not re-run the one-shot jobs: never tested (G17).

## 5. Backup and restore

- `backup` (a verified `pg_dump -Fc`) runs **before** `migrate` on every start. Never skip it.
- **Restore drill before the alpha opens, on the real host:** restore the newest dump into a **new** database (`pg_restore --no-owner`), compare row counts and the schema fingerprint, then point `POSTGRES_DB` at it only if recovering. Never restore over the live database. Locally rehearsed; **not yet rehearsed on a host**.
- Record backup time, size, restore time. Those numbers are the RTO evidence an accountant will ask for.
- **The backups volume holds two kinds of dump.** `pre-migrate-*` dumps (one per start, written by the `backup` job; the first `up` also backs up the still-empty database) are **rollback points and are never pruned**: restore the file whose name the `backup` job printed and whose sha256 you recorded, not "the newest" and not "the first". `scheduled-YYYYMMDDTHHMMSSZ.dump` files come from the new `backup-scheduler` service (next bullet).
- **Scheduled backups and retention (built 2026-11-27, tested locally, NOT deployed, NOT approved).** The `backup-scheduler` service uses the **same PostgreSQL image as the database** and, every `BACKUP_INTERVAL_HOURS` (default 24, allowed 1 to 24), writes a verified `pg_dump -Fc` (`pg_restore --list` must read it, a size floor of 4,096 bytes must be met) plus a `.sha256` sidecar, and only then records the time in `.last-backup-ok`. Its Compose healthcheck turns **unhealthy when that file is missing or older than 26 h**, and `host-readiness.sh` checks the same. After every **successful** backup it keeps the newest `BACKUP_KEEP` **verified** scheduled dumps (default 14, allowed 3 to 365) and deletes older ones with their sidecars; it never touches `pre-migrate-*` dumps, partial, unverified or unrecognised files. A **failed** backup writes `.last-backup-failed`, deletes **nothing**, and retries in 15 minutes. `preflight.mjs` refuses out-of-range values. **The interval, retention, RPO and RTO are owner decisions; the defaults are a proposal.** The scheduler holds the PostgreSQL superuser password, exactly like the existing `backup` job.
- **Off-host copy: OPEN, owner decision (destination, encryption, who holds the key, how long).** Nothing in the repository transfers a backup off the host and none was invented. What is ready for it: the dump and its sidecar are plain files in the `flower-staging-backups` volume, and `restore-offhost.sh` (below) **refuses a dump that has no matching sidecar**. Until a destination exists the backups are **not** a disaster backup (a lost host loses the database and every dump with it).
- **Restoring on a different server needs the four cluster roles first** (measured 2026-11-27): a dump of one database does not carry roles, so on an empty server `pg_restore --exit-on-error` stops at the first `GRANT … TO flower_app`, and without `--exit-on-error` it restores 79 policies and **0 of the grants**. The script does it in the right order: `bash infra/staging/ops/restore-offhost.sh <dump> <postgres-container> [database]` checks the sidecar, **refuses an existing database**, creates the four roles from `roles-bootstrap.sql` (idempotent; **fails closed if an existing role has the wrong attributes**, e.g. `BYPASSRLS` on `flower_app`), restores with `--exit-on-error`, and prints post-checks (policies equal to the dump's, tables with row level security, migrations). Then run the `roles` job and `MIGRATION_MODE=check`. Verified on a fresh container of the pinned image: the roles-first order works, the same restore **without** the roles fails (negative control), a tampered or sidecar-less dump is refused, a second restore into the same database is refused. **Not yet done on a real second machine.** Whether a later migration adds a fifth role is not covered: compare `roles-bootstrap.sql` with the source cluster each time. Evidence: `STAGING-READINESS-MATRIX.md` §2.12 and §2.6.
- The earlier manual restore of the same kind (measured 2026-11-27 with hand-created roles) gave exit 0, a fingerprint equal to the backup's except the one explained CHECK parenthesisation, and tenant isolation as `flower_app`: `STAGING-READINESS-MATRIX.md` §2.6.

## 7. Cashier onboarding (the alpha path)

1. An operator on `OPS_HOST` (platform realm, `platform:tenant_users:manage`, **step-up MFA**) provisions a workspace, then invites staff with route A: `POST /v1/platform/tenants/:tenantId/staff-invites` (roles `cashier`, `sales`, `manager`; scope is one company and one branch).
2. The response carries a one-time `setPasswordToken` (24 hours, single use, stored hashed, `Cache-Control: no-store`). **Delivering it is a human step (OPEN: channel).** Hand it over in person or through a channel the owner approves; never paste it in a ticket.
3. **There is no set-password screen in any app** (verified: no page or client call in POS, Owner Web, Super Admin or Customer Web; only `POST /v1/auth/set-password` and an API-client method exist). Until a screen is built (**OPEN, next engineering task**), the operator completes this step with the API on the staff member's behalf, in front of them, so the chosen password is never typed into a ticket or chat. Then the staff member signs in on the till. A cashier needs no MFA (owner decision); a **manager** must enrol an authenticator **in front of the operator**, immediately, before being given any duty (Owner Web has a Security page for it, `POST /v1/auth/mfa/enrol` + `/confirm`, and the API accepts both calls from an enrolment-only session; **the page itself was not exercised in a browser with an enrolment-only session**, the harness enrols through the API: verify it in A6). Until enrolment is **confirmed** and the manager signs in again, the manager can do nothing financial (the gate).
4. Operator checks: the cashier sees the catalog (F-1a), a sale takes cash or recorded card, a second cashier cannot see the first one's workspace (cross-tenant check with two workspaces).
5. There is **no invite revoke and no re-issue** and **no MFA reset** in the code today. A mistyped email or a lost authenticator is an operator-with-database-access problem. **OPEN** (see `MANAGER-MFA-GATE-REVIEW.md`).

## 8. Financial reconciliation (what exists now)

Reports available through Owner Web and the API: sales and VAT report, tender totals, receivables current state ("Who owes us"), customer advances and unapplied receipts, trial balance (API; no Owner Web screen). **Not part of the alpha:** cash-drawer reconciliation and X/Z reports (Phase 4, routes inert; cash sales write no register movement).

Daily procedure for the alpha, to be agreed with the accountant:

1. Sales report gross, VAT and net for the day equals the sum of the day's invoices.
2. Tender totals per method equals the sales report's paid total; cash is counted on paper until the register is wired.
3. Receivables control equals the sum of open balances per customer; advance liability is shown separately and never netted.
4. A sample of at least 10 invoices per day is recomputed by the accountant against the VAT rules (F-6 refuses an unclassified product for a sale).
5. Any difference is recorded and explained; nothing is "absorbed".

## 9. Rollback

Migrations are forward-only, so **the rollback is a restore**, never "run the old image on the new schema": the previous image's migrate runner **refuses** a database that carries a migration it does not know (`{"ok":false,"refused":"database drift: applied migrations are not all approved and finished — nothing was applied","unknown":[…]}`, exit code 2; measured).

**Rehearsed locally on 2026-11-27** (`infra/staging/rollback-rehearsal-local.sh`, Docker Desktop only, disposable `flower-staging` resources, two real workspaces, a sealed balanced ledger, a labelled test migration that is NOT part of any release): **142 checks passed, 0 failed, 1 explained deviation** (below). Not rehearsed on a host.

1. Stop sales (the till is online-only; use the paper log of `PILOT-RUNBOOK.md` §7). Record the image IDs of the running set (`release-images.mjs`) **before** every deploy; deploy by those IDs.
2. Quiesce writers: `docker compose stop caddy pos owner-web api`, confirm no `flower_app` / `flower_platform` connection remains, then run `backup` (a verified `pg_dump -Fc`). Note the dump's sha256 and size.
3. Deploy the new set. `MIGRATION_MODE=check` first: it must list exactly the approved pending migrations; the runner refuses an unlisted extra folder and a changed file (both measured), and applies nothing in that case.
4. **To roll back:** quiesce writers again, then restore the pre-migration dump into a **new** database: `CREATE DATABASE <new>` then `pg_restore --no-owner --exit-on-error` (use the pinned PostgreSQL image). Keep the migrated database untouched for forensics. Compare the fingerprint (`rollback-rehearsal/fingerprint.sql`) of the restored copy with the one taken at backup time.
5. **Flush Redis before the previous API serves traffic**: `bash infra/staging/ops/flush-redis-sessions.sh <redis-container> <api-container>`. It **refuses while the API container is running or cannot be found** (a running API could be refilling sessions or serving a stale one), runs `FLUSHALL`, checks `DBSIZE` is 0, prints only counts (never a key or the password). Sessions, rate limits and idempotency state live in Redis and are **not** part of the database backup. Measured: without the flush, an access token issued while the new set was running was still accepted (HTTP 200) after the database was rolled back; with the flush it is rejected (401) and everyone signs in again. The flush also drops idempotency keys and rate limits, so **roll back only with sales stopped** (readiness matrix G12).
6. Point the env at the previous set **by the recorded immutable IDs** and at the new database (`POSTGRES_DB=<new>`; Compose recreates the services whose configuration changed, the postgres container included, on the same volume; the migrated database stays in that volume, measured), run `preflight.mjs`, then `MIGRATION_MODE=deploy docker compose … up -d --wait`. The runner reports 49 approved / 49 applied / nothing pending; `backup`, `roles` and `seed` run as on any start.
7. Verify: run `bash infra/staging/ops/host-readiness.sh infra/staging/.env.staging` (read-only; exit 0 only if every check passes: all services running and healthy, `/readyz` ok, a verified backup within 26 h, the four application containers on an immutable image reference, rotated logs, disk, TLS expiry on the three hosts, clock sync). Then: image IDs equal the recorded set; row counts equal the backup; the ledger is balanced and sealed; two-workspace isolation; one sale, one reprint, the Owner sales report.
8. Revert-forward in git for any bad merge; no history rewrite, no force-push.

**What the rehearsal showed (read before relying on it):**

- **Data written after the backup is lost by design** (the recovery point is the backup time). The B-era customer written after the backup was gone after the restore, as intended.
- The restored schema equals the original in every table row-hash and every schema aspect **except the parenthesisation of one CHECK constraint** (`item_identifier_value_chk`): PostgreSQL re-parses the dumped text and flattens `((a AND b) AND c …)` into `(a AND b AND c …)`. The definition is the same; both forms gave the same result on 11 boundary values (4 accepted, 7 rejected, 0 disagreements). The strict fingerprint therefore reports this as an **explained deviation**, not a pass.
- After the previous set was redeployed, its `seed` job re-ran idempotently and changed only `updatedAt` on 472 reference rows (`app_meta` 1, `business_type_template` 35, `business_type_template_capability` 429, `country` 6, `plan` 1); no row was added or removed.
- Backup file: byte-identical (sha256) from creation to the end of the rehearsal.
- Not covered by the rehearsal itself: object storage (MinIO) content is not in the database backup (no first-party code imports a storage client, so it holds no business data at this tip); no host, no off-host copy, no ACME TLS, no real data volume. The **off-host restore onto a fresh server** was measured separately on 2026-11-27 (`STAGING-READINESS-MATRIX.md` §2.6; it found the missing-roles step above).
