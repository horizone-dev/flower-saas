# Manager MFA enrolment gate — security review of the candidate (2026-11-18)

**Candidate, not applied.** `patches/F7c-mfa-gate.candidate.patch` (sha256 `13ab801c…d51d`, 15 files, no migration, no schema change, no permission change, no new route). It applies after F-7c in `december-sequence.sh`. Nothing below is an approval; the reviewer and the owner decide.

## What the gate does

A session for a user who holds the system role `manager` and has **no CONFIRMED TOTP factor** keeps only `users:view`, the key that guards just the enrol, confirm, step-up and logout routes. The decision is read from the database each time a session's access is built (login, token rotation, post-RBAC refresh); a failed lookup issues no session. The admin view of a user's access (`resolveForUser`) is unchanged. Cashier and sales onboarding is unchanged.

Tests (real PostgreSQL + Redis, the real guard pipeline and login/invite/enrol/step-up routes): `mfa-enrolment-gate.integration.test.ts` **G1–G10**, `mfa-enrolment-gate.test.ts` (9 unit tests), seven mutants caught (gate never applied, PENDING counted, role list emptied, enrolment set widened, system-role check dropped, bypass in `resolveForSession`, refresher reverted).

### Read-only check before applying to a workspace that already has managers

```sql
SELECT u.id, u.email FROM "user" u
JOIN user_role ur ON ur."userId" = u.id JOIN role r ON r.id = ur."roleId"
WHERE u.status = 'ACTIVE' AND r.key = 'manager' AND r."isSystem" AND NOT EXISTS (
  SELECT 1 FROM mfa_factor f WHERE f."userId" = u.id AND f.kind = 'TOTP' AND f.status = 'CONFIRMED');
```

(Run it with a read-only role. Table and column names were checked against `schema.prisma` at the #49 tip; the query was run against the real test database inside the gate suite (a temporary test, not committed) and returned exactly the managers without a confirmed factor; it has not been run against any live database.)

## Verdict for the reviewer

The gate does what it claims and fails closed. It **removes** the password-only manager exposure but it does **not** make manager onboarding safe by itself: recovery (2), token delivery (6) and the owner/admin gap (5) are open decisions. The smallest honest alpha is cashier + sales + owner with managers added only after recovery is decided.
