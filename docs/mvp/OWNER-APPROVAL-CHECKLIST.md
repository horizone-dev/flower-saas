## 4. Addendum 2026-11-14 (later): R-1 security review, and the staging/bootstrap additions

**R-1 review — every code path that touches the vault.** Only `SecretsService` uses a `CryptoProvider` (nothing else imports it; the only cipher code in the API is in `crypto-provider.ts`, so there is no plaintext fallback). Its only entry point is the platform route `/v1/platform/tenants/:id/provider-credentials` (`platform:secrets:manage`). With `SECRETS_PROVIDER=disabled`: **create / rotate** encrypt _before_ any write → `503 SECRETS_DISABLED`, no row, nothing stored; **read of a sealed credential** → 503; **list / revoke / not-found** need no secret and keep working. **Must stay unavailable:** creating any provider credential, and therefore everything that needs a `provider_credential` row — provider-backed card payments, payment webhooks, settlement batches, provider refunds (already `501`) and any future provider adapter. **Unaffected:** cash and card-**terminal** sales (a recorded local tender, no provider). Evidence (disposable copy with R-1 applied; the patch stays unapplied): 4/4 vault tests — create refused, **no row and the plaintext found in no table of the database**, a pre-existing credential cannot be opened (503), a cash + card-terminal split sale completes — plus 15 unit tests (env guard, provider); a mutant "disabled" provider that stored the plaintext is caught by 2 tests. Residual (existing behaviour, not new): the platform route receives the plaintext secret in the request body (TLS only, not logged).
