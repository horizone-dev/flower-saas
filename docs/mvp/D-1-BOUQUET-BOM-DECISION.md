# D-1 — florist bouquet / BOM: the owner decision (smallest implementable design)

2026-11-15 · DECISION PAPER · nothing here is approved or implemented in the product. Proven now: the pure explosion arithmetic (`recipe-explosion.ts`, 6 tests) and — at ledger level — that component consumption, COGS, cancellation and "no double deduction" work on the existing valued ledger (`stock-bom-simulation.integration.test.ts`, both costing methods — written after this paper first cited it; see the correction in section 6). **BOM is neither assumed approved nor deferred: this paper asks for the decision and prices each answer.**

## 1. What the frozen architecture already decides (ARCHITECTURE §23–26, ADR-0018)

- A `BOM` variant (a predefined bouquet) **consumes its COMPONENTS**; the system "does **not** decrement a fictional finished-bouquet stock for a BOM variant". A recipe version is snapshotted per order. A `CUSTOM` bouquet snapshots the components the florist picked. A work order may create `MATERIAL_CONSUMPTION` movements and an optional `PRODUCTION_OUTPUT`.
- **None of it exists in code**: there is no `recipe`, `recipe_component`, `work_order` or order-line component snapshot table — only the catalog capability flags (`strategy.bom`, `production`, `custom_composition`) and `product.fulfilmentStrategy ∈ STOCKED | BOM | CUSTOM`. Today a BOM variant would sell **with no stock effect at all**.
- Consequence for the MVP: the I-7 sale hook can deduct STOCKED lines only. Every bouquet sold would leave its stems, ribbon and wrap on the books — the shelf and the valuation would drift from reality on day one. That is why this decision cannot wait.

## 3. Build-to-order versus build-to-stock — and what each does to the books

| Aspect                      | **Build-to-order** (BOM consumed at sale) — recommended minimum                                                                                                 | **Build-to-stock** (production document, then sell a finished item)                                                                                                                                              |
| --------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Stock on the books          | components only (no finished-bouquet stock; matches ARCHITECTURE §23)                                                                                           | components AND finished bouquets                                                                                                                                                                                 |
| When components leave       | at the sale                                                                                                                                                     | at the production run                                                                                                                                                                                            |
| Accounting at the event     | sale: `Dr COGS / Cr Inventory` = Σ components' cost (one entry, existing mapping)                                                                               | production: value moves inside **one** inventory account (`Dr Inventory / Cr Inventory`) — **no GL entry** while there is a single inventory account; sale: `Dr COGS / Cr Inventory` at the finished item's cost |
| Cost of the finished unit   | n/a (cost recognised at the sale from the components)                                                                                                           | LOT_ACTUAL: the batch costs Σ the consumed component batches; WEIGHTED_AVERAGE: the pooled average of the finished item (production cost is added to it)                                                         |
| Unsold / spoiled bouquets   | invisible until sold (components stay "available" although assembled) — a known inaccuracy; discarded bouquets must be written off as component wastage by hand | exact: a finished bouquet is wasted at its own cost                                                                                                                                                              |
| Yield loss on assembly      | none recorded                                                                                                                                                   | production wastage entry (components consumed − output)                                                                                                                                                          |
| Expiry of the finished item | n/a (components keep their own expiry; FEFO picks the oldest)                                                                                                   | needs a rule (earliest component expiry, or a fixed shelf life)                                                                                                                                                  |

| Sale-hook change            | explode, then issue the components                                                                                                                              | none beyond STOCKED (the finished item is a STOCKED line)                                                                                                                                                        |
| Realistic fit for a florist | shops that assemble to order (most orders, delivery, events)                                                                                                    | shops with a counter of ready-made bouquets                                                                                                                                                                      |

## 4. The smallest implementable design (recommended) and its price

**Recommended D-1 = build-to-order BOM, MVP scope A, with B and CUSTOM as separately priced options.**

_Scope A (the minimum that makes bouquets correct):_

1. `recipe(id, tenant, company, variant, version, yield_qty, status, effective_from)` + `recipe_component(recipe, component_variant, qty_base, wastage_bps)` — versioned; a recipe in use is immutable (a new version supersedes it).
2. `order_line_component` snapshot written when the sale explodes the recipe (component, quantity, recipe version) — the single source for retries, cancellations and credit notes.
3. In the I-7 sale transaction: BOM line → `explodeRecipe` → `issueStockLines` for the components; STOCKED line → deducts itself. COGS = Σ.
4. Cancellation / credit note: reverse from the snapshot at original cost (I-8).
5. Availability for a BOM variant = `buildableUnits` over **sellable** component stock; the sale itself still re-checks inside the lock.
6. Owner Web: a recipe editor per BOM variant (component picker, quantity + unit, allowance). Permissions `recipe:view` / `recipe:manage` (already named in the architecture).
7. DB guard: a BOM variant can carry no stock movements of its own.

_Price:_ recipe schema + service + tests 3–4 d · sale / cancel integration (inside I-7 / I-8) +2–3 d · availability + POS 1–2 d · Owner Web recipe editor 3–4 d · tests / review 1–2 d ≈ **10–15 working days** on top of the inventory estimate. _Option B (production documents for pre-made bouquets)_ ≈ +5–7 d plus an accountant decision on production costing and finished-item expiry. _CUSTOM bouquet at the till_ ≈ +3–4 d (the component snapshot already exists; the POS picker is the cost). **If none of A, B, CUSTOM is chosen, every bouquet sold stays outside inventory — not recommended for "real inventory".**

## 6. Evidence available today

**Correction (2026-11-15):** the first version of this paper cited `stock-bom-simulation.integration.test.ts` as existing evidence **before that file had been written**. That claim was unsupported when it was made. The file now exists and its results are recorded below; nothing in the paper depended on it.

Final run (all stock tests, after the last source / test edit): 22 files, **269 tests passing**. The evidence specific to D-1:

- `recipe-explosion.test.ts` — **6 tests**, pure: exact explosion (12 roses + 0.5 m ribbon + 1 wrap; S / M / L; +5 % → 13 stems); never under-consumes and never over-consumes by a full grid step across 300 random recipes; duplicates merge in ascending variant id (the lock order); availability equals the explosion's own coverage; malformed recipes refused.
- `stock-bom-simulation.integration.test.ts` — **23 tests**, real PostgreSQL, application role, row-level security, **both costing methods** (11 per method + 1 cross-company). Per method: recipe quantities entered in other units convert exactly (1 dozen = 12 stems, 50 cm = 0.5 m) and explode to 13 roses / 0.5 m / 1 wrap per bouquet; a build-to-order sale consumes all components atomically at the method's cost (COGS = Σ components: 2,900 under LOT_ACTUAL vs 3,550 under WEIGHTED_AVERAGE for two bouquets) and the ledger reconciles; **no double deduction** — a retry replays (stock unchanged) and a retry with a recipe edited in between is refused `IDEMPOTENCY_CONFLICT`; availability = consumption (n bouquets sell, n + 1 is refused whole with nothing half-deducted, the limiting component is named, in two different positions); expired components neither count nor can be consumed; branch isolation (a sale in the branch without the components is refused `STOCK_NOT_TRACKED`, availability 0); rollback after the components were issued leaves nothing and the retry then succeeds; 12 simultaneous sales against stock for 7 → exactly 7 succeed, every minor unit of cost accounted, no deadlock; cancellation reverses every component at its original cost and restores stock and value exactly, once only; a simulated build-to-stock production run conserves total inventory value to the minor unit and the finished item then sells at its production cost.
- `stock-availability.integration.test.ts` — **12 tests**: the read-only `sellableQuantity` foundation (section 7).
- Mutation checks on the new availability code: 6 mutants, 6 caught (two only after tests were added for an expired batch in another branch and a non-first limiting component).

**What this does NOT prove (and the paper does not claim):** any recipe schema or service (none exists), the sale hook (the frozen complete-sale is untouched), the order-line component snapshot (the test supplies the stored explosion itself), a database rule forbidding stock movements on a BOM variant (**not implemented** — double deduction is prevented in this simulation by per-component source keys and by the caller choosing one mode; the "one stock mode per variant" invariant is a proposal that still needs a trigger and the sale hook), or production documents (the production run is simulated with ordinary receipt / issue calls and would need its own movement types). **D-1 is not approved.**

## 7. Stock-based availability — status

`sellableQuantities` / `sellableQuantity` (valued ledger) and `bomAvailability` (`stock-availability.repository.ts`) are implemented, **read-only, inert (no route)**: per item and branch, `onHand`, `sellable` (expired batches excluded under both methods) and `expired`, computed in one SQL statement (one snapshot), taking no lock and writing nothing (a test holds an item's balance row in an open transaction and the read still answers immediately). Tenant / company / branch are validated; an item of another tenant reads as not tracked; a branch-narrowed session sees only its branch; a company without a confirmed method gets `409 INVENTORY_NOT_ENABLED`. UI semantics (`availabilityStatus`): `AVAILABLE`, `INSUFFICIENT` (tracked, show what is available), `NOT_TRACKED` (never received here = out of stock). It is a **hint**: a sale can still be refused `409 INSUFFICIENT_STOCK` if another sale won the race, so the POS must treat that response as normal. `bomAvailability` takes the recipe from the caller (no recipe table).

## 8. Update — the recommended scope A foundation now exists (inert), still NOT approved

After the first version of this paper, the recipe schema draft (`DRAFT-M-recipes-build-to-order.sql`) and services (`recipe.repository.ts`, `bom-build-to-order.repository.ts`) were written and tested on disposable databases: `recipe-bom.integration.test.ts` — **30 tests**, both costing methods, covering immutable recipe versions (units converted exactly; one ACTIVE version; no edit / delete / extension, even by the owner role), the stored consumption snapshot (a retry replays it; a recipe published in between changes nothing; a different request is refused), atomic component consumption and COGS, availability = consumption per branch, negative-stock refusal, rollback, concurrency (12 sales against stock for 7 → 7; 10 simultaneous retries → one; concurrent publishing and cancelling), full cancellation at original cost even after a new recipe version, isolation (tenant, company, branch), and the database rule that a BOM variant carries no stock of its own. 26 mutants of this code: 26 caught after two direct tests were added (see the plan, section 13). The pieces the paper said were missing are now: a recipe schema and service (**present, inert**), the order-line snapshot (**present as `bom_consumption`**, keyed by the sale line), and the "no stock on a BOM variant" trigger (**present in DRAFT-M**). Still absent: the sale hook (frozen), any route (drafted: `DRAFT-N`), the Owner Web recipe editor, bouquet availability in the POS, partial-bouquet cancellation (full cancellation only), and build-to-stock production (a separate feature). **D-1 remains the owner's decision.**

## 2026-11-15 addendum — B1 versus B2, and the smallest B2 path (NOT APPROVED; this is not a request to build B2)

**B1 is already built and proved end-to-end** (`stock-sale-integration.integration.test.ts`: bouquet sale consumes components, COGS = Σ components, cancellation returns the stored explosion at original cost, no double deduction, both methods). **B2 is a separate feature that does not exist in code.** Nothing below is approved; D-1b stays the owner's decision.

| Question the shop asks                                  | **B1** — components leave when the bouquet is SOLD                            | **B2** — components leave when the bouquet is ASSEMBLED                                                                    |
| ------------------------------------------------------- | ----------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------- |
| Raw-flower count while ready bouquets sit in the cooler | **overstated** — those stems are still "in stock" until the bouquet sells     | exact — stems leave at assembly                                                                                            |
| Count of ready-made bouquets                            | not tracked (a bouquet has no stock of its own; the database refuses it)      | tracked as a normal stocked item                                                                                           |
| Bouquet that wilts unsold                               | the loss shows up as nothing until someone adjusts the **components** by hand | normal wastage of the **bouquet** at its production cost                                                                   |
| Cost of a sold bouquet                                  | Σ components at the sale date (method cost _at the sale_)                     | the cost frozen at assembly (LOT_ACTUAL: exact batches; WEIGHTED_AVERAGE: pooled average of the finished item)             |
| Staff discipline                                        | none — selling is the only action                                             | a production entry for every batch assembled; a missed entry = sale refused (bouquet stock 0) — a real operating burden    |
| Journal                                                 | one `STOCK_COGS_SALE` (already contracted)                                    | production posts **nothing** while there is one inventory account (value moves inside it); the later sale posts COGS as B1 |
| Build effort                                            | done (B1 services, tests); remaining = the I-7 sale hook                      | ≈ **5–7 working days backend** (below) **+ 2–3** for an Owner Web production screen                                        |

**Smallest B2 path** (reuses the ledger; no second stock engine):

1. **Schema (edit the unapplied drafts only):** a `production_run` document (header + lines, immutable, same one-transaction / deferred header = lines = ledger pattern as `stock_document`); two new movement types `PRODUCTION_CONSUME` and `PRODUCTION_OUTPUT` in DRAFT-I's type check (so purchase-receipt reports and the `STOCK_RECEIPT` journal can never pick up an assembly); `recipe.mode` gains `BUILD_TO_STOCK` whose finished variant must be a **STOCKED** variant (the existing trigger keeps BOM variants stockless, so one variant can never be both — that is what makes double counting impossible).
2. **Service:** one scoped transaction: lock components + finished item in the single ascending-id order → `issueStockLines` for the exploded components (existing, both methods) → receive the finished quantity at **Σ the consumed values** (LOT_ACTUAL: the output batch carries Σ the consumed batch costs; expiry = earliest component expiry, accountant A-13; WEIGHTED_AVERAGE: added to the finished item's pool). Idempotency by run id; a stored explosion exactly like `bom_consumption`; **no journal** (value is conserved inside `ASSET.INVENTORY`; the reconciliation gate already proves GL = ledger).
3. **Sale without double counting:** the finished item is an ordinary STOCKED line (`issueStockLines`); a BOM line still consumes components. The line's strategy decides — a line cannot do both.
4. **Wastage / cancellation:** wastage of the finished bouquet = the existing adjustment path (`WASTAGE`) at its production cost; cancelling a **sale** of it = the existing `ISSUE_REVERSAL`; cancelling an **assembly** before any unit sold = a production reversal (issue the output at cost, return components to their original batches) — refused once any output unit has been sold.
5. **Proof needed before approval of the code:** 25 simultaneous assemblies + sales against limited stock, GL = ledger after every scenario, both methods, mutation sweep — the same bar as B1.

The earlier "+5–7 d" is this backend path; a screen is extra. **Accountant A-13** (no GL entry for production; finished-item expiry rule; yield-loss account) is only needed if B2 is chosen. **Recommendation unchanged: B1 now; B2 only if the shop keeps a counter of ready-made bouquets whose stems are significant stock.** The ledger-level simulation of a production run (`stock-bom-simulation.integration.test.ts`) remains the only B2 evidence — it proves value conservation, not a production service.

## 2026-11-15 addendum 2 — B2 (build-to-stock) implementation design, independently safe (NOT APPROVED, NOT BUILT)

Scope of this section: a design a reviewer can approve or reject **without touching B1**. B2 stays inert until the owner chooses D-1b = B2, the accountant answers A-13, its own migration is approved under C-7 and the security scope covers it. Nothing below is implemented; the only B2 evidence in the repository is the value-conservation simulation in `stock-bom-simulation.integration.test.ts`. **B2 is not unlocked by D-1a, by B1, by C-3 or by the paid-return decisions.**

**Independence from B1 (why it cannot disturb it):** B1 keeps working untouched — a BOM variant carries no stock (database rule), its recipe `mode` stays `BUILD_TO_ORDER`, and `consumeBuildToOrder` / `cancelBuildToOrder` are not edited. B2 adds a _different_ variant kind: the pre-made bouquet is an ordinary **STOCKED** variant (a "Ready Rose Box" SKU) whose recipe has `mode = BUILD_TO_STOCK`; the sale hook already treats a STOCKED line as a stocked line. One variant can never be both (a BOM variant carries no stock; a BUILD_TO_STOCK finished variant must be STOCKED — enforced by trigger), so a sale can never deduct a bouquet twice.
