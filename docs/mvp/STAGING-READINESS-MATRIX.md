# Staging readiness matrix for the December internal alpha (2026-11-27)

**Nothing here was run on a host.** No staging host exists (decision **D-HOST** is open), no credential exists in the repository, nothing was deployed, pushed or merged. This matrix sits next to `STAGING-DEPLOYMENT-CHECKLIST.md` (the procedure) and `RELEASE-CANDIDATE-INTEGRATION-ORDER.md` (the merge order). Its job is to say, per requirement, **what is already proven locally, what only a real host can prove, and what is a gap**.

Legend: **LOCAL** = proven on this machine in Docker, evidence named. **HOST** = can only be proven on the real staging host. **GAP** = missing in the repository or undecided; not invented here.

### 2.6 Off-host restore: measured 2026-11-27, with a finding

**Question.** Rehearsal phase 5 restored the pre-migration dump into a new database **on the same PostgreSQL server**. Could the dump file alone, copied elsewhere, bring the database back on a **brand-new server**?

**Method (`rc/offhost-probe.sh`, disposable, nothing remote).** A real pre-migration dump (845,652 bytes, sha256 `6a6242fc…`, two real workspaces, a sealed balanced ledger, 103 tables) was copied out of the backups volume as a plain file. A fresh container of the **pinned** PostgreSQL image (17.11 at the recorded digest, empty cluster, no application roles, no network access except the probe's own network) restored it.

| Case                                                                             | Result                                                                                                                                                                                                                                                                                                    |
| -------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **A** fresh server, no roles, `pg_restore --no-owner --exit-on-error`            | **Fails, exit 1**: `role "flower_app" does not exist` at the first `GRANT USAGE ON SCHEMA public TO flower_app`                                                                                                                                                                                           |
| **A2** same, errors ignored (what an operator might do next)                     | exit 1, **110 errors, 0 of the table grants restored**, 79 of 79 policies restored. The database would load but the application roles would have no privileges. Not usable, and it looks restored                                                                                                         |
| **B** the four cluster roles created first, then the same restore                | **exit 0 in 1 s**; row counts equal (2 tenants, 2 users, 2 customers, 49 migrations); 79 of 79 policies; row level security enabled on 77 of 77 tables (equal to the source); grants fingerprint identical                                                                                                |
| B: fingerprint of the restored copy against the one taken at backup time         | 112 of 113 lines identical. The one difference is the **already explained** CHECK constraint re-parenthesisation: compared one by one, **700 of 700 constraints exist, exactly one definition differs** (`item_identifier_value_chk`, `((a AND b) AND c …)` becomes `(a AND b AND c …)`, same expression) |
| B: set-A migration runner, `MIGRATION_MODE=check`, against the restored database | `{"ok":true,"approved":49,"applied":49,"pending":[]}`, exit 0                                                                                                                                                                                                                                             |
| B: the real `roles` job (sets the application passwords)                         | exit 0, no password in its output                                                                                                                                                                                                                                                                         |
| B: tenant isolation on the restored copy, as `flower_app` over a real login      | not superuser, no `BYPASSRLS`; with **no tenant set it sees 0 customers**; as tenant A it sees 1 and **0 of tenant B's**; as tenant B it sees 1; the superuser control sees both (2)                                                                                                                      |

**Cause.** `pg_dump` of one database never carries cluster-level objects. The roles are created by a migration inside the source cluster, so the dump references roles it cannot create. **The four roles** (`flower_app`, `flower_platform`, `flower_dispatcher`, `flower_migrate`) **must exist, with the source's attributes, before `pg_restore`**:

```sql
-- run as the superuser on the NEW server BEFORE pg_restore; verify against the source with the query below
CREATE ROLE flower_app        NOLOGIN NOSUPERUSER NOCREATEROLE NOCREATEDB NOBYPASSRLS;
CREATE ROLE flower_platform   NOLOGIN NOSUPERUSER NOCREATEROLE NOCREATEDB BYPASSRLS;
CREATE ROLE flower_dispatcher NOLOGIN NOSUPERUSER NOCREATEROLE NOCREATEDB BYPASSRLS;
CREATE ROLE flower_migrate    NOLOGIN NOSUPERUSER NOCREATEROLE CREATEDB   NOBYPASSRLS;
-- source check (attributes must match; LOGIN is granted later by the roles job):
-- SELECT rolname, rolsuper, rolcreaterole, rolcreatedb, rolbypassrls FROM pg_roles WHERE rolname LIKE 'flower_%' ORDER BY 1;
```

Then `pg_restore --no-owner --exit-on-error -d <new db> <dump>`, then the `roles` job (it refuses unless the roles and `_prisma_migrations` exist), then `MIGRATION_MODE=check`. **Add this to the runbook and to the A5 evidence** (**G10**). Whether a later migration adds a fifth role is not covered by this snippet: compare against the source cluster each time. **Not tested:** the alternative of bringing the stack up on the new host with an empty database first (the migrations then create the roles) and restoring into a second database.

**What this does not prove.** Real data volume, real transfer, encryption, a different CPU architecture, the time a restore takes. All **HOST**.

### 2.7 Redis session invalidation during rollback

**LOCAL, measured:** an access token issued while the new set was running was accepted (HTTP 200) after the database was rolled back, and rejected (401) after `redis-cli FLUSHALL`. **Procedure:** flush **before** the previous API serves traffic (`STAGING-DEPLOYMENT-CHECKLIST.md` §9 step 5). **G12:** the flush also clears idempotency keys and rate limits, so a client that retries a pre-rollback request with the same `Idempotency-Key` would execute it again. That is why the rollback is done with sales stopped (paper log) and everyone signs in again. **HOST:** repeat on the host, with the Redis password from the env file.

### 2.9 Tenant isolation

The build-blocking probe suites (cross-tenant and branch isolation) and the 15 structural pin suites are green with R-1 applied (21 files, 742 tests, together with the secrets and config tests). The rehearsal's two-workspace checks (cross-tenant trial balance refused, cross-paired company and branch refused, positive control) passed on set A, set B and the redeployed set A, and now also on a **restored copy on a fresh server** (section 2.6). **HOST (A8):** two real workspaces through the real TLS front door. ### 2.10 Rollback from recorded image IDs

**LOCAL:** the whole sequence (stop writers, backup, deploy a new set with one labelled test migration, restore into a new database, flush Redis, redeploy the previous set by its recorded IDs, verify) passed **142 checks, 0 failed, 1 explained deviation**; phases 1 to 3 were re-run for this matrix with **53 passed, 0 failed**. **HOST:** repeat once with the real images (**A5**), after fixing **G1, G2, G10, G16**.

### 2.11 The host itself (nothing exists to measure)

Firewall (22 restricted to the operator, 80, 443 only), SSH keys only, unattended security updates, **time synchronisation** (TOTP codes and token expiry depend on it), disk sizing for PostgreSQL, backups, Redis and logs, and a **reboot test**: after `sudo reboot` the stack must come back to `/readyz` all `ok` without manual steps (**G17**: Docker restarts the `unless-stopped` services but does not honour `depends_on` ordering after a reboot, and the one-shot jobs do not re-run; this was never tested). **Sizing has not been measured; do not assume it.**
