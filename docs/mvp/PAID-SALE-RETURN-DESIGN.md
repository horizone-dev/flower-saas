# Paid-sale returns — the missing contracts and the smallest correct workflow

2026-11-15 · **DESIGN + DISPOSABLE PROOF · NOT APPROVED · nothing here is live.** No migration, route, permission, frozen file or journal activation was changed. The proof is `apps/api/src/modules/stock/returns/` (inert service + pure math + pure journal) with `DRAFT-O-paid-sale-returns.sql` (never applied to a real database), run on disposable PostgreSQL through the **unmodified** public sale route. ## 1. What the frozen code can and cannot do today (inspected, not assumed)

| Need                                     | What exists                                                                                                                                                                            | Evidence                                                                                                                                                                        |
| ---------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Return a **paid** sale                   | **Nothing.** A settled invoice cannot be cancelled.                                                                                                                                    | `INVOICE_CANCELLATION_BLOCKED_STATUSES` = SETTLED / CANCELLED / PARTIALLY_REFUNDED / REFUNDED / VOID (`order.repository.ts:73`), thrown as `INVOICE_CANCELLATION_NOT_SUPPORTED` |
| Return a **walk-in** (anonymous) sale    | **Nothing.** Refused outright.                                                                                                                                                         | `WALKIN_POST_INVOICE_CANCELLATION_NOT_AVAILABLE` (`order.repository.ts`, before the invoice lock)                                                                               |
| **Partial** credit note                  | Schema ready (`credit_note_line.quantityCredited`, 7-component capacity trigger, proportional columns); **repository is full-cancellation only**                                       | `issueCreditNoteForFullCancellation` is the only public method (`credit-note.repository.ts:91`)                                                                                 |
| Refund money                             | Only **customer-advance** refunds: one CREDIT_NOTE-sourced advance → one payment, CASH / BANK_TRANSFER only; card / gateway / manual refused; provider route is a side-effect-free 501 | `refund-execution.repository.ts` header; `RefundController`                                                                                                                     |
| Refund without a customer                | **Impossible in the database:** a deferred trigger forces every `refund` to be fully covered by `customer_advance_refund_application` rows                                             | `fn_check_refund_application_complete_anchor` (migration 20261005120000)                                                                                                        |
| Credit note without a customer           | **Impossible in the database:** `arReductionMinor + advanceExcessMinor = totalAmountMinor` plus the advance-excess anchor force a CREDIT_NOTE customer advance                         | `credit_note_split_eq_total_chk`, `trg_check_credit_note_advance_excess_anchor`                                                                                                 |
| Release **part** of a payment's coverage | No: releases are 1:1 and full ("no split resolution", "LIFO partial walk" explicitly out of scope)                                                                                     | `credit-note.repository.ts` header                                                                                                                                              |
| Stock / COGS on any return               | None (stock is not wired anywhere in the frozen sale)                                                                                                                                  | —                                                                                                                                                                               |

**Conclusion:** for an anonymous paid sale — the dominant POS case — no amendment of the frozen credit-note / refund tables is possible without breaking their database guarantees. The smallest correct design therefore leaves those tables **untouched** and adds a small immutable return document family beside them (Track W). Customer-linked paid returns can reuse the existing chain but need real frozen amendments (Track C, design only).

## 3. The workflow (Track W — implemented as a disposable proof)

One call, one scoped transaction supplied by the caller, **one global lock order** (the same family as the verified sale and cancel orders):

`idempotency advisory lock → order → order lines → stock balance rows (ascending variant id; stocked lines + bouquet components) → payments (ascending id) → company CREDIT_NOTE counter → [return, lines, refund legs] → ledger movements → Posting Engine (company / period, shared)` — never a stock lock after a payment, counter or GL lock; the scope guard first refuses a session narrowed to another branch with the same non-disclosing `ORDER_NOT_FOUND`.

1. **Gate:** order is anonymous, in this branch; invoice is PAID / SETTLED (always true for a walk-in sale). A customer-linked order is refused (`SALE_RETURN_CUSTOMER_SALE_NOT_SUPPORTED`).
2. **Quantities:** per order line, `returned ≤ sold − Σ earlier returns`, under the order-line lock, backstopped by the database.
3. **VAT / money:** `creditedForReturn` — gross, discount, document-discount share and tax each `floor(x · q / Qo)`, net = gross − discount − share, total = net (+ tax when tax-exclusive); the part that returns the last of the quantity takes the exact remainder. Revenue booked = total − tax (net-of-discount convention, owner ruling 3b.9-ACC). Full return ⇒ credited money = invoice, VAT included (database check at commit).
4. **Refund legs:** to the ORIGINAL payments only — default newest payment first, or an explicit cashier split; both validated (known payment, same method, no duplicates, ≤ what is left on the payment, Σ = return total). The method maps to the account the sale used (cash → cash, bank → bank, manual card → payment clearing); provider-backed tenders are refused (cannot exist in an atomic sale).
5. **Stock (company with a locked method; money-only otherwise):** the whole returned quantity comes back through the existing `reverseIssue` at its **original cost** (LOT_ACTUAL: the very batches it left, last-consumed first; WEIGHTED_AVERAGE: the original issue's cost share) → `STOCK_COGS_REVERSAL`. The **non-resellable** part (`wasteQuantity`, reason DAMAGED / WASTAGE, approver mandatory) is then written off with the existing targeted `adjustStockOut` **from the very lot it returned to** → `STOCK_WASTAGE`. The customer is refunded the full returned units either way; the disposition is the shop's loss. No new account, no new journal kind, no ledger change.
6. **Bouquets (B1):** components restock / write off pro-rata `required × returned ÷ sold` from the stored consumption (never today's recipe), only when exact on the unit grid (`BOUQUET_RETURN_NOT_DIVISIBLE` otherwise — e.g. a ceil-rounded wastage recipe cannot split one bouquet of two).
7. **Journals:** the return entry (M4) plus the stock entries, all through the existing Posting Engine in the same transaction; a closed period aborts everything including the stock movements.
8. **Idempotency:** unique `(tenant, branch, key)` + request fingerprint: same key / same request replays the stored return (no second refund, movement or entry); same key / different request → `IDEMPOTENCY_CONFLICT`; ten simultaneous submissions → one return.
9. **Immutability / audit:** return, lines and legs are append-only for every role (including the database owner); ledger movements carry source keys `SALE_RETURN_LINE` / `SALE_RETURN_WASTE`, reason and approver; one `sale_return.posted` audit row in the same transaction (the audit registry action is part of M8).

## 4. Track C — customer-linked paid returns (design only, NOT built, NOT proposed for the first release)

A customer-linked paid invoice already has the right accounting chain (credit note → coverage release → CREDIT_NOTE advance → refund). Making it work for a paid, partial return means amending frozen code and its pins: (a) lift the SETTLED guard for a return and add `issueCreditNoteForReturn` (quantity per line, the same `creditedForReturn` math, `credit_note_line` capacity trigger already exists); (b) a **partial** coverage release — LIFO over the invoice's payment allocations, each release funding one advance (the 1:1 release→advance rule stays, amounts are partial); (c) refund execution for CARD_TERMINAL (manual terminal slip, payment-clearing account) and a split over several advances; (d) invoice status projection PARTIALLY_REFUNDED / REFUNDED (the vocabulary exists, no transition); (e) the same stock disposition step as §3.5 placed **before the customer-account lock** (proved necessary in I-7 §7). Estimate **8–12 days** after approval, plus independent review; every one of (a)–(d) is a frozen-contract amendment. Until then a customer-linked paid sale cannot be returned and the service refuses it explicitly.

## 6. Evidence (disposable PostgreSQL + Redis, the unmodified public sale route, the real Posting Engine)

`returns/sale-return.integration.test.ts` (27 tests, both costing methods + a company without a method) and 10 unit tests: partial and full returns, VAT and journal reconciliation (revenue, tax payable and cash net to zero across the sale and its returns), exact original-cost reversal (LOT_ACTUAL 500 / WEIGHTED_AVERAGE 450 of a 900 / 1,050 sale, and the two returns sum to the whole cost), rounding stress, split tender, refund validation (explicit split, over-refund, unknown payment), double-refund and over-return refusal (service and database), non-resellable goods written off from the returned lot with reason + approver, failed refund rolls back return / legs / stock / journals / audit / number, 8 concurrent returns of a 3-unit sale → exactly 3, idempotent replay and 10 simultaneous submissions → one, tenant / sibling-branch / customer-sale refusals, immutability for every role, database backstops with the service bypassed, deterministic lock order, bouquet return and write-off. **Mutation sweep: 27 mutants, 25 caught, 2 judged equivalent** (plan §15). Verification: stock suite 410 / 410, pins + gate + returns 1,276 / 1,276.
