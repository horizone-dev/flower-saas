# I-7 — frozen `complete-sale` amendment: design (NOT a patch)

2026-11-15 · DESIGN ONLY · nothing in `orders/`, `sales/`, `payments/` or any frozen contract was edited. A reviewable patch is produced only after the owner approves this design (C-3) and the accountant approves the postings (`I-3-POSTING-CONTRACTS.md`). Ledger-level behaviour that the sale will rely on is already proven (`stock-sale-lines.integration.test.ts`, 13 tests, both methods).

## 1. Goal and non-goals

**Goal:** a completed sale deducts stock automatically, valued by the company's locked costing method, with the COGS journal — all in the sale's own transaction; a cancellation or refund returns the stock at its original cost. **Not in this amendment:** reservations (Phase 5, rule 24 — adding to a cart never consumes stock), BOM/recipe expansion, offline sales (Class C, hard-blocked), provider payments.

## 4. Lock ordering and deadlock protection

Frozen hierarchy today: `order → order lines → company ORDER counter → company INVOICE counter → [order UPDATE, invoice INSERT] → order (share) → invoice → payment rows → company (share) → accounting period (share)`; cancellation uses the frozen ORDER → INVOICE order (task 3b.8 F4).

**Global rule for the amendment:** stock `(branch, variant)` balance rows are locked **after the order / lines (and, on cancellation, the invoice) and before any document counter**, always in **ascending variant id** (`issueStockLines` sorts; one branch per sale). Therefore:

- a transaction that holds a stock lock never waits for an order, invoice, counter, payment or GL lock that a stock-lock waiter could hold — a stock waiter holds (at most) order / invoice rows of its **own** document and other stock rows with a lower id;
- two sales (or a sale and a goods-receipt document) touching the same items in opposite line order serialise in id order — **proved:** 40 concurrent multi-item sales listing items in opposite order, 0 deadlocks, no lost unit; a goods-receipt document uses the same ascending order (30 documents, opposite orders, 0 deadlocks);
- the Posting Engine's company / period locks are **shared** and taken after stock; period close (exclusive) never waits on stock.

**To prove in the patch's own disposable-copy suite (not provable at ledger level):** the full-path pg-lock test of the frozen sale + stock together (a pinned observed lock order like the existing `atomic-walk-in-sale.integration.test.ts`), with `HG3b-SALE-LATENCY` re-run (the deduction adds ≈ 20–50 ms per hot item; that gate is still OPEN from Phase 3B and must be re-measured, not assumed).
