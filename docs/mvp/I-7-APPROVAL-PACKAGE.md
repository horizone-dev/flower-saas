## 2. Transaction sequence and lock order (deadlock protection)

Frozen order today: `order → order lines → company ORDER counter → company INVOICE counter → [order UPDATE, invoice INSERT] → order (share) → invoice → payments → company (share) → accounting period (share)`; cancellation: ORDER → INVOICE. **Amendment:** stock `(branch, variant)` balance rows are locked after the order / lines (and, on cancellation, the invoice) and **before** any counter, always in **ascending variant id** (`issueStockLines` and the BOM explosion sort); the Posting Engine's company / period locks are **shared** and come last. Therefore a transaction holding a stock lock never waits for an order, invoice, counter, payment or GL lock that a stock waiter could hold; two sales (or a sale and a receipt) touching the same items in opposite line order serialise by id.

Proved so far at ledger level (disposable DB, both methods): 40 concurrent multi-item sales in opposite orders — 0 deadlocks, no lost unit; 30 receiving documents in opposite orders — 0 deadlocks; 25 simultaneous sales against 10 units — exactly 10 succeed; 12 bouquet sales against stock for 7 — exactly 7; concurrent counts + sales (4 + 20) — 0 deadlocks. **Left to the patch's own disposable-copy suite:** the pinned observed lock order of the whole frozen path with stock inside it, and the sale-latency gate `HG3b-SALE-LATENCY` (still OPEN since Phase 3B; the deduction adds ≈ 20–50 ms per hot item and must be re-measured, not assumed).

## 7. Findings from the disposable integration harness (2026-11-15) — they correct sections 1–2

`stock-sale-integration.integration.test.ts` (41 tests, real PostgreSQL + Redis, the **unmodified** public sale / cancel routes, the proposed composition applied to the booted instances only — `stock-sale-harness.test.ts`; no frozen file edited; 12/12 mutants of the composition caught):

1. **Lock position on cancellation is stricter than section 2 said.** The frozen cancel locks order → invoice → **customer account** → credit note; the frozen customer sale locks the **customer account** after the stock rows. A cancel that takes its stock locks at the credit-note step (after the account lock) therefore **deadlocks with a sale to the same customer for the same item** — reproduced deterministically with barriers and confirmed by PostgreSQL's own deadlock counter (+1 per run, both methods). Taking the stock locks **before the invoice / account locks** (right after the order lock) makes the same race complete both operations (counter unchanged). The patch must hook `cancelInvoicedOrderInTx` at its start, not only the credit-note call.
2. **Bouquet lines need ONE ascending pass across all lines.** Consuming bouquet lines one by one deadlocks two sales listing the same bouquets in opposite order (proved the same way); locking every stocked line and every bouquet component in a single ascending pass first removes it. Plain multi-item sales (24 concurrent, opposite order, both methods) never deadlocked.
3. **Frozen code cannot return a PAID sale.** The cancel route refuses SETTLED (and CANCELLED / REFUNDED / VOID) invoices; credit-note issuance exists only for full cancellation of an unsettled invoice; the refund route drains a credit-note advance and moves no stock. So the reversal path I-7 can hook today is **full cancellation of an unpaid (ON_CREDIT / partly paid) customer invoice**. "Return of a paid sale" and "partial return" are **not hook points — they are missing frozen features** that need their own design, owner decision and accountant review (this changes what C-3 item 3 can mean). Anonymous walk-in invoices cannot be cancelled at all (`WALKIN_POST_INVOICE_CANCELLATION_NOT_AVAILABLE`).
4. **Proved with the composition**: deduction atomic with the sale (insufficient stock, untracked item, closed period → nothing persisted); COGS = the locked method's cost (900 LOT / 1,050 WAC on the worked example) in ONE entry per sale; retry with the same key replays and deducts once, a new key on the sold order is refused; 25 simultaneous sales vs 10 units → exactly 10 (both methods, no 5xx); cancellation returns stock and value at original cost and posts the mirrored entry, a second cancel moves nothing; bouquet components consumed / returned from the stored explosion even after a recipe edit; a company without a locked method behaves exactly as shipped (no movement, no entry); tenant isolation (foreign tenant, branch-narrowed session) and branch isolation of stock.
5. **Still not measured here:** the sale-latency gate `HG3b-SALE-LATENCY` (open since Phase 3B), and the frozen content-hash / lock-order pins (they change only when the real patch is written).

**Finding (hot-SKU serialisation):** the stock rows are locked first and held to commit, so concurrent sales of the _same_ item queue behind each other for the whole transaction (≈ 165 ms) instead of only for the company document counters. For distinct items there is no measurable per-sale penalty. This is inherent to "re-check availability inside the lock" (rule 23) and to the lock order that removed the deadlocks; it is not a defect, but it caps sales per second of **one** popular SKU at about 6 / s in this container (≈ 12 / s before). Mitigation options for the owner / reviewer (none implemented): keep it (simplest, correct), or shorten the critical section later by moving counter allocation after stock only if the order hierarchy is re-proven. Zero deadlocks in every measured run (`pg_stat_database.deadlocks` unchanged), every sale 200, GL inventory = ledger after each run, both methods.
